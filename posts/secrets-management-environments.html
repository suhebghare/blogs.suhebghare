Secrets Management Across Environments

Why Secrets Management Is Hard

Most teams start with secrets in environment variables, then graduate to .env files, then someone commits one to git and everything breaks. We've been there. The real problem isn't storing secrets — it's the full lifecycle: creation, rotation, access control, auditing, and revocation across multiple environments.

What we were doing wrong (and you probably are too)
  • Secrets hardcoded in Kubernetes manifests (base64 is not encryption)
  • Shared AWS credentials across dev and prod
  • No rotation — some secrets were 3 years old
  • No audit trail — couldn't tell who accessed what
  • Secrets in CI/CD environment variables visible to all repo members

The Architecture We Landed On

AWS Secrets Manager → External Secrets Operator → Kubernetes Secrets → Pods

We evaluated HashiCorp Vault, AWS Secrets Manager, and GCP Secret Manager. We chose AWS Secrets Manager as the source of truth because we're AWS-native, and External Secrets Operator (ESO) to sync them into Kubernetes. This gives us a clean separation: secrets live in one place, Kubernetes just gets read-only synced copies.

AWS Secrets Manager Setup

Naming Convention

Consistent naming is the foundation. We use a strict hierarchy:

# Format: /{environment}/{service}/{secret-name}
/prod/payments-api/db-password
/prod/payments-api/stripe-api-key
/staging/payments-api/db-password
/dev/payments-api/db-password

# Shared secrets (same value across envs)
/shared/datadog/api-key
/shared/pagerduty/integration-key
Why this naming matters

IAM policies can use path-based conditions. A production service's IAM role can be restricted to /prod/payments-api/* only — it literally cannot read staging or other services' secrets even if misconfigured.

IAM Policy Per Service

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "secretsmanager:GetSecretValue",
        "secretsmanager:DescribeSecret"
      ],
      "Resource": "arn:aws:secretsmanager:us-east-1:123456789:secret:/prod/payments-api/*"
    }
  ]
}

Each service gets its own IAM role (via IRSA on EKS) with access only to its own secrets. The payments service cannot read the auth service's secrets. Period.

External Secrets Operator

ESO runs in the cluster and syncs secrets from AWS Secrets Manager into Kubernetes Secrets on a schedule. No init containers, no custom code.

Install ESO

helm repo add external-secrets https://charts.external-secrets.io
helm install external-secrets external-secrets/external-secrets \
  -n external-secrets \
  --create-namespace \
  --set installCRDs=true

ClusterSecretStore (one per cluster)

apiVersion: external-secrets.io/v1beta1
kind: ClusterSecretStore
metadata:
  name: aws-secrets-manager
spec:
  provider:
    aws:
      service: SecretsManager
      region: us-east-1
      auth:
        jwt:
          serviceAccountRef:
            name: external-secrets-sa
            namespace: external-secrets

ExternalSecret (one per service)

apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: payments-api-secrets
  namespace: payments
spec:
  refreshInterval: 1h          # re-sync every hour
  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore
  target:
    name: payments-api-secrets  # name of the K8s Secret created
    creationPolicy: Owner
  data:
    - secretKey: DB_PASSWORD     # key in K8s Secret
      remoteRef:
        key: /prod/payments-api/db-password   # path in Secrets Manager
    - secretKey: STRIPE_API_KEY
      remoteRef:
        key: /prod/payments-api/stripe-api-key

ESO creates a real Kubernetes Secret. Your pod references it normally — no SDK, no sidecar, no code changes:

env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: payments-api-secrets
        key: DB_PASSWORD

Secret Rotation

This is where most setups fall apart. Rotation is useless if your app doesn't pick up the new value.

AWS-Managed Rotation

For RDS passwords, AWS Secrets Manager handles rotation natively. Enable it with a 30-day schedule:

resource "aws_secretsmanager_secret_rotation" "db_password" {
  secret_id           = aws_secretsmanager_secret.db_password.id
  rotation_lambda_arn = aws_lambda_function.rotation.arn

  rotation_rules {
    automatically_after_days = 30
  }
}

The Rotation → Reload Problem

When AWS rotates a secret, ESO picks it up within refreshInterval (we use 1h). But the Kubernetes Secret update doesn't automatically restart pods. We solved this with Reloader:

helm install reloader stakater/reloader -n kube-system

Annotate your deployment:

metadata:
  annotations:
    secret.reloader.stakater.com/reload: "payments-api-secrets"

Now when ESO updates the Kubernetes Secret, Reloader triggers a rolling restart automatically. Zero manual intervention.

Rotation timing gap

There's a window between AWS rotating the secret and ESO syncing it (up to 1h). For database passwords, AWS Secrets Manager keeps the previous version active during this window. For API keys, coordinate rotation with the provider to keep both old and new keys valid briefly.

Environment Isolation

EnvironmentAWS AccountSecret Path PrefixAccess
ProductionSeparate prod account/prod/*Prod EKS IRSA roles only
StagingNon-prod account/staging/*Staging EKS + engineers
DevNon-prod account/dev/*All engineers
CI/CDNon-prod account/ci/*GitHub Actions OIDC role

Production secrets live in a completely separate AWS account. Even if a developer's laptop is compromised, they cannot access prod secrets — they don't have the account access.

CI/CD Secrets (GitHub Actions)

We stopped using GitHub Secrets for anything sensitive. Instead, GitHub Actions assumes an AWS IAM role via OIDC and fetches secrets directly from Secrets Manager at runtime:

# .github/workflows/deploy.yml
- name: Configure AWS credentials
  uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123456789:role/github-actions-deploy
    aws-region: us-east-1

- name: Fetch deploy secrets
  run: |
    export DB_MIGRATION_URL=$(aws secretsmanager get-secret-value \
      --secret-id /ci/deploy/db-migration-url \
      --query SecretString --output text)
    # Use $DB_MIGRATION_URL in subsequent steps

The OIDC trust policy restricts which repos and branches can assume the role:

{
  "Condition": {
    "StringLike": {
      "token.actions.githubusercontent.com:sub": 
        "repo:myorg/myrepo:ref:refs/heads/main"
    }
  }
}

Auditing and Alerting

AWS CloudTrail logs every GetSecretValue call. We ship these to CloudWatch and alert on:

  • Any access to /prod/* secrets from outside the prod account
  • More than 10 GetSecretValue calls in 1 minute from a single identity (potential exfiltration)
  • Access to secrets by IAM users (should only be roles)
  • Failed access attempts (AccessDenied on secrets)
# CloudWatch metric filter for prod secret access anomaly
filter_pattern = '{ ($.eventName = "GetSecretValue") && ($.requestParameters.secretId = "/prod/*") && ($.userIdentity.type != "AssumedRole") }'

Secrets in Terraform State

This one bites everyone. If you create an RDS instance in Terraform, the master password ends up in the state file in plaintext. Our rule: never put secret values in Terraform. Create the secret resource, but set the value out-of-band:

# Create the secret resource (no value)
resource "aws_secretsmanager_secret" "db_password" {
  name = "/prod/payments-api/db-password"
  recovery_window_in_days = 7
}

# Set value separately via CLI or rotation Lambda
# NEVER: aws_secretsmanager_secret_version with plaintext in .tf file

For RDS, use manage_master_user_password = true — AWS manages the password entirely and it never touches Terraform state:

resource "aws_db_instance" "main" {
  # ...
  manage_master_user_password = true  # AWS manages this, never in state
}

What We Learned the Hard Way

Month 1: Migrated all hardcoded secrets to Secrets Manager. Found 3 secrets that were identical across all environments — a sign they were never actually rotated.
Month 2: Deployed ESO. First rotation test failed — pods didn't restart. Added Reloader. Rotation now fully automated.
Month 4: CloudTrail alert fired — a developer's personal AWS profile was accessing staging secrets from their laptop. Tightened IAM to require MFA for human access.
Month 6: Moved prod to a separate AWS account. This was the single biggest security improvement — complete blast radius isolation.
Month 18: Zero leaks. 100% of secrets rotated at least once. Full audit trail for every access.

The Checklist

Secrets management checklist
  • Consistent naming convention with environment prefix
  • Per-service IAM roles with path-scoped access (IRSA on EKS)
  • External Secrets Operator syncing to Kubernetes
  • Reloader for automatic pod restarts on rotation
  • Automated rotation enabled (30-day minimum)
  • Production secrets in a separate AWS account
  • GitHub Actions using OIDC, not stored credentials
  • CloudTrail alerts for anomalous access patterns
  • No secret values in Terraform state
  • Quarterly access review — remove stale permissions
