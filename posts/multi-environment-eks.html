How We Designed Multi-Environment EKS for Production Stability

The Single Cluster vs Multi-Cluster Debate

We tried both. Started with a single cluster using namespace-based isolation. It worked for 18 months. Then a developer on the payments team ran kubectl delete namespace production instead of kubectl delete namespace dev-payments. Twelve microservices went down for 23 minutes. That incident ended the single-cluster experiment.

But multi-cluster isn't free either. It costs more, requires more tooling, and adds operational complexity. Here's how we designed our multi-environment EKS setup after learning from both approaches.

Namespace-Based vs Cluster-Based Isolation

FactorNamespace IsolationCluster Isolation
Security boundarySoft (RBAC, NetworkPolicy)Hard (separate API servers)
Blast radiusHigh (shared control plane)Low (isolated control planes)
CostLow (1 cluster)Higher (N × $73/mo EKS fee)
Resource contentionPossible (shared nodes)None (separate node pools)
ComplianceHarder to auditClear separation for auditors
Operational complexityLowMedium-High
Noisy neighborYes (dev can starve prod)No
🚨 The Incident That Changed Everything

A junior developer had cluster-admin ClusterRole (our RBAC was too permissive). They ran a cleanup script that targeted the wrong namespace. In a shared cluster, kubectl delete namespace is a nuclear option — it deletes everything: deployments, services, configmaps, secrets, PVCs. All gone in seconds. Recovery took 23 minutes because we had to redeploy 12 services and restore 3 configmaps from Git.

Our Final Design: 3 Clusters, 2 AWS Accounts

AWS Account: Non-Production (111111111111)
├── EKS Cluster: dev (us-east-1)
├── EKS Cluster: staging (us-east-1)
AWS Account: Production (222222222222)
└── EKS Cluster: prod (us-east-1)

Why 2 Accounts, Not 3?

Dev and staging share an AWS account because:

  • They share the same compliance requirements (non-production data)
  • Developers need access to both for debugging
  • Cost savings: shared NAT Gateways, shared ECR, shared VPC endpoints
  • Staging uses production-like configs but non-production data — same account is fine

Production gets its own account for hard security boundary, separate billing, and SCPs (Service Control Policies) that prevent accidental resource deletion.

Network Design

VPC Layout

Dev VPC: 10.10.0.0/16 — 3 private subnets, 3 public subnets

Staging VPC: 10.20.0.0/16 — 3 private subnets, 3 public subnets

Prod VPC: 10.30.0.0/16 — 3 private subnets, 3 public subnets

Shared Services VPC: 10.40.0.0/16 — monitoring, ArgoCD, Vault

VPC peering connects the shared services VPC to all three environment VPCs. This allows ArgoCD (running in shared services) to deploy to all clusters, and Prometheus to scrape metrics from all environments.

# Terraform — VPC peering from shared services to prod
resource "aws_vpc_peering_connection" "shared_to_prod" {
  vpc_id        = module.shared_services_vpc.vpc_id
  peer_vpc_id   = module.prod_vpc.vpc_id
  peer_owner_id = var.prod_account_id
  peer_region   = "us-east-1"
  auto_accept   = false

  tags = {
    Name = "shared-services-to-prod"
  }
}

# Route table entry in shared services VPC
resource "aws_route" "shared_to_prod" {
  route_table_id            = module.shared_services_vpc.private_route_table_ids[0]
  destination_cidr_block    = "10.30.0.0/16"
  vpc_peering_connection_id = aws_vpc_peering_connection.shared_to_prod.id
}

Shared Services Cluster

A dedicated small cluster runs cross-cutting tools that serve all environments:

  • 🚀 ArgoCD: Single ArgoCD instance manages deployments across dev, staging, and prod clusters
  • 📊 Prometheus + Grafana: Centralized monitoring with remote-write from each cluster
  • 🔐 HashiCorp Vault: Secrets management for all environments
  • 📋 Backstage: Developer portal and service catalog

💡 Is the Premium Worth It?

That 23-minute production outage from the namespace deletion cost us approximately $18,000 in lost revenue and 40 engineer-hours in incident response. The $1,245/month premium for cluster isolation pays for itself if it prevents even one such incident per year.

Cluster Access Management

Option 1: aws-auth ConfigMap (Legacy)

apiVersion: v1
kind: ConfigMap
metadata:
  name: aws-auth
  namespace: kube-system
data:
  mapRoles: |
    - rolearn: arn:aws:iam::111111111111:role/DevTeamRole
      username: dev-team
      groups:
        - dev-namespace-admin
    - rolearn: arn:aws:iam::222222222222:role/SRETeamRole
      username: sre-team
      groups:
        - system:masters

Option 2: EKS Access Entries (Recommended)

EKS access entries (GA since EKS 1.28) are managed via the AWS API, not a ConfigMap. This means no risk of locking yourself out by misconfiguring aws-auth, and changes are audited in CloudTrail.

resource "aws_eks_access_entry" "dev_team" {
  cluster_name  = aws_eks_cluster.dev.name
  principal_arn = "arn:aws:iam::111111111111:role/DevTeamRole"
  type          = "STANDARD"
}

resource "aws_eks_access_policy_association" "dev_team" {
  cluster_name  = aws_eks_cluster.dev.name
  principal_arn = "arn:aws:iam::111111111111:role/DevTeamRole"
  policy_arn    = "arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewPolicy"

  access_scope {
    type       = "namespace"
    namespaces = ["team-payments", "team-orders"]
  }
}

We use EKS access entries for all new clusters. Developers get namespace-scoped access. SREs get cluster-admin. Nobody gets cross-environment access by default — you must assume a different IAM role to access prod.

Promoting Workloads with ArgoCD ApplicationSets

ArgoCD ApplicationSets let you define a single template that generates Applications for each environment. When you merge to main, the same Helm chart is deployed to dev → staging → prod with environment-specific values.

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: payment-service
  namespace: argocd
spec:
  generators:
    - list:
        elements:
          - cluster: dev
            url: https://dev-cluster.us-east-1.eks.amazonaws.com
            values:
              replicas: "2"
              cpu: "250m"
              memory: "256Mi"
          - cluster: staging
            url: https://staging-cluster.us-east-1.eks.amazonaws.com
            values:
              replicas: "3"
              cpu: "500m"
              memory: "512Mi"
          - cluster: prod
            url: https://prod-cluster.us-east-1.eks.amazonaws.com
            values:
              replicas: "10"
              cpu: "1"
              memory: "1Gi"
  template:
    metadata:
      name: 'payment-service-{{cluster}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/org/helm-charts
        targetRevision: main
        path: charts/payment-service
        helm:
          values: |
            replicas: {{values.replicas}}
            resources:
              requests:
                cpu: {{values.cpu}}
                memory: {{values.memory}}
      destination:
        server: '{{url}}'
        namespace: payments
      syncPolicy:
        automated:
          prune: true
          selfHeal: true

Promotion Flow

Dev (automatic)

Every push to main auto-syncs to dev cluster. No approval needed. Developers can test immediately.

Staging (automatic with gates)

After dev sync succeeds and integration tests pass (ArgoCD sync hook), staging auto-syncs. Smoke tests run post-deploy.

Production (manual approval)

Prod sync requires manual approval in ArgoCD UI or a Slack command. SRE or tech lead approves. Canary rollout strategy applies.

Lessons Learned

Never share clusters between prod and non-prod. RBAC is not a security boundary — it's an authorization layer. A misconfigured ClusterRole or a kubectl context mistake can wipe production. Separate clusters in separate AWS accounts is the only reliable isolation.

Centralize your deployment tooling. Running ArgoCD per cluster creates drift and operational overhead. A single ArgoCD instance in a shared services cluster, with cluster-scoped access to each environment, is simpler and easier to audit.

Plan your CIDR ranges upfront. VPC peering requires non-overlapping CIDRs. If you use 10.0.0.0/16 for everything, you can't peer. We use a /16 per environment with the second octet as the environment identifier (10.10, 10.20, 10.30, 10.40).

✅ Key Takeaway

Multi-cluster EKS costs ~28% more than a single shared cluster. That premium buys you hard security boundaries, zero blast radius between environments, and the peace of mind that a kubectl delete namespace in dev won't take down production. For any organization running production workloads on Kubernetes, the premium is worth it.
