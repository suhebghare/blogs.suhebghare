WAF Rule Group Architecture

We organize our WAF rules into four distinct rule groups, evaluated in priority order. This layered approach ensures that the cheapest checks run first, and expensive regex evaluations only happen on traffic that passes initial filters.

1. IP Reputation Lists → Known bad IPs blocked immediately
2. Rate Limiting → Per-IP throttling (100 req/5min)
3. AWS Managed Rules → Bot Control + Common Rule Set
4. Custom Rules → Bad user agents, scanner paths, geo-blocking

Rule Group 1: IP Reputation Blocking

The first line of defense is the cheapest — blocking known malicious IPs before any further evaluation. We use the AWS-managed AWSManagedRulesAmazonIpReputationList plus a custom IP set updated daily from threat intelligence feeds.

{
  "Name": "IPReputationRule",
  "Priority": 1,
  "Statement": {
    "ManagedRuleGroupStatement": {
      "VendorName": "AWS",
      "Name": "AWSManagedRulesAmazonIpReputationList"
    }
  },
  "OverrideAction": { "None": {} },
  "VisibilityConfig": {
    "SampledRequestsEnabled": true,
    "CloudWatchMetricsEnabled": true,
    "MetricName": "IPReputationRule"
  }
}

Rule Group 2: Rate Limiting

Rate limiting is the single most effective rule we run. It catches distributed attacks, slow scrapers, and brute-force attempts that IP reputation lists miss.

{
  "Name": "RateLimitPerIP",
  "Priority": 2,
  "Statement": {
    "RateBasedStatement": {
      "Limit": 100,
      "AggregateKeyType": "IP",
      "ScopeDownStatement": {
        "NotStatement": {
          "Statement": {
            "IPSetReferenceStatement": {
              "ARN": "arn:aws:wafv2:us-east-1:123456789:regional/ipset/AllowlistedIPs/abc123"
            }
          }
        }
      }
    }
  },
  "Action": { "Block": {} },
  "VisibilityConfig": {
    "SampledRequestsEnabled": true,
    "CloudWatchMetricsEnabled": true,
    "MetricName": "RateLimitPerIP"
  }
}
💡 Pro Tip

Always add a scope-down statement to exclude your allowlisted IPs (monitoring systems, partner integrations, load balancers). We learned this the hard way when our own health checks got rate-limited during a deploy.

Rule Group 3: AWS Managed Bot Control

The AWSManagedRulesBotControlRuleSet is expensive ($10/month + $1 per million requests) but catches sophisticated bots that simple rules miss. It analyzes TLS fingerprints, browser capabilities, and behavioral signals.

Challenge vs Block vs Count Mode

AWS WAF offers three action types, and choosing the wrong one is the most common mistake I see teams make.

Action What It Does When to Use
Count Logs the match but allows the request through Testing new rules, measuring impact before blocking
Block Returns 403 Forbidden immediately High-confidence rules (scanner paths, known bad IPs)
Challenge Presents a CAPTCHA or silent challenge Suspected bots where false positives are possible
⚠️ Never Deploy Rules Directly in Block Mode

Always start in Count mode for at least 72 hours. Analyze the matched requests in WAF logs. Only switch to Block after confirming zero (or acceptable) false positives. We once blocked Googlebot for 6 hours because a regex was too aggressive.

Testing Methodology: Count → Analyze → Block

Our rule deployment process follows a strict three-phase approach:

  1. Deploy in Count mode — Rule matches requests but doesn't block. Run for 72 hours minimum.
  2. Analyze with Athena — Query WAF logs to identify false positives. Check if any legitimate user agents, IPs, or paths are being matched.
  3. Switch to Block mode — After validation, update the rule action. Monitor CloudWatch metrics for the first 24 hours.

WAF Logging to S3 + Athena Analysis

WAF logs go to S3 via Kinesis Firehose. We use Athena to query them for analysis. Here's the Athena table creation and our most-used queries:

-- Create Athena table for WAF logs
CREATE EXTERNAL TABLE waf_logs (
  timestamp bigint,
  formatVersion int,
  webaclId string,
  terminatingRuleId string,
  terminatingRuleType string,
  action string,
  httpSourceName string,
  httpSourceId string,
  ruleGroupList array<struct<
    ruleGroupId:string,
    terminatingRule:struct<ruleId:string,action:string>,
    nonTerminatingMatchingRules:array<struct<ruleId:string,action:string>>
  >>,
  httpRequest struct<
    clientIp:string,
    country:string,
    headers:array<struct<name:string,value:string>>,
    uri:string,
    args:string,
    httpVersion:string,
    httpMethod:string,
    requestId:string
  >
)
ROW FORMAT SERDE 'org.openx.data.jsonserde.JsonSerDe'
LOCATION 's3://my-waf-logs-bucket/AWSLogs/';
-- Top blocked IPs in the last 24 hours
SELECT httpRequest.clientIp, COUNT(*) as block_count
FROM waf_logs
WHERE action = 'BLOCK'
  AND from_unixtime(timestamp/1000) > current_timestamp - interval '24' hour
GROUP BY httpRequest.clientIp
ORDER BY block_count DESC
LIMIT 20;

-- False positive check: blocked requests with common browser user agents
SELECT httpRequest.clientIp, httpRequest.uri,
  filter(httpRequest.headers, h -> h.name = 'user-agent')[1].value as ua
FROM waf_logs
WHERE action = 'BLOCK'
  AND terminatingRuleId = 'BlockBadUserAgents'
  AND from_unixtime(timestamp/1000) > current_timestamp - interval '72' hour
ORDER BY timestamp DESC
LIMIT 100;

False Positive Management

False positives are inevitable. The key is having a fast feedback loop to detect and fix them.

  • CloudWatch alarm on the Count metric for new rules — if it spikes, investigate immediately
  • Weekly Athena audit — review all blocked requests with browser-like user agents
  • Customer support integration — support tickets mentioning "access denied" or "403" trigger an automatic WAF log lookup
  • IP allowlist — maintained in a separate IP set for partners, monitoring tools, and known-good crawlers

Cost Analysis

WAF costs us ~$200/month — $5 per web ACL, $1 per rule, $0.60 per million requests, plus $10/month for Bot Control. Against an estimated $15K/month in abuse handling costs (origin server overload, stolen product data, credential stuffing cleanup), the ROI is 75x.

Real Incident: Residential Proxy Bot Attack

In March 2024, we faced an attack that bypassed every IP-based defense we had. Here's what happened:

Day 1, 02:00 AM — Attack Begins

Login endpoint starts receiving 50K requests/hour. Each request comes from a unique residential IP address. Rate limiting doesn't trigger because no single IP exceeds 100 requests/5 minutes. IP reputation lists don't match because these are clean residential IPs.

Day 1, 06:00 AM — Detection

CloudWatch alarm fires on 401 response rate exceeding 40% on the login endpoint. On-call engineer investigates and sees thousands of unique IPs all hitting /api/auth/login with different email/password combinations.

Day 1, 06:30 AM — Pattern Identified

Athena query reveals the pattern: all requests have identical TLS fingerprints (JA3 hash), identical Accept-Language headers, and arrive in perfectly uniform intervals — 2 requests per second per IP. This is a residential proxy botnet.

Day 1, 07:00 AM — Emergency Rule Deployed

We deploy a rate-based rule scoped to the login endpoint with a much lower threshold (20 requests/5 minutes per IP), combined with a CAPTCHA challenge for all login requests from IPs not seen in the last 30 days (using a custom header set by our CDN).

Day 1, 08:00 AM — Attack Stopped

Bot traffic drops to near zero. The CAPTCHA challenge was the kill shot — residential proxy bots can't solve CAPTCHAs. We later enabled AWS Bot Control's targeted bot protection, which detects residential proxy patterns using TLS fingerprinting.

🚨 Lesson Learned

IP-based rate limiting alone is not enough. Sophisticated attackers use residential proxy networks with millions of clean IPs. You need behavioral analysis (TLS fingerprinting, request patterns, challenge-response) to catch them. AWS Bot Control's targeted protection ($10/month) would have caught this on Day 1.

Key Takeaways

  • Layer your WAF rules: IP reputation → rate limiting → managed rules → custom rules
  • Always deploy new rules in Count mode first — 72 hours minimum
  • Log everything to S3 and query with Athena for analysis
  • IP-based blocking alone won't stop residential proxy botnets
  • CAPTCHA challenges are the most effective defense against sophisticated bots
  • At $200/month, WAF is the highest-ROI security investment you can make
  • Automate false positive detection — don't wait for customer complaints
