How to Design Production-Grade Node Groups (Spot + OnDemand Strategy)

Why Node Group Design Matters

Your node group strategy determines three things: cost (spot vs on-demand mix), reliability (blast radius when a node group has issues), and operational complexity (how many configurations you maintain). Get it wrong and you're either overpaying by 40% or waking up at 3 AM because your batch jobs starved your production APIs of resources.

After running EKS clusters for 4 years across 3 organizations, we settled on a 4-tier node group strategy that balances all three concerns.

The 4-Tier Node Group Strategy

Tier Overview

Tier 1 — System: On-demand, small instances, kube-system only, tainted

Tier 2 — General Workload: Mixed on-demand + spot, m5/m6i family

Tier 3 — Memory-Optimized: r5/r6i for databases and caches

Tier 4 — Spot-Only: For batch jobs and CI runners

Tier 1: System Node Group

This node group runs only kube-system components: CoreDNS, kube-proxy, aws-node (VPC CNI), metrics-server, and cluster-critical add-ons. It's tainted so application workloads never land here.

resource "aws_eks_node_group" "system" {
  cluster_name    = aws_eks_cluster.main.name
  node_group_name = "system-on-demand"
  node_role_arn   = aws_iam_role.node.arn
  subnet_ids      = var.private_subnet_ids
  capacity_type   = "ON_DEMAND"
  instance_types  = ["t3.large", "t3a.large"]

  scaling_config {
    desired_size = 2
    min_size     = 2
    max_size     = 4
  }

  taint {
    key    = "CriticalAddonsOnly"
    value  = "true"
    effect = "NO_SCHEDULE"
  }

  labels = {
    "node-group" = "system"
    "workload"   = "kube-system"
  }
}

Why on-demand: If your system nodes go down, DNS resolution fails, networking breaks, and the entire cluster is effectively dead. Never run system components on spot.

Why small instances: kube-system pods are lightweight. 2 x t3.large (2 vCPU, 8GB each) is more than enough for clusters up to 100 nodes. Smaller instances also mean faster replacement if one fails.

Tier 2: General Workload Node Group

This is where 70% of your application pods run. We use a mix of on-demand (for baseline capacity) and spot (for elastic scaling).

resource "aws_eks_node_group" "general_on_demand" {
  cluster_name    = aws_eks_cluster.main.name
  node_group_name = "general-on-demand"
  node_role_arn   = aws_iam_role.node.arn
  subnet_ids      = var.private_subnet_ids
  capacity_type   = "ON_DEMAND"
  instance_types  = ["m6i.xlarge", "m5.xlarge", "m6a.xlarge"]

  scaling_config {
    desired_size = 6
    min_size     = 4
    max_size     = 8
  }

  labels = {
    "node-group" = "general"
    "capacity"   = "on-demand"
  }
}

resource "aws_eks_node_group" "general_spot" {
  cluster_name    = aws_eks_cluster.main.name
  node_group_name = "general-spot"
  node_role_arn   = aws_iam_role.node.arn
  subnet_ids      = var.private_subnet_ids
  capacity_type   = "SPOT"
  instance_types  = ["m6i.xlarge", "m5.xlarge", "m6a.xlarge",
                     "m5a.xlarge", "m7i.xlarge"]

  scaling_config {
    desired_size = 8
    min_size     = 2
    max_size     = 25
  }

  labels = {
    "node-group" = "general"
    "capacity"   = "spot"
  }
}

Tier 3: Memory-Optimized Node Group

For workloads that need high memory-to-CPU ratios: Redis, Elasticsearch, in-memory caches, and data processing pipelines.

resource "aws_eks_node_group" "memory_optimized" {
  cluster_name    = aws_eks_cluster.main.name
  node_group_name = "memory-optimized-on-demand"
  node_role_arn   = aws_iam_role.node.arn
  subnet_ids      = var.private_subnet_ids
  capacity_type   = "ON_DEMAND"
  instance_types  = ["r6i.xlarge", "r5.xlarge", "r6a.xlarge"]

  scaling_config {
    desired_size = 3
    min_size     = 2
    max_size     = 6
  }

  taint {
    key    = "workload"
    value  = "memory-optimized"
    effect = "NO_SCHEDULE"
  }

  labels = {
    "node-group" = "memory-optimized"
  }
}

Tier 4: Spot-Only (Batch & CI)

resource "aws_eks_node_group" "spot_batch" {
  cluster_name    = aws_eks_cluster.main.name
  node_group_name = "batch-spot"
  node_role_arn   = aws_iam_role.node.arn
  subnet_ids      = var.private_subnet_ids
  capacity_type   = "SPOT"
  instance_types  = ["m5.xlarge", "m5a.xlarge", "m6i.xlarge",
                     "m6a.xlarge", "c5.xlarge", "c5a.xlarge"]

  scaling_config {
    desired_size = 2
    min_size     = 0
    max_size     = 20
  }

  taint {
    key    = "dedicated"
    value  = "batch"
    effect = "NO_SCHEDULE"
  }

  labels = {
    "node-group" = "batch"
    "capacity"   = "spot"
  }
}

Example toleration in a Redis deployment:

spec:
  tolerations:
    - key: "workload"
      operator: "Equal"
      value: "memory-optimized"
      effect: "NoSchedule"
  nodeSelector:
    node-group: memory-optimized

Instance Type Diversification

⚠️ Never Use a Single Instance Type

If you only specify m5.xlarge in a spot node group and AWS reclaims all m5.xlarge capacity in your AZ, your node group can't scale. Always specify 3+ instance types from different families (m5, m6i, m6a) and generations.

Our rule: minimum 3 instance types per node group, spanning at least 2 instance families. For spot groups, we go to 5-6 types for maximum availability.

We use managed node groups for Tier 1 (system) and Tier 3 (memory-optimized) where stability matters. Karpenter NodePools for Tier 2 (general) and Tier 4 (batch) where cost optimization and fast scaling matter.

Launch Template Customization

Key customizations we apply via launch templates:

resource "aws_launch_template" "eks_nodes" {
  name_prefix = "eks-node-"

  # EBS optimization
  block_device_mappings {
    device_name = "/dev/xvda"
    ebs {
      volume_size           = 100
      volume_type           = "gp3"
      iops                  = 3000
      throughput            = 125
      encrypted             = true
      delete_on_termination = true
    }
  }

  # IMDSv2 enforced — prevents SSRF attacks
  metadata_options {
    http_endpoint               = "enabled"
    http_tokens                 = "required"
    http_put_response_hop_limit = 2
  }

  # User data for custom kubelet config
  user_data = base64encode(templatefile("userdata.sh.tpl", {
    cluster_name = var.cluster_name
    max_pods     = 58  # for m5.xlarge with prefix delegation
  }))
}

Node Group Sizing: Min/Max/Desired Strategy

Min: Set to the number of nodes needed to survive a single AZ failure. For 3-AZ clusters, min = desired / 3 × 2 (lose one AZ, keep running).

Max: Set to 3-4x your normal desired count. This gives headroom for traffic spikes without requiring Terraform changes. But set billing alerts — a runaway HPA can scale your cluster to max in minutes.

Desired: Set to your normal steady-state. Let the autoscaler (CA or Karpenter) adjust from there. Don't hardcode desired in Terraform if you're using autoscaling — use lifecycle { ignore_changes = [scaling_config[0].desired_size] }.

✅ Key Takeaway

A well-designed node group strategy isn't about having the most groups — it's about having the right isolation boundaries. System components get their own on-demand nodes. Memory-heavy workloads get right-sized instances. Batch jobs get cheap spot nodes. Everything else lands on the general tier. Four tiers, clear taints, 60% spot usage, 45% cost savings.
