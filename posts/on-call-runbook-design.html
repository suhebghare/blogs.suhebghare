Writing On-Call Runbooks That Actually Work at 3am

📅 December 28, 2024 ⏱ 12 min read 👁 780 reads
👁️780reads
👍334likes
👎19dislikes

It's 3:17am. Your phone is screaming. You're half-asleep, your laptop screen is blinding, and you have 30 seconds to figure out what's on fire. You open the runbook and it says: "Investigate the issue and take appropriate action." Thanks. Very helpful.

I've been on-call for 6 years across 4 organizations. The difference between a 5-minute resolution and a 2-hour firefight almost always comes down to the runbook. Not the engineer's skill — the runbook. A junior engineer with a great runbook will outperform a senior engineer with no runbook every single time at 3am.

What Most Runbooks Get Wrong

  • Too long: 15-page documents that read like architecture docs. Nobody reads 15 pages at 3am.
  • Too vague: "Check the logs for errors." Which logs? Where? What errors?
  • Outdated: References services that were decommissioned 6 months ago, or commands that no longer work.
  • No decision tree: Walls of text instead of "if X, do Y; if Z, do W."
  • Missing escalation paths: No guidance on when to wake someone else up.
  • Written by the person who built the system: They skip steps that are "obvious" to them but not to anyone else.
The Litmus Test

Give your runbook to someone who has never touched the service. If they can't follow it to resolution (or at least to a clear escalation point) within 10 minutes, the runbook is broken.

Anatomy of a Good Runbook

Every runbook should have exactly these sections, in this order. No more, no less.

Runbook Template

1. Alert Name & Severity — What fired and how urgent is it?

2. Impact (1-2 sentences) — What's broken from the user's perspective?

3. Quick Check (30 seconds) — Is this a real problem or a false alarm?

4. Decision Tree — If/then steps based on what you observe.

5. Remediation Steps — Exact commands, copy-pasteable.

6. Verification — How to confirm the fix worked.

7. Escalation — When and who to escalate to.

8. Post-Incident — What to document after resolution.

Decision Tree Format

Decision trees are the single most important improvement you can make to your runbooks. They replace paragraphs of text with a clear flow that a sleep-deprived brain can follow.

High CPU Alert Decision Tree

Alert: CPU > 90% for 5 minutes
Check: Is it a single pod or all pods?
kubectl top pods -n production -l app=api-server
Single pod → Likely a code issue (infinite loop, memory leak causing GC thrash)
→ Restart the pod: kubectl delete pod POD_NAME -n production
→ If it recurs within 10 min, escalate to app team
All pods → Likely a traffic spike or upstream issue
→ Check request rate: sum(rate(http_requests_total{service="api-server"}[5m]))
→ If traffic spike: scale up HPA or add replicas manually
→ If normal traffic: check for slow downstream (DB, cache)

OOMKilled Decision Tree

Alert: Pod OOMKilled
Check: How many times has it restarted?
kubectl describe pod POD_NAME -n production | grep -A5 "Last State"
First occurrence → Likely a traffic spike or large request
→ Pod will auto-restart. Monitor for 10 minutes.
→ If it doesn't recur, no action needed.
Repeated (3+ times) → Memory limit too low or memory leak
→ Check current limits: kubectl get pod POD_NAME -o jsonpath='{.spec.containers[0].resources}'
→ Temporary fix: increase memory limit in deployment
→ File ticket for app team to investigate leak

Pod CrashLoopBackOff Decision Tree

Alert: Pod in CrashLoopBackOff
Check recent events:
kubectl describe pod POD_NAME -n production
Exit Code 1 (application error) → Check logs:
kubectl logs POD_NAME -n production --previous
Exit Code 137 (OOMKilled) → Follow OOMKilled tree above
Exit Code 0 (clean exit) → App thinks it's done. Check entrypoint/CMD config.
ImagePullBackOff → Wrong image tag or registry auth issue
→ Check: kubectl get events -n production --field-selector reason=Failed
→ Verify image exists: aws ecr describe-images --repository-name api-server --image-ids imageTag=LATEST_TAG

DB Connection Exhausted Decision Tree

Alert: DB connection pool exhausted (active connections > 90% of max)
Check current connections:
SELECT count(*) FROM pg_stat_activity WHERE state = 'active';
SELECT count(*) FROM pg_stat_activity WHERE state = 'idle';
Many idle connections → Connection leak in application
→ Identify the culprit: SELECT client_addr, count(*) FROM pg_stat_activity GROUP BY client_addr ORDER BY count DESC;
→ Temporary fix: kill idle connections older than 10 min
→ SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle' AND state_change < now() - interval '10 minutes';
Many active connections → Traffic spike or slow queries
→ Check for slow queries: SELECT pid, now() - pg_stat_activity.query_start AS duration, query FROM pg_stat_activity WHERE state = 'active' ORDER BY duration DESC LIMIT 10;
→ If one query is blocking: consider pg_terminate_backend(pid)
→ If general overload: scale read replicas or enable connection pooling (PgBouncer)

Real Example: CrashLoopBackOff Runbook

Here's a complete runbook for one of the most common Kubernetes alerts. This is the actual format we use.

🚨 Alert: KubePodCrashLooping

Severity: Warning (auto-escalates to Critical after 15 min)

Impact: Service capacity is reduced. If enough pods crash, users will see errors or timeouts.

Quick Check (30 seconds)

# Is it one pod or many?
kubectl get pods -n NAMESPACE -l app=SERVICE_NAME

# Was there a recent deployment?
kubectl rollout history deployment/SERVICE_NAME -n NAMESPACE

If a deployment happened in the last 30 minutes → likely a bad deploy. Roll back:

kubectl rollout undo deployment/SERVICE_NAME -n NAMESPACE

→ Verify pods are stable, then escalate to the deploying team.

If no recent deployment → continue to diagnosis.

Diagnosis

# Check why the pod is crashing
kubectl describe pod POD_NAME -n NAMESPACE | tail -30

# Check application logs from the crashed container
kubectl logs POD_NAME -n NAMESPACE --previous | tail -50
SymptomLikely CauseAction
Exit code 137OOMKilledIncrease memory limit by 50%, file ticket
Exit code 1 + "connection refused" in logsDownstream dependency downCheck dependency status, not an app issue
Exit code 1 + "config error" in logsBad ConfigMap/SecretCheck recent ConfigMap changes, revert if needed
ImagePullBackOff in eventsBad image tag or ECR authVerify image tag, check ECR token expiry
Liveness probe failedApp too slow to startIncrease initialDelaySeconds on liveness probe

Verification

# Confirm pods are running and ready
kubectl get pods -n NAMESPACE -l app=SERVICE_NAME

# Confirm no more restarts (wait 5 minutes)
kubectl get pods -n NAMESPACE -l app=SERVICE_NAME -w

# Check error rate is back to normal
# Grafana: dashboard/service-overview → select SERVICE_NAME

Escalation

Escalate immediately if:

  • More than 50% of pods are crashing
  • The service is customer-facing and errors are visible
  • You can't identify the cause within 15 minutes

Escalation path: #incident-response Slack → @oncall-secondary → Engineering Manager (if P1)

Keeping Runbooks Fresh

The hardest part of runbooks isn't writing them — it's keeping them updated. Here's what actually works:

Link Alerts Directly to Runbooks

Every alert should have a runbook_url annotation that links directly to the relevant runbook. When the on-call engineer gets paged, the runbook is one click away.

- alert: KubePodCrashLooping
  expr: |
    increase(kube_pod_container_status_restarts_total[1h]) > 5
  for: 5m
  labels:
    severity: warning
  annotations:
    summary: "Pod {{ $labels.pod }} is crash looping"
    runbook_url: "https://wiki.internal/runbooks/crashloopbackoff"
    dashboard_url: "https://grafana.internal/d/pod-overview?var-pod={{ $labels.pod }}"

Review Cadence

After Every Incident

The post-incident review must include: "Was there a runbook? Did it help? What was missing?" Update the runbook as part of the incident action items — not as a separate task that gets deprioritized.

Monthly: On-Call Retro

Review all pages from the past month. For each: was the runbook used? Was it accurate? Were there alerts without runbooks? Assign owners for missing or outdated runbooks.

Quarterly: Runbook Audit

Go through every runbook. Delete ones for decommissioned services. Test commands in staging. Have a new team member read through them and flag anything confusing.

The "New Hire Test"

Every quarter, have your newest team member attempt to follow each critical runbook in staging. If they get stuck, the runbook is broken. This is the single most effective way to find gaps. Bonus: it's great onboarding.

Measuring Runbook Effectiveness

You can't improve what you don't measure. Track these metrics before and after implementing structured runbooks:

MTTR
Mean Time to Resolve. The primary metric. Our MTTR dropped from 47 minutes to 12 minutes after implementing decision-tree runbooks.
Escalation Rate
% of incidents escalated beyond the primary on-call. Dropped from 62% to 23%. Engineers could resolve more issues independently.
Runbook Coverage
% of alerts that have a linked runbook. Target: 100% for P1/P2 alerts. We went from 34% to 91% in 3 months.
Runbook Accuracy
% of incidents where the runbook led to resolution without deviation. Track this in post-incident reviews. Target: >80%.

Runbook Anti-Patterns

Anti-PatternWhy It's BadFix
"Check Grafana for anomalies" Which dashboard? Which panel? What's an anomaly? Link to specific dashboard with specific query. Define what "normal" looks like.
"Contact the team lead" Who? What's their number? What if they're on vacation? Use role-based escalation: @oncall-secondary, not person names.
20-step remediation Too many steps = too many places to make mistakes at 3am Automate multi-step remediations into a script. Runbook says: "Run ./scripts/fix-connection-pool.sh"
"Restart the service" How? Which pods? All at once? Rolling? Exact command: kubectl rollout restart deployment/api-server -n production
Runbook in a Google Doc No version control, no review process, no link from alerts Store runbooks in git (markdown), deploy to internal wiki, link from alert annotations.

Automating Runbook Steps

The ultimate goal is to automate yourself out of the runbook. If a runbook step is "restart the pod," that should be automated. If it's "scale up replicas when CPU > 80%," that's an HPA. The runbook should only contain steps that require human judgment.

Automation Progression

Level 0: No runbook. Engineer figures it out from scratch every time.

Level 1: Written runbook with copy-paste commands.

Level 2: Runbook with linked scripts that automate multi-step procedures.

Level 3: Auto-remediation for known issues. Runbook only covers edge cases.

Level 4: Alert is eliminated entirely through architectural improvement.

Most teams are at Level 0-1. Getting to Level 2 is achievable in a quarter and has the highest ROI. Level 3-4 requires investment but eliminates entire categories of pages.

Key Takeaways

A runbook is not documentation — it's a tool for a sleep-deprived engineer to resolve an incident quickly. Write them as decision trees, not essays. Include exact commands, not vague instructions. Link them from alerts so they're one click away. Test them with new team members. Update them after every incident. And measure MTTR to prove they're working. The 2 hours you spend writing a good runbook will save 20 hours of 3am firefighting.
