Zero-Downtime Database Migrations on Live Production Systems

📅 January 8, 2025 ⏱ 15 min read 👁 860 reads
👁️860reads
👍372likes
👎29dislikes

I've shipped hundreds of database migrations to production. Most of them were boring and uneventful — exactly how they should be. But the ones that went wrong? Those are the ones that taught me everything. Including the time an ALTER TABLE locked our primary PostgreSQL database for 8 minutes during peak traffic, causing a full service outage for 2.3 million active users.

Database migrations are the scariest part of any deployment. Code can be rolled back in seconds. A bad database migration can corrupt data, lock tables, or create states that are impossible to undo. This article covers every pattern I've learned for making migrations safe, boring, and zero-downtime.

The Golden Rule

Never assume you can roll back a migration. Design every migration to be forward-only and safe to run while the previous version of your application is still serving traffic.

The Expand-Contract Pattern

This is the only safe way to do schema changes on live production systems. Every migration follows two phases:

Expand: Add new columns/tables. Old code still works. New code can use new schema.
Migrate: Backfill data. Both old and new schemas contain correct data.
Transition: Deploy new code that uses the new schema exclusively.
Contract: Remove old columns/tables. Only new schema remains.

The key insight: at every step, both the old and new versions of your application can run simultaneously. This is what makes zero-downtime possible. During a rolling deployment, some pods are running v1 (old code) and some are running v2 (new code). Both must work with the current database schema.

Safe Migration: Adding a Column

Adding a nullable column is the simplest and safest migration. It's a metadata-only operation in PostgreSQL — no table rewrite, no lock contention:

-- Safe: adds a nullable column, no table lock
ALTER TABLE orders ADD COLUMN shipping_notes TEXT;

-- Also safe: with a non-volatile default (PostgreSQL 11+)
ALTER TABLE orders ADD COLUMN priority INTEGER DEFAULT 0;
PostgreSQL 11+ Changed Everything

Before PostgreSQL 11, adding a column with a DEFAULT value required rewriting the entire table. On a 500GB table, that could take hours and hold an ACCESS EXCLUSIVE lock the entire time. PostgreSQL 11+ stores the default in the catalog metadata, making it instant. If you're on an older version, always add the column as nullable first, then set the default separately.

Dangerous Migration: Renaming a Column

Renaming a column seems simple. It's not. If you run ALTER TABLE orders RENAME COLUMN status TO order_status, every query referencing status will break instantly. During a rolling deployment, old pods still reference the old column name.

The safe approach is a 3-step process spread across 3 separate deployments:

Deploy 1: Expand

Add the new column. Set up a trigger to keep both columns in sync. Backfill existing data.

-- Step 1: Add new column
ALTER TABLE orders ADD COLUMN order_status VARCHAR(50);

-- Step 2: Backfill existing data
UPDATE orders SET order_status = status WHERE order_status IS NULL;
-- Do this in batches for large tables:
-- UPDATE orders SET order_status = status
-- WHERE id BETWEEN 1 AND 100000 AND order_status IS NULL;

-- Step 3: Create trigger to keep columns in sync
CREATE OR REPLACE FUNCTION sync_order_status()
RETURNS TRIGGER AS $$
BEGIN
  IF TG_OP = 'INSERT' OR TG_OP = 'UPDATE' THEN
    IF NEW.order_status IS NULL AND NEW.status IS NOT NULL THEN
      NEW.order_status := NEW.status;
    ELSIF NEW.status IS NULL AND NEW.order_status IS NOT NULL THEN
      NEW.status := NEW.order_status;
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_sync_order_status
BEFORE INSERT OR UPDATE ON orders
FOR EACH ROW EXECUTE FUNCTION sync_order_status();

Deploy 2: Transition

Update application code to read from and write to order_status. The trigger keeps status in sync for any old pods still running.

Deploy 3: Contract

Once all pods are on the new code and you've verified everything works, remove the old column and trigger.

-- Remove the sync trigger
DROP TRIGGER trg_sync_order_status ON orders;
DROP FUNCTION sync_order_status();

-- Remove old column
ALTER TABLE orders DROP COLUMN status;

Yes, this is three deployments for a column rename. That's the cost of zero downtime. If you think this is overkill, you haven't been paged at 2 AM for a broken migration yet.

Adding a NOT NULL Constraint Without Locking

Adding a NOT NULL constraint requires PostgreSQL to scan the entire table to verify no null values exist. On a large table, this holds an ACCESS EXCLUSIVE lock for the duration of the scan. Here's the safe approach:

-- Step 1: Add a CHECK constraint as NOT VALID (instant, no scan)
ALTER TABLE orders
ADD CONSTRAINT orders_email_not_null
CHECK (email IS NOT NULL) NOT VALID;

-- Step 2: Validate the constraint (scans table but only holds
-- a SHARE UPDATE EXCLUSIVE lock — reads and writes still work)
ALTER TABLE orders VALIDATE CONSTRAINT orders_email_not_null;

-- Step 3 (optional): Convert to a proper NOT NULL constraint
-- In PostgreSQL 12+, if a valid CHECK constraint exists,
-- adding NOT NULL is instant because PG trusts the CHECK
ALTER TABLE orders ALTER COLUMN email SET NOT NULL;

-- Step 4: Drop the now-redundant CHECK constraint
ALTER TABLE orders DROP CONSTRAINT orders_email_not_null;

Why this works: The NOT VALID flag tells PostgreSQL to enforce the constraint for new rows immediately but skip validation of existing rows. The VALIDATE CONSTRAINT step scans existing rows but uses a weaker lock that allows concurrent reads and writes.

Index Creation: Always Use CONCURRENTLY

A standard CREATE INDEX holds a lock that blocks all writes to the table for the entire duration of index creation. On a 100M row table, that could be 10-30 minutes of write downtime.

-- WRONG: Blocks all writes for the duration
CREATE INDEX idx_orders_customer_id ON orders(customer_id);

-- RIGHT: Builds index without blocking writes
CREATE INDEX CONCURRENTLY idx_orders_customer_id ON orders(customer_id);
CONCURRENTLY Gotchas

CREATE INDEX CONCURRENTLY cannot run inside a transaction. If your migration framework wraps everything in a transaction (most do), you need to configure it to run this statement outside a transaction. In Rails, use disable_ddl_transaction!. In Django, use SeparateDatabaseAndState. In Flyway, use a separate migration file.

Also watch out for failed concurrent index builds. If the build fails partway through, PostgreSQL leaves behind an INVALID index that still consumes space and slows down writes. Always check for invalid indexes after a migration:

-- Find invalid indexes
SELECT indexrelid::regclass AS index_name,
       indrelid::regclass AS table_name
FROM pg_index
WHERE NOT indisvalid;

-- Drop and retry if found
DROP INDEX CONCURRENTLY idx_orders_customer_id;
CREATE INDEX CONCURRENTLY idx_orders_customer_id ON orders(customer_id);

pt-online-schema-change vs gh-ost

For MySQL, you don't have the luxury of PostgreSQL's transactional DDL. Schema changes on large tables require external tools that create a shadow copy of the table, apply the change, and swap them.

Featurept-online-schema-changegh-ost
MechanismTriggers on original tableReads binlog stream
Trigger overheadYes — adds write latencyNo triggers
PausableLimitedYes — can pause/resume
TestableLimitedYes — can test on replica first
Foreign keysPartial supportNo support
Cut-overRENAME TABLE (brief lock)Atomic cut-over (brief lock)
Recommended forSimpler schemas, FK supportLarge tables, production safety

We use gh-ost for all MySQL migrations on tables over 1GB. The ability to pause, throttle based on replication lag, and test on a replica before running on primary is invaluable. A typical gh-ost command:

gh-ost \
  --host=primary-db.internal \
  --database=production \
  --table=orders \
  --alter="ADD COLUMN shipping_notes TEXT" \
  --chunk-size=1000 \
  --max-lag-millis=1500 \
  --throttle-control-replicas="replica-1.internal,replica-2.internal" \
  --cut-over=default \
  --exact-rowcount \
  --concurrent-rowcount \
  --default-retries=120 \
  --verbose \
  --execute

Migrations in the CI/CD Pipeline

Our migration pipeline enforces safety at every stage:

PR opened → Migration linter checks for unsafe operations (table locks, missing CONCURRENTLY, etc.)
CI → Migration runs against a clone of production schema. Verifies forward and backward compatibility.
Staging → Migration runs against staging DB with production-like data volume.
Production → Migration runs before code deployment. Canary period. Then full rollout.

Our migration linter catches these patterns and fails the PR:

  • ALTER TABLE ... RENAME COLUMN — must use expand-contract
  • ALTER TABLE ... DROP COLUMN — must be in a separate deploy from code changes
  • CREATE INDEX without CONCURRENTLY
  • ALTER TABLE ... ADD COLUMN ... NOT NULL without a default
  • ALTER TABLE ... ALTER COLUMN ... TYPE — column type changes rewrite the table
  • Any migration that takes longer than 10 seconds on the schema clone

Rollback Strategy

Here's the uncomfortable truth: most database migrations cannot be rolled back. If you've added a column and deployed code that writes to it, rolling back the column means losing that data. If you've dropped a column, the data is gone.

Our rollback strategy is based on the expand-contract pattern itself:

  • Expand phase: Rollback is easy — just drop the new column/table. No data loss because nothing was writing to it yet.
  • Transition phase: Rollback means redeploying old code. The old schema still exists, so old code works fine.
  • Contract phase: No rollback possible. This is why we wait at least 1 week between transition and contract, and take a logical backup before contracting.

Always take a backup before the contract phase. We use pg_dump of the specific table before dropping columns. It's saved us twice — once when we discovered a reporting query that still referenced the old column name 3 weeks after the migration.

The Incident: ALTER TABLE That Locked Production

This is the incident that changed how we do migrations forever. A developer ran what seemed like a simple migration:

-- This looks innocent. It is not.
ALTER TABLE users ALTER COLUMN email SET NOT NULL;

The users table had 47 million rows. PostgreSQL needed to scan every row to verify no nulls existed. This acquired an ACCESS EXCLUSIVE lock — blocking all reads and writes to the table.

T+0:00 — Migration starts

ALTER TABLE begins. Lock acquired. All queries to the users table start queuing.

T+0:30 — Connection pool saturates

Queued queries consume all available connections. New requests can't get a connection. API starts returning 503s.

T+2:00 — Cascading failure

Services that depend on the users table start timing out. Health checks fail. Kubernetes starts killing pods. Load balancer removes backends.

T+5:00 — Incident declared

On-call engineer identifies the locked query via pg_stat_activity. Debates whether to kill it (losing progress) or wait.

T+8:00 — Migration completes

Lock released. Queued queries flood the database. Brief spike in latency, then recovery. Total downtime: 8 minutes.

The fix was the CHECK NOT VALID + VALIDATE CONSTRAINT pattern described above. The same migration, done safely, took 45 minutes to validate but caused zero downtime because it used a weaker lock.

Migration Safety Checklist

We run through this checklist for every migration before it hits production:

  • Can the old version of the application run with this schema change?
  • Can the new version of the application run without this schema change?
  • Does this migration acquire an ACCESS EXCLUSIVE lock? For how long?
  • Is there a backfill? How long will it take on production data volume?
  • Is CREATE INDEX CONCURRENTLY used for all new indexes?
  • Is the migration idempotent? Can it be safely re-run?
  • What's the rollback plan? Is data loss possible?
  • Has this been tested against a production-sized dataset?

"A boring migration is a successful migration. If your migration is exciting, something has gone wrong."
