Chaos Engineering in Production: How We Break Things on Purpose

📅 December 22, 2024 ⏱ 14 min read 👁 830 reads
👁️830reads
👍355likes
👎25dislikes

In Q3 last year, we ran our first chaos engineering experiment in production. We killed a single pod of our payment processing service during business hours. Within 90 seconds, we discovered that our circuit breaker configuration had a bug — it was set to open after 10 failures, but the health check interval was 30 seconds, meaning the circuit breaker never tripped fast enough. Requests piled up behind a dead pod for over a minute before Kubernetes rescheduled it.

That single experiment led us to find two more critical bugs: a missing retry configuration in our API gateway and a database connection pool that didn't handle reconnection after a pod restart. All three would have caused real customer impact during an actual failure. We found them on our terms, during business hours, with the whole team watching.

That's the value of chaos engineering. You don't do it to break things — you do it to find the things that are already broken but haven't been triggered yet.

The Chaos Maturity Model

You don't start chaos engineering by simulating an AZ failure in production. That's how you create the incident you were trying to prevent. Chaos maturity is a progression:

Level 0: No Chaos

You hope things work. You find out they don't when customers tell you. Most teams are here.

Level 1: Staging Chaos

Kill pods, inject latency, and simulate failures in staging. Build confidence in your tools and processes. This is where you should spend 2-3 months.

Level 2: Production Chaos (Controlled)

Run experiments in production during business hours with the team watching. Small blast radius. Kill one pod, not a whole deployment. Inject 200ms latency, not 30 seconds.

Level 3: Production Chaos (Automated)

Scheduled experiments run automatically. Chaos Monkey-style random pod kills. The system is expected to handle it without human intervention.

Level 4: GameDays

Full-scale failure simulations. AZ failures, database failovers, DNS outages. Cross-team exercises with incident response practice.

We're currently at Level 3 for most services and run Level 4 GameDays quarterly. It took us 8 months to get here from Level 0.

Starting Small: Kill a Pod, Not a Region

Your first chaos experiment should be embarrassingly simple: kill a single pod of a non-critical service and see what happens. If your system can't handle that, you have no business simulating an AZ failure.

Here's what our first experiment looked like:

Experiment #1: Pod Failure — Order Service

Hypothesis: If one pod of the order-service (3 replicas) is killed, the remaining 2 pods will handle traffic with no errors and latency increase under 50ms.

Steady state: Error rate < 0.1%, p99 latency < 200ms, all health checks passing.

Method: kubectl delete pod order-service-abc123 --grace-period=0

Blast radius: 1 pod out of 3. ~33% capacity reduction.

Abort conditions: Error rate > 1% OR p99 latency > 500ms OR any 5xx from downstream services.

What actually happened: The pod was killed. Traffic shifted to the remaining 2 pods within 5 seconds (kube-proxy updated iptables rules). Latency increased by 30ms — within our hypothesis. But we noticed something unexpected: the replacement pod took 45 seconds to become ready because the readiness probe had a 30-second initialDelaySeconds. During those 45 seconds, we were running at 66% capacity. For a service with tight margins, that's a problem during peak traffic.

Action taken: Reduced initialDelaySeconds to 5 seconds, added a proper startup probe, and increased replicas from 3 to 4 for services with slow startup times.

GameDay Planning

A GameDay is a structured chaos engineering exercise involving multiple teams. It's part technical exercise, part incident response drill. Here's our GameDay template:

PhaseDurationActivities
Pre-GameDay (1 week before)2 hoursDefine experiments, set hypotheses, brief all teams, verify monitoring, confirm abort procedures
Setup30 minVerify steady state, confirm all dashboards are live, open incident channel, assign roles (experimenter, observer, scribe)
Experiments2-3 hoursRun experiments sequentially. 15-min recovery between each. Document observations in real time.
Debrief1 hourReview findings, categorize issues by severity, assign action items, update runbooks
Follow-up (1 week after)1 hourReview action item progress, plan next GameDay
The Scribe Role Is Critical

Assign someone whose only job is to document everything in real time — timestamps, observations, metrics, decisions. During the experiment, engineers are focused on the system. Without a scribe, you'll forget half of what happened and lose valuable learnings.

AWS Fault Injection Simulator (FIS)

For AWS-level chaos (not just Kubernetes), we use AWS Fault Injection Simulator. It integrates natively with EC2, ECS, EKS, and RDS. Here's how we set up an AZ failure simulation:

# FIS experiment template — simulate AZ failure
resource "aws_fis_experiment_template" "az_failure" {
  description = "Simulate us-east-1a availability zone failure"
  role_arn    = aws_iam_role.fis_role.arn

  stop_condition {
    source = "aws:cloudwatch:alarm"
    value  = aws_cloudwatch_metric_alarm.error_rate_high.arn
  }

  # Action 1: Stop EC2 instances in the target AZ
  action {
    name      = "stop-instances-az-a"
    action_id = "aws:ec2:stop-instances"

    parameter {
      key   = "startInstancesAfterDuration"
      value = "PT10M"  # Auto-restart after 10 minutes
    }

    target {
      key   = "Instances"
      value = "instances-az-a"
    }
  }

  # Action 2: Inject network disruption to RDS in target AZ
  action {
    name      = "disrupt-rds-network"
    action_id = "aws:network:disrupt-connectivity"

    parameter {
      key   = "duration"
      value = "PT5M"
    }

    parameter {
      key   = "scope"
      value = "availability-zone"
    }

    target {
      key   = "Subnets"
      value = "subnets-az-a"
    }
  }

  # Target: EC2 instances in us-east-1a with chaos-eligible tag
  target {
    name           = "instances-az-a"
    resource_type  = "aws:ec2:instance"
    selection_mode = "ALL"

    resource_tag {
      key   = "chaos-eligible"
      value = "true"
    }

    filter {
      path   = "Placement.AvailabilityZone"
      values = ["us-east-1a"]
    }
  }

  target {
    name           = "subnets-az-a"
    resource_type  = "aws:ec2:subnet"
    selection_mode = "ALL"

    resource_tag {
      key   = "chaos-eligible"
      value = "true"
    }

    filter {
      path   = "AvailabilityZone"
      values = ["us-east-1a"]
    }
  }

  tags = {
    Purpose = "chaos-engineering"
  }
}

The stop_condition is your safety net. If the CloudWatch alarm fires (error rate exceeds threshold), FIS automatically rolls back the experiment. Always configure this.

Chaos Mesh on Kubernetes

For Kubernetes-level chaos, we use Chaos Mesh. It's a CNCF project that runs as a set of CRDs in your cluster. Here are the experiments we run regularly:

Experiment: Pod Failure

apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: pod-kill-order-service
  namespace: chaos-testing
spec:
  action: pod-kill
  mode: one
  selector:
    namespaces:
      - production
    labelSelectors:
      app: order-service
  scheduler:
    cron: "@every 2h"  # Kill a random pod every 2 hours
  duration: "60s"

Experiment: Network Latency Injection

apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: latency-payment-to-db
  namespace: chaos-testing
spec:
  action: delay
  mode: all
  selector:
    namespaces:
      - production
    labelSelectors:
      app: payment-service
  delay:
    latency: "200ms"
    jitter: "50ms"
    correlation: "75"
  direction: to
  target:
    selector:
      namespaces:
        - production
      labelSelectors:
        app: postgres
    mode: all
  duration: "5m"

Getting Management Buy-In

This is the hardest part. "We want to intentionally break production" is a tough sell. Here's what worked for us:

  • Frame it as risk reduction, not breaking things. "We're testing our disaster recovery before a disaster happens" resonates with leadership.
  • Start in staging. Run 3-4 experiments in staging first. Document the bugs you find. Present those findings to leadership: "We found these 3 bugs in staging. They exist in production too. Chaos engineering in production would have caught them before customers did."
  • Quantify the cost of incidents. If your last production incident cost $50K in lost revenue and took 4 hours to resolve, a chaos engineering program that prevents one such incident per quarter pays for itself immediately.
  • Show the blast radius controls. Demonstrate the abort conditions, the stop conditions in FIS, the monitoring dashboards. Show that you're not randomly breaking things — you're running controlled, scientific experiments.
  • Start with non-critical services. Your first production experiment should not be on the payment processing pipeline. Pick an internal tool or a read-only service.
The Pitch That Worked

"We have 99.95% uptime SLO. We've never tested what happens when an AZ goes down. We assume our multi-AZ setup works, but we've never verified it. I'd rather find out it doesn't work on a Tuesday at 2 PM with the team ready than on Black Friday at midnight."

Steady-State Hypothesis

Every chaos experiment must start with a steady-state hypothesis. This is the measurable definition of "the system is working correctly." Without it, you can't tell if the experiment caused a problem or if the system was already degraded.

Our steady-state checklist before every experiment:

  • Error rate below SLO threshold (< 0.1% for critical services)
  • P99 latency within SLO (< 500ms for API, < 2s for web)
  • All health checks passing
  • No active incidents or ongoing deployments
  • No scheduled maintenance windows
  • CPU and memory utilization below 70% (headroom for failover)
  • All replicas running and ready

If any of these conditions aren't met, we postpone the experiment. Running chaos on an already-degraded system doesn't teach you anything useful — it just creates an incident.

Blast Radius Control

The most important principle in chaos engineering is controlling the blast radius. Every experiment should have clearly defined boundaries:

Safe blast radius:

  • Kill 1 pod out of 5
  • Add 100ms latency to one service
  • Fail 5% of requests to a dependency
  • Drain one node in a 20-node cluster

Dangerous blast radius:

  • Kill all pods of a service
  • Add 10s latency to the database
  • Fail 100% of requests to auth service
  • Simulate full AZ failure without testing single-node first

We tag all resources eligible for chaos experiments with chaos-eligible: true. Production databases, stateful services, and anything handling financial transactions are explicitly excluded until we've built sufficient confidence with less critical services.

Key Takeaways

  • Every experiment finds something. In 14 experiments, we've never had one where the system behaved exactly as expected. The gaps between assumption and reality are where incidents live.
  • Start embarrassingly small. Kill one pod. If that breaks things, you have bigger problems than chaos engineering can solve.
  • Steady-state hypothesis is non-negotiable. If you can't define "working correctly" in measurable terms, you can't run a meaningful experiment.
  • Abort conditions save you. Every experiment needs a kill switch. Automate it with CloudWatch alarms or Prometheus alerts.
  • Document everything. The scribe role during GameDays is as important as the engineer running the experiment.
  • Chaos engineering is a practice, not a tool. Chaos Mesh and FIS are just instruments. The value comes from the hypotheses, the observations, and the follow-up actions.

"Chaos engineering is not about breaking things. It's about building confidence in your system's ability to withstand turbulent conditions in production." — Principles of Chaos Engineering
