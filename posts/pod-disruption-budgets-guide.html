PodDisruptionBudgets: Why Most Teams Misconfigure Them

What PodDisruptionBudgets Actually Do

A PodDisruptionBudget (PDB) tells Kubernetes: "during voluntary disruptions, keep at least X pods running." Voluntary disruptions include node drains, cluster upgrades, Karpenter consolidation, and spot instance termination. PDBs do not protect against involuntary disruptions like OOMKills or node failures.

Simple concept. Massively misconfigured in practice. I've audited PDBs across 6 organizations and found critical misconfigurations in every single one.

The 7 Most Common Misconfigurations

Mistake 1: minAvailable=100% — Blocking Node Drains Forever

🚨 The Classic Deadlock

Setting minAvailable: 100% means Kubernetes cannot evict a single pod. Node drains hang indefinitely. Cluster upgrades stall. Karpenter can't consolidate. We've seen this block EKS upgrades for 4+ hours.

# ❌ WRONG — blocks all voluntary disruptions
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-gateway-pdb
spec:
  minAvailable: "100%"
  selector:
    matchLabels:
      app: api-gateway
# ✅ CORRECT — allows 1 pod to be disrupted at a time
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-gateway-pdb
spec:
  minAvailable: "80%"
  selector:
    matchLabels:
      app: api-gateway

For a 5-replica deployment, minAvailable: 80% means 4 pods must stay running — 1 can be evicted at a time. This allows rolling node drains while maintaining availability.

Mistake 2: PDB on a Single-Replica Deployment

# ❌ WRONG — single replica + PDB = can never be evicted
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: worker-pdb
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: worker
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: worker
spec:
  replicas: 1  # only 1 replica!

If you have 1 replica and minAvailable: 1, the pod can never be evicted. The node it's on can never be drained. This is the same as minAvailable: 100% but less obvious.

💡 Fix

Either increase replicas to 2+ or use maxUnavailable: 1 instead. With maxUnavailable: 1, Kubernetes will evict the pod and wait for the replacement to be ready before proceeding.

Mistake 3: Label Selector Mismatch — PDB Applies to Nothing

# PDB targets app: payment-svc
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: payment-svc  # ← typo!
---
# Deployment uses app: payment-service
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
spec:
  selector:
    matchLabels:
      app: payment-service  # ← doesn't match PDB

The PDB matches zero pods. It provides zero protection. Kubernetes won't warn you — kubectl get pdb will show ALLOWED DISRUPTIONS: 0 and CURRENT: 0, which looks correct but means the PDB is orphaned.

Detection:

# Check if PDB is actually protecting pods
kubectl get pdb payment-pdb -o jsonpath='{.status.currentHealthy}'
# If this returns 0 and you have running pods, the selector is wrong

Mistake 4: Too-Tight PDB Blocking Cluster Upgrades

🚨 Real Incident: 4-Hour Upgrade Stall

During an EKS 1.28 → 1.29 upgrade, node drain got stuck on 3 services with minAvailable: 90% and 10 replicas each. That means only 1 pod per service could be evicted at a time. With 45-second startup times, draining a single node took 12 minutes. We had 28 nodes to drain. The upgrade took 4 hours instead of the expected 45 minutes.

Fix: For cluster upgrades, temporarily relax PDBs or use maxUnavailable: 25% which allows faster parallel eviction:

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  maxUnavailable: "25%"  # allows 2-3 pods to be evicted simultaneously
  selector:
    matchLabels:
      app: api-service

Mistake 5: No PDB on Critical Services

Without a PDB, Kubernetes can evict all pods of a service simultaneously during a node drain. If 3 pods of your payment service are on the same node and that node gets drained, all 3 are evicted at once.

Service TypeRecommended PDB
Stateless API (3+ replicas)maxUnavailable: 1 or minAvailable: 80%
Stateful (database, cache)minAvailable: 50% (quorum-aware)
Single-replica workermaxUnavailable: 1
Batch jobsNo PDB needed (jobs are retried)
DaemonSetsNo PDB needed (one per node)

Mistake 6: PDB Without Matching HPA

If your HPA scales down to 2 replicas and your PDB says minAvailable: 2, no pods can ever be evicted. The HPA and PDB are fighting each other.

# HPA can scale to min 2
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  minReplicas: 2
  maxReplicas: 20

# PDB requires 2 always available
apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  minAvailable: 2  # ← deadlock when HPA is at minReplicas

Rule: PDB.minAvailable must be less than HPA.minReplicas. If HPA min is 2, set PDB minAvailable: 1 or use maxUnavailable: 1.

Mistake 7: Forgetting PDB During StatefulSet Rolling Updates

StatefulSets update pods in reverse ordinal order (pod-2, pod-1, pod-0). If your PDB is too restrictive, the rolling update stalls because Kubernetes won't terminate the next pod until the previous one is fully ready.

For a 3-replica StatefulSet with minAvailable: 2: pod-2 is terminated and recreated. If pod-2 takes 3 minutes to become ready, the entire update takes 9+ minutes. With minAvailable: 3, the update never completes.

How to Debug PDB Issues

# List all PDBs and their status
kubectl get pdb -A

# Example output:
# NAMESPACE   NAME          MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
# prod        api-pdb       3               N/A               2                     30d
# prod        payment-pdb   N/A             1                 1                     30d
# prod        orphan-pdb    2               N/A               0                     90d  ← suspicious

# Check if a specific PDB is protecting any pods
kubectl get pdb api-pdb -o yaml | grep -A5 status

# Test eviction API directly
kubectl drain node-xyz --dry-run=client --ignore-daemonsets --delete-emptydir-data
💡 Quick Audit Script

Run this to find PDBs that match zero pods (orphaned PDBs):

#!/bin/bash
for pdb in $(kubectl get pdb -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{"\n"}{end}'); do
  ns=$(echo $pdb | cut -d/ -f1)
  name=$(echo $pdb | cut -d/ -f2)
  current=$(kubectl get pdb $name -n $ns -o jsonpath='{.status.currentHealthy}')
  if [ "$current" = "0" ]; then
    echo "⚠️  ORPHANED: $pdb (currentHealthy=0)"
  fi
done

Right-Sizing PDBs by Workload Type

Decision Framework

High-availability APIs (payment, auth): minAvailable: 80% — always keep most pods running. Pair with pod anti-affinity to spread across nodes.

General microservices: maxUnavailable: 1 — simple, works for any replica count. Allows one pod to be disrupted at a time.

Stateful workloads (Redis, Kafka): minAvailable: 50% — maintain quorum. Never go below majority for consensus-based systems.

Batch/cron jobs: No PDB. Jobs are designed to be retried. A PDB on a Job will block node drains unnecessarily.

✅ Key Takeaway

Every service with 2+ replicas should have a PDB. Use maxUnavailable: 1 as your default — it works for 90% of cases. Audit PDBs quarterly: check for orphaned selectors, deadlocks with HPAs, and overly restrictive values that block cluster operations. A 5-minute audit can prevent a 4-hour upgrade nightmare.
