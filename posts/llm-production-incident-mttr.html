The Real Problem: Signal-to-Noise, Not Tooling

MTTR isn't a tooling problem. You already have Prometheus, Grafana, CloudWatch, Loki, Jaeger, kubectl, and a dozen Slack channels. The problem is that during an incident, you have too much data and not enough context. You're staring at 14 Grafana panels, tailing logs from 3 services, and trying to remember if that deployment 20 minutes ago touched the payment path — all while someone in Slack is asking "is this related to the thing from last week?"

LLMs don't replace SREs. They compress the time between "alert fired" and "I know what's wrong."

Why This Matters in Real Production

Three failure modes kill MTTR in every team I've worked with:

Failure Mode 1: Wrong Signal

The alert fires on CPU. The engineer opens the CPU dashboard. Spends 12 minutes investigating CPU. The actual issue is a downstream database connection timeout that's causing goroutines to pile up — which looks like CPU pressure but isn't the cause.

Failure Mode 2: Context Switching

Grafana → CloudWatch → kubectl → Slack → Jira → back to Grafana. Each tool switch costs 30-90 seconds of cognitive reload. Over a 40-minute incident, you lose 8-10 minutes just navigating between tools.

Failure Mode 3: Cognitive Load at 3am

A well-rested engineer at 2pm can hold 5-6 signals in working memory simultaneously. The same engineer at 3am, jolted awake by PagerDuty, can hold maybe 2-3. The diagnosis that takes 5 minutes during business hours takes 25 minutes at night.

LLMs are good at exactly one thing here: correlating signals across sources and surfacing the most likely explanation. They read every log line, every metric data point, every K8s event — and produce a 5-sentence briefing before you've finished opening your laptop.

Real scenario: Payment service latency spike. Alert fired on p99 latency exceeding 2s. The on-call engineer's instinct was to check CPU (it was at 78%, looked suspicious). The LLM analyzed app logs alongside the metrics and correctly identified Redis connection pool exhaustion — visible in application WARN logs showing redis.clients.jedis.exceptions.JedisExhaustedPoolException 340 times in 5 minutes. The CPU spike was a symptom (threads spinning on connection retries), not the cause. Time to correct diagnosis: 14 seconds after the LLM received the data.

Architecture Deep Dive

The system has four layers. Each one is independently replaceable — you can swap Loki for CloudWatch, GPT-4o for Claude, Slack for Teams — without touching the others.

LLM Incident Assistant — Architecture

Layer 1 — Signal Collection: Prometheus (metrics via HTTP API), Loki/CloudWatch (logs), Jaeger/X-Ray (traces), kubectl (K8s events), ArgoCD/git (recent deployments)

Layer 2 — Context Assembly: Python asyncio fetches all signals in parallel → truncate/summarize to fit token budget → structure into JSON context → serialize to prompt

Layer 3 — LLM Analysis: System prompt (SRE role + JSON output schema) + user prompt (structured context) → GPT-4o / Claude 3.5 Sonnet / Llama 3 (self-hosted)

Layer 4 — Delivery: Slack thread on incident channel, PagerDuty incident note, runbook link if pattern matches known issue

Signal Collection Layer

Each signal source gets a dedicated fetcher. All fetchers take the same inputs: service name and incident_time. All return structured data. The incident window is ±15 minutes from the alert timestamp — wide enough to catch the cause, narrow enough to keep token count manageable.

Real-World Implementation

Below is the actual code we run in production. Each fetcher is a standalone function — easy to test, easy to swap.

Prometheus Metrics Fetcher

Fetches error rate, p99 latency, and pod restarts for the incident window. Returns peak, current, and trend for each metric.

import requests
from datetime import datetime, timedelta

def fetch_prometheus_context(service: str, incident_time: datetime) -> dict:
    base = "http://prometheus:9090"
    start = (incident_time - timedelta(minutes=30)).timestamp()
    end = (incident_time + timedelta(minutes=5)).timestamp()

    queries = {
        "error_rate": f'rate(http_requests_total{{service="{service}",status=~"5.."}}[5m])',
        "latency_p99": f'histogram_quantile(0.99, rate(http_request_duration_seconds_bucket{{service="{service}"}}[5m]))',
        "pod_restarts": f'increase(kube_pod_container_status_restarts_total{{namespace="prod",pod=~"{service}.*"}}[30m])',
    }

    results = {}
    for name, query in queries.items():
        r = requests.get(f"{base}/api/v1/query_range", params={
            "query": query, "start": start, "end": end, "step": "60"
        })
        data = r.json()["data"]["result"]
        if data:
            values = data[0]["values"]
            results[name] = {
                "peak": max(float(v[1]) for v in values),
                "current": float(values[-1][1]),
                "trend": "rising" if float(values[-1][1]) > float(values[0][1]) else "falling"
            }
    return results

CloudWatch Logs Insights Fetcher

Queries the last 500 ERROR/WARN lines from the service's EKS log group. Uses Logs Insights for server-side filtering — never pull raw logs client-side.

import boto3, time
from datetime import datetime, timedelta

def fetch_cloudwatch_logs(service: str, incident_time: datetime, max_lines=500) -> str:
    client = boto3.client("logs", region_name="us-east-1")
    start_ms = int((incident_time - timedelta(minutes=30)).timestamp() * 1000)
    end_ms = int((incident_time + timedelta(minutes=5)).timestamp() * 1000)

    response = client.start_query(
        logGroupName=f"/aws/eks/prod/{service}",
        startTime=start_ms,
        endTime=end_ms,
        queryString=f"""
            fields @timestamp, level, message, traceId
            | filter level in ["ERROR", "WARN"]
            | sort @timestamp desc
            | limit {max_lines}
        """
    )
    query_id = response["queryId"]

    while True:
        result = client.get_query_results(queryId=query_id)
        if result["status"] == "Complete":
            lines = []
            for row in result["results"]:
                fields = {f["field"]: f["value"] for f in row}
                lines.append(
                    f"[{fields.get('@timestamp','')}] "
                    f"{fields.get('level','')} {fields.get('message','')}"
                )
            return "\n".join(lines)
        time.sleep(1)

Loki Alternative (LogQL via HTTP)

If you're running Loki instead of CloudWatch, the fetcher is simpler — no async query polling needed.

import requests
from datetime import datetime, timedelta

def fetch_loki_logs(service: str, incident_time: datetime, max_lines=500) -> str:
    start_ns = int((incident_time - timedelta(minutes=30)).timestamp() * 1e9)
    end_ns = int((incident_time + timedelta(minutes=5)).timestamp() * 1e9)

    r = requests.get("http://loki:3100/loki/api/v1/query_range", params={
        "query": f'{{namespace="prod", app="{service}"}} |= "ERROR" | logfmt',
        "start": start_ns,
        "end": end_ns,
        "limit": max_lines,
        "direction": "backward"
    })
    streams = r.json()["data"]["result"]
    lines = []
    for stream in streams:
        for ts, line in stream["values"]:
            lines.append(line)
    return "\n".join(lines[:max_lines])

Grafana Panel Data Fetcher

Pulls metric data from Grafana's datasource proxy API for the incident window. Useful when your dashboards have custom queries you don't want to duplicate.

import requests
from datetime import datetime, timedelta

def fetch_grafana_panel(dashboard_uid: str, panel_id: int,
                        incident_time: datetime, grafana_url: str, api_key: str) -> dict:
    from_ts = int((incident_time - timedelta(minutes=30)).timestamp() * 1000)
    to_ts = int((incident_time + timedelta(minutes=5)).timestamp() * 1000)

    # Use the data API, not the render API (which returns PNG)
    r = requests.get(
        f"{grafana_url}/api/datasources/proxy/1/api/v1/query_range",
        headers={"Authorization": f"Bearer {api_key}"},
        params={
            "query": "...",  # Replace with your panel's actual query
            "start": from_ts // 1000,
            "end": to_ts // 1000,
            "step": 60
        }
    )
    return r.json()

Context Assembly + LLM Call

This is the core. Fetch all signals in parallel, manage the token budget, build the prompt, call the model.

import asyncio, json
from datetime import datetime
from openai import AsyncOpenAI

client = AsyncOpenAI()

SYSTEM_PROMPT = """You are an SRE incident assistant. You will be given telemetry data
(metrics, logs, k8s events) from a production incident. Analyze the data and respond
with a JSON object containing:
- likely_cause: string (1-2 sentences, specific)
- confidence: "high" | "medium" | "low"
- evidence: list of strings (specific log lines or metric values that support your conclusion)
- recommended_actions: list of strings (ordered by priority, specific commands where possible)
- needs_human_escalation: boolean
- escalation_reason: string (if needs_human_escalation is true)

Be specific. Reference actual values from the data. Do not speculate beyond the evidence."""

async def analyze_incident(
    service: str, incident_time: datetime, alert_description: str
) -> dict:
    # Fetch all signals in parallel
    metrics, logs, k8s_events = await asyncio.gather(
        asyncio.to_thread(fetch_prometheus_context, service, incident_time),
        asyncio.to_thread(fetch_cloudwatch_logs, service, incident_time),
        asyncio.to_thread(fetch_k8s_events, service, incident_time),
    )

    # Token budget management: truncate logs to ~3000 tokens
    log_lines = logs.split("\n")
    if len(log_lines) > 100:
        # Keep first 20 (earliest errors) + last 80 (most recent)
        logs = "\n".join(
            log_lines[:20] + ["...[truncated]..."] + log_lines[-80:]
        )

    user_prompt = f"""Incident: {alert_description}
Service: {service}
Time: {incident_time.isoformat()}

## Metrics (last 30 min)
{json.dumps(metrics, indent=2)}

## Application Logs (ERROR/WARN only)
{logs}

## Kubernetes Events
{k8s_events}

What is the most likely root cause?"""

    response = await client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": user_prompt}
        ],
        response_format={"type": "json_object"},
        temperature=0.1,  # Low temp for factual analysis
        max_tokens=1000
    )

    return json.loads(response.choices[0].message.content)
Token Budget Strategy

GPT-4o's 128k context window is deceptively large. The real constraint is cost: a 50k-token prompt costs ~$0.25. We target 8-12k input tokens per incident — enough for meaningful context, cheap enough to run on every alert. The truncation logic (first 20 + last 80 log lines) preserves both the initial trigger and the most recent state.

PagerDuty Webhook → Lambda Handler

The entry point. PagerDuty fires a webhook on new incidents. Lambda receives it, runs the analysis, posts results to Slack and back to PagerDuty.

import json, asyncio
from datetime import datetime

def lambda_handler(event, context):
    body = json.loads(event["body"])

    # Only trigger on new incidents
    if body["event"]["event_type"] != "incident.trigger":
        return {"statusCode": 200}

    incident = body["event"]["data"]
    service = incident["service"]["name"]
    alert_desc = incident["title"]
    incident_time = datetime.fromisoformat(
        incident["created_at"].replace("Z", "+00:00")
    )

    # Run analysis
    result = asyncio.run(
        analyze_incident(service, incident_time, alert_desc)
    )

    # Post to Slack incident thread
    post_to_slack_thread(
        incident_id=incident["id"],
        analysis=result,
        service=service
    )

    # Add note to PagerDuty incident
    add_pagerduty_note(incident["id"], result)

    return {"statusCode": 200}
Lambda Timeout Gotcha

API Gateway has a 29-second hard timeout. GPT-4o can take 3-8 seconds, plus signal fetching takes 2-5 seconds. Return 200 immediately from the webhook and process asynchronously — either use Lambda with async invocation, or have the webhook handler push to SQS and process from a separate Lambda.

Challenges & Pitfalls

We hit every one of these. Sharing so you don't have to.

1. Token Budget Is Your Biggest Constraint — Not Model Quality

GPT-4o's 128k context window sounds generous. Then you do the math:

ScenarioInput TokensCost per IncidentAt 100 incidents/day
Minimal (metrics + 50 log lines)~3k$0.015$1.50/day
Standard (metrics + 200 log lines + events)~12k$0.06$6/day
Full context (everything, no truncation)~50k$0.25$25/day = $750/mo

Strategy: aggressive pre-filtering. Only ERROR/WARN logs. Only anomalous metric windows. Deduplicate repeated error messages (send count + one example instead of 340 identical lines). Summarize before sending.

2. LLMs Hallucinate Root Causes Confidently

The model will produce a plausible-sounding but completely wrong explanation. It sounds authoritative. It references real metric names. And it's wrong.

Mitigation: Require the evidence field in JSON output. After receiving the response, validate that every evidence string actually appears in the input data (simple substring match). If evidence doesn't match input, downgrade confidence to "low" automatically. Only auto-post "high" confidence analyses to Slack — flag "medium" and "low" for human review.

3. Log Verbosity Explosion During Incidents

When a service is failing, it logs 10x more than normal. A 30-minute incident window might produce 500k log lines. You cannot send all of them.

  • Deduplicate: Group identical error messages, send count + one example
  • Pre-aggregate: Use CloudWatch Logs Insights stats count(*) by message before pulling raw lines
  • Prioritize unique errors: Send the 20 most unique error messages, not the 20 most frequent

4. Trace Correlation Is the Hardest Part

Distributed traces span multiple services. X-Ray trace IDs appear in logs, but correlating them requires joining data from multiple sources. The LLM cannot do this join — you have to do it in code before building the prompt. We built a trace_enricher that takes error trace IDs from logs, fetches the full trace from X-Ray, and includes the span tree in the context. This alone took 3 weeks to get right.

5. The Model Doesn't Know Your System

It doesn't know that your payments-worker service normally runs at 70% memory, or that FailedScheduling events on the batch namespace are expected during off-peak hours.

Solution: Maintain a YAML context file per service. Inject it into the system prompt. 
# service-context/payments-worker.yaml
service: payments-worker
description: "Processes async payment events from SQS. High memory usage is normal (in-memory transaction cache)."
normal_behavior:
  memory_usage: "60-75% is normal, alert only above 85%"
  error_rate: "Baseline 0.1% — Stripe webhook retries cause transient 4xx"
  restart_frequency: "1-2 restarts/day from JVM GC pressure is expected"
known_issues:
  - "CONN_TIMEOUT to payments-db during daily backup window (02:00-02:15 UTC)"
  - "SQS visibility timeout errors are retried automatically, not actionable"
runbook: "https://wiki.internal/runbooks/payments-worker"
on_call_escalation: "#payments-team"

6. Latency: The API Gateway Timeout Trap

GPT-4o takes 3-8 seconds for a 1000-token response. Signal fetching adds 2-5 seconds. If you're calling this synchronously in a Lambda behind API Gateway, you'll hit the 29-second timeout on complex incidents. The fix is simple: async processing. Webhook returns 200 immediately. Lambda (or SQS consumer) processes in the background. Posts to Slack when done.

7. PII and Sensitive Data in Logs

Application logs contain user IDs, emails, IPs, request payloads. Sending these to OpenAI's API violates most privacy policies and potentially GDPR.

✅
Regex scrubbing — Strip emails, IPs, credit card patterns before sending
✅
AWS Bedrock (Claude) — Data stays in your AWS account
✅
Self-hosted Llama 3 70B — Full control on your GPU instances
✅
Structured logging with PII fields — Mask at the application level, not at analysis time

Best Practices

Concrete, actionable lessons from 3 months of running this in production.

Service Context Files

Maintain a YAML file per service (shown above). Include: description, normal behavior baselines, known non-issues, runbook links, escalation channels. Inject the relevant file into the system prompt for every analysis. This single change improved our correct root cause rate from 58% to 71%.

Feedback Loop

After every incident, the on-call engineer rates the LLM analysis: correct, partially correct, or wrong. We store this alongside the prompt and response. Use it to improve prompts and track model accuracy over time.

Don't Auto-Remediate (With One Exception)

Use the LLM for diagnosis, not action. The one exception: if confidence=high AND the recommended action matches a pre-approved safe action (pod restart, cache flush, feature flag toggle), you can auto-execute with a 60-second confirmation window in Slack. If no one cancels within 60 seconds, it runs. This handles the 3am case where the engineer is still waking up.

Pre-Approved Safe Actions Only

We maintain an explicit allowlist: kubectl rollout restart, redis-cli FLUSHDB (non-prod caches only), feature flag disable via LaunchDarkly API. Anything not on the list requires human confirmation regardless of confidence score.

Cost Control: Circuit Breaker

Implement a circuit breaker on LLM API calls. If the API is slow (>15s), expensive (daily spend exceeds threshold), or returning errors — fall back to a simpler keyword-based analysis that pattern-matches known error signatures. Don't let LLM costs scale linearly with incident volume during an outage storm.

Pin Your Model Version

Use gpt-4o-2024-08-06, not gpt-4o. Model updates can change behavior and break your JSON output format. We learned this the hard way when an unannounced model update started returning markdown-wrapped JSON instead of raw JSON, breaking our parser during a SEV1.

Test With Historical Incidents

Before going live, run your system against 50+ past incidents where you know the root cause. Measure accuracy. Tune prompts. We iterated through 4 prompt versions before finding one that consistently produced actionable output. This backtesting phase took 2 weeks and was the highest-ROI time we spent on the project.

Conclusion

The goal isn't to replace the on-call engineer. It's to hand them a briefing document the moment they pick up the page — so they spend their cognitive energy on fixing, not finding.

The 30-minute reduction in MTTR we achieved isn't magic. It's eliminating the time spent context-switching between 5 tools at 3am. The LLM reads every log line, every metric data point, every K8s event, and produces a structured analysis before you've finished opening your laptop.

Think of it as a very fast, very well-read junior engineer who has already read every log line and every metric before you even opened your laptop. It doesn't have your experience or judgment — but it has perfect recall and zero cognitive fatigue. Use it that way.

Start small. Pick one high-frequency alert. Build the fetchers. Wire up the prompt. Test against 10 past incidents. Measure accuracy. Then expand. The architecture is modular — every component is independently replaceable. You don't need to build the whole system on day one.

TL;DR: Feed your logs, metrics, and K8s events into an LLM with a well-structured prompt. Get a root cause analysis in 15 seconds instead of 30 minutes of manual investigation. Pin your model version, scrub PII, implement a feedback loop, and never auto-remediate without a human-approved allowlist.
