Designing Reusable CI/CD Templates

📅 2024 ⏱ 10 min read 👁 500 reads
👁️ 500 reads
👍 294 likes

We support 50+ engineering teams on a shared CI/CD platform. Before we built a template library, every team had their own pipeline — copy-pasted, diverged, unmaintainable. A security fix meant 50 PRs. A new linting standard meant 50 conversations. We fixed this by building reusable CI/CD templates that gave us 95% code reuse and saved 40 hours/month in maintenance.

The Problem With Copy-Paste Pipelines

When every team owns their pipeline YAML, you get drift. Team A upgrades to Node 20, Team B is still on 16. Team C adds SAST scanning, Teams D through Z don't. Someone finds a credentials leak pattern — you need to patch 50 files. We had all of these problems simultaneously.

What we found when we audited 50 pipelines
  • 12 different ways to build a Docker image
  • 8 teams not running any security scanning
  • 23 teams using deprecated action versions
  • No consistent caching strategy — builds averaging 14 minutes
  • Secrets referenced by different names in every repo

Template Architecture

We use GitHub Actions reusable workflows stored in a central platform/ci-templates repo. Teams call them with a single uses: line. The template handles everything — they just pass inputs.

Team Repo
calls template
platform/ci-templates
runs standardized steps
reports back

Repository Structure

platform/ci-templates/
├── .github/workflows/
│   ├── build-docker.yml        # Reusable: build & push Docker image
│   ├── deploy-eks.yml          # Reusable: deploy to EKS via Helm
│   ├── run-tests.yml           # Reusable: test runner (Node/Python/Go/Java)
│   ├── security-scan.yml       # Reusable: Trivy + Semgrep + secret scan
│   └── notify.yml              # Reusable: Slack/PagerDuty notifications
└── docs/
    └── usage.md

The Docker Build Template

This is the most-used template. It handles: layer caching, multi-platform builds, image signing, vulnerability scanning, and ECR push — all standardized.

# .github/workflows/build-docker.yml (in platform/ci-templates repo)
name: Build and Push Docker Image

on:
  workflow_call:
    inputs:
      image-name:
        required: true
        type: string
      dockerfile:
        required: false
        type: string
        default: Dockerfile
      context:
        required: false
        type: string
        default: .
      platforms:
        required: false
        type: string
        default: linux/amd64
      scan-severity:
        required: false
        type: string
        default: HIGH,CRITICAL
    outputs:
      image-tag:
        description: "Full image URI with tag"
        value: ${{ jobs.build.outputs.image-tag }}
    secrets:
      AWS_ROLE_ARN:
        required: true

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}
    permissions:
      id-token: write
      contents: read

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: us-east-1

      - name: Login to ECR
        id: ecr-login
        uses: aws-actions/amazon-ecr-login@v2

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ steps.ecr-login.outputs.registry }}/${{ inputs.image-name }}
          tags: |
            type=sha,prefix=,format=short
            type=ref,event=branch
            type=semver,pattern={{version}}

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: ${{ inputs.context }}
          file: ${{ inputs.dockerfile }}
          platforms: ${{ inputs.platforms }}
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Scan image for vulnerabilities
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ${{ steps.meta.outputs.tags }}
          severity: ${{ inputs.scan-severity }}
          exit-code: 1   # fail build on HIGH/CRITICAL

How a Team Uses It

This is the entire pipeline a team needs to write:

# team-repo/.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    uses: platform/ci-templates/.github/workflows/build-docker.yml@main
    with:
      image-name: payments-api
    secrets:
      AWS_ROLE_ARN: ${{ secrets.AWS_ROLE_ARN }}

That's it. 10 lines. They get caching, scanning, signing, ECR push, and metadata tagging — all maintained by the platform team.

The EKS Deploy Template

# .github/workflows/deploy-eks.yml
name: Deploy to EKS

on:
  workflow_call:
    inputs:
      environment:
        required: true
        type: string          # dev | staging | prod
      service-name:
        required: true
        type: string
      image-tag:
        required: true
        type: string
      helm-chart:
        required: false
        type: string
        default: ./helm
      namespace:
        required: false
        type: string
        default: default
    secrets:
      AWS_ROLE_ARN:
        required: true
      EKS_CLUSTER_NAME:
        required: true

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}   # requires manual approval for prod
    permissions:
      id-token: write
      contents: read

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: us-east-1

      - name: Update kubeconfig
        run: |
          aws eks update-kubeconfig \
            --name ${{ secrets.EKS_CLUSTER_NAME }} \
            --region us-east-1

      - name: Helm deploy
        run: |
          helm upgrade --install ${{ inputs.service-name }} ${{ inputs.helm-chart }} \
            --namespace ${{ inputs.namespace }} \
            --create-namespace \
            --set image.tag=${{ inputs.image-tag }} \
            --set environment=${{ inputs.environment }} \
            --wait \
            --timeout 5m \
            --atomic   # auto-rollback on failure

      - name: Verify rollout
        run: |
          kubectl rollout status deployment/${{ inputs.service-name }} \
            -n ${{ inputs.namespace }} \
            --timeout=3m

The Test Runner Template

One template handles Node, Python, Go, and Java — teams just declare their language:

# .github/workflows/run-tests.yml
on:
  workflow_call:
    inputs:
      language:
        required: true
        type: string    # node | python | go | java
      node-version:
        type: string
        default: '20'
      python-version:
        type: string
        default: '3.11'
      go-version:
        type: string
        default: '1.21'
      test-command:
        type: string
        default: ''     # override if needed

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node
        if: inputs.language == 'node'
        uses: actions/setup-node@v4
        with:
          node-version: ${{ inputs.node-version }}
          cache: npm

      - name: Setup Python
        if: inputs.language == 'python'
        uses: actions/setup-python@v5
        with:
          python-version: ${{ inputs.python-version }}
          cache: pip

      - name: Setup Go
        if: inputs.language == 'go'
        uses: actions/setup-go@v5
        with:
          go-version: ${{ inputs.go-version }}
          cache: true

      - name: Install dependencies
        run: |
          case "${{ inputs.language }}" in
            node)   npm ci ;;
            python) pip install -r requirements.txt ;;
            go)     go mod download ;;
            java)   mvn dependency:resolve -q ;;
          esac

      - name: Run tests
        run: |
          if [ -n "${{ inputs.test-command }}" ]; then
            ${{ inputs.test-command }}
          else
            case "${{ inputs.language }}" in
              node)   npm test ;;
              python) pytest --cov --cov-report=xml ;;
              go)     go test ./... -race -coverprofile=coverage.out ;;
              java)   mvn test ;;
            esac
          fi

      - name: Upload coverage
        uses: codecov/codecov-action@v4
        if: always()
        continue-on-error: true

Composing Templates: Full Pipeline

Teams compose templates into a full pipeline. This is a complete prod-ready pipeline in 40 lines:

# team-repo/.github/workflows/pipeline.yml
name: Pipeline

on:
  push:
    branches: [main, staging]
  pull_request:

jobs:
  test:
    uses: platform/ci-templates/.github/workflows/run-tests.yml@main
    with:
      language: node

  security:
    uses: platform/ci-templates/.github/workflows/security-scan.yml@main

  build:
    needs: [test, security]
    uses: platform/ci-templates/.github/workflows/build-docker.yml@main
    with:
      image-name: payments-api
    secrets:
      AWS_ROLE_ARN: ${{ secrets.AWS_ROLE_ARN }}

  deploy-staging:
    needs: build
    if: github.ref == 'refs/heads/staging'
    uses: platform/ci-templates/.github/workflows/deploy-eks.yml@main
    with:
      environment: staging
      service-name: payments-api
      image-tag: ${{ needs.build.outputs.image-tag }}
    secrets:
      AWS_ROLE_ARN: ${{ secrets.STAGING_AWS_ROLE_ARN }}
      EKS_CLUSTER_NAME: ${{ secrets.STAGING_CLUSTER }}

  deploy-prod:
    needs: build
    if: github.ref == 'refs/heads/main'
    uses: platform/ci-templates/.github/workflows/deploy-eks.yml@main
    with:
      environment: prod      # triggers manual approval gate
      service-name: payments-api
      image-tag: ${{ needs.build.outputs.image-tag }}
    secrets:
      AWS_ROLE_ARN: ${{ secrets.PROD_AWS_ROLE_ARN }}
      EKS_CLUSTER_NAME: ${{ secrets.PROD_CLUSTER }}

Versioning Templates

This is critical. If teams pin to @main, a breaking change in the template breaks all 50 pipelines simultaneously. We use semantic versioning via git tags:

# Teams pin to a major version tag
uses: platform/ci-templates/.github/workflows/build-docker.yml@v2

# We maintain v1, v2 tags — breaking changes bump major version
# Teams opt-in to upgrades on their schedule
StrategyRiskControlOur recommendation
@mainHigh — any push breaks teamsNoneNever for prod
@v2.1.3Low — fully pinnedFullToo much friction
@v2Low — patch/minor auto-updateGood✓ Our choice
@shaNoneMaximumFor security-critical steps

Enforcing Template Adoption

Offering templates isn't enough — teams default to copy-paste. We enforced adoption through:

  • Repository templates — new repos are created from a GitHub template that already has the pipeline wired up
  • CODEOWNERS — platform team is required reviewer for any changes to .github/workflows/
  • Compliance dashboard — weekly report showing which repos are on old pipeline versions
  • Breaking the old way — we deprecated shared IAM credentials that old pipelines depended on, forcing migration

Results After 6 Months

Before

  • 50 unique pipeline files
  • Avg build time: 14 minutes
  • Security fix rollout: 2 weeks
  • 8 teams with no security scanning
  • Platform team: 40h/month on pipeline support

After

  • 5 template files, 50 callers
  • Avg build time: 6 minutes (caching)
  • Security fix rollout: same day
  • 100% teams with security scanning
  • Platform team: <1h/month on pipeline support

Lessons Learned

Start with the most-used workflow. Docker build was used by every team. One template, maximum impact.
Make inputs optional with sensible defaults. Teams shouldn't need to understand the template to use it. The happy path should be zero config.
Version from day one. We didn't, and our first breaking change caused a bad Monday morning for 12 teams.
Escape hatches matter. Always provide a test-command override or similar. Teams with unusual setups will block adoption if they can't customize.
Treat templates like a product. Changelog, migration guides, deprecation notices. Teams are your users.
The single most important thing

Make the template easier to use than writing your own pipeline. If teams have to fight the template, they'll bypass it. Every friction point is a future copy-paste pipeline waiting to happen.
