The AWS Compute Landscape

AWS offers 5 major compute options, and choosing the wrong one can cost you 3-10x more than necessary. After running workloads across all of them, here's my decision framework based on real cost data.

EC2
Full control, any workload
ECS Fargate
Containers, no servers
Lambda
Event-driven, short tasks
AWS Batch
HPC, ML, batch jobs
EKS
Kubernetes orchestration

The T-Instance Trap

T3 instances are cheap but have CPU credits. Once credits are exhausted, performance drops to baseline (20-40% of a vCPU). I've seen production APIs go from 5ms to 500ms latency because they ran out of burst credits at 2 PM. Use T3 for dev/test only. Production gets M or C instances.

Savings Plans vs Reserved Instances

Always prefer Compute Savings Plans over Reserved Instances for most workloads. Same discount, but Savings Plans apply across instance families, regions, and even Fargate. RIs lock you into a specific instance type. The only exception: RIs give you capacity reservation in a specific AZ — useful if you've been hit by capacity issues.

ECS Fargate: When It Beats EC2

Fargate charges per vCPU-hour ($0.04048) and per GB-hour ($0.004445). No cluster management, no patching, no capacity planning.

✅ Fargate Wins When

  • Small team (no dedicated infra engineers)
  • Bursty workloads (scale to zero possible with ECS)
  • Running <20 containers
  • Operational simplicity matters more than cost
  • Short-lived tasks (batch jobs, CI runners)

❌ EC2 Wins When

  • Running 50+ containers (EC2 bin-packing is cheaper)
  • Need GPU instances
  • Steady-state workloads (Savings Plans on EC2 are cheaper)
  • Need specific instance types (high memory, storage)
  • Cost is the primary concern at scale

Fargate cost for a typical web service: 0.5 vCPU + 1GB memory = $0.02024 + $0.004445 = $0.02469/hour = $18.02/month per task. Running 3 tasks for HA = $54.07/month.

Lambda: The 1ms Billing Sweet Spot

Lambda charges $0.0000166667 per GB-second (1ms granularity since 2020). Plus $0.20 per million invocations. It's the cheapest option for very bursty, short-duration workloads.

When Lambda gets expensive: At high sustained throughput, Lambda's per-invocation cost adds up. A function running 256MB for 200ms at 1,000 req/min costs ~$47/month. At 10,000 req/min constant, that's $470/month — Fargate would be $146/month for the same workload.

Migration Checklist for Graviton

Most workloads run on Graviton without changes. Watch out for: native compiled dependencies (C extensions in Python/Node), Docker images (must be multi-arch or arm64), and Java — use Corretto for best Graviton performance. Test with one service first, then roll out.

AWS Batch: For HPC and ML Workloads

AWS Batch manages compute environments for batch processing. It's essentially a job scheduler that provisions EC2 or Fargate resources on demand. No charge for Batch itself — you pay only for the underlying compute.

  • Spot integration: Batch can use Spot instances with automatic retry on interruption. We run ML training jobs at 70% discount.
  • Multi-node parallel jobs: For HPC workloads needing MPI across nodes.
  • Array jobs: Run 10,000 parameter sweep jobs with one API call.

EKS: When the Overhead Is Worth It

EKS costs $0.10/hour ($73/month) for the control plane, plus node costs. The operational overhead is significant — you need expertise in networking, RBAC, upgrades, and monitoring.

✅ EKS Makes Sense

  • Running 50+ microservices
  • Need advanced scheduling (affinity, topology)
  • Multi-cloud or hybrid strategy
  • Team already knows Kubernetes
  • Need service mesh, custom operators

❌ EKS Is Overkill

  • Running <10 services
  • Small team without K8s expertise
  • Simple web apps or APIs
  • Tight budget (control plane + tooling adds up)

Key Takeaways

  • Start with Fargate for simplicity, move to EC2 when cost matters at scale
  • Lambda is cheapest for bursty, short-duration workloads — expensive for steady-state
  • Graviton instances are a free 20% discount — migrate everything you can
  • Compute Savings Plans over Reserved Instances for flexibility
  • EKS only when you need Kubernetes features and have the team to support it
  • Spot instances for fault-tolerant workloads — 70% savings
  • Don't use T-instances in production — burst credit exhaustion causes outages
