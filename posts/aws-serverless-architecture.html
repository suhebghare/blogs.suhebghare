When Serverless Makes Sense (And When It Doesn't)

After building event-driven systems on AWS for the past 6 years, I've learned that serverless isn't a silver bullet — it's a scalpel. It's phenomenal for bursty, event-driven workloads. It's terrible for steady-state, long-running compute. The trick is knowing which one you're dealing with.

✅ Serverless Wins

  • Bursty traffic (0 to 10K req/s in seconds)
  • Event-driven processing (file uploads, webhooks)
  • Low/unpredictable traffic APIs
  • Glue code between AWS services
  • Scheduled jobs (cron-like tasks)

❌ Serverless Loses

  • Steady-state high-throughput APIs (>1000 req/s constant)
  • Long-running processes (>15 min)
  • Workloads needing GPUs or large memory (>10GB)
  • Latency-sensitive apps where cold starts matter
  • Complex stateful workflows (use containers instead)

Real Architecture: Order Processing System

Here's a production order processing system I built that handles 50K+ orders/day. Every component is serverless, and the monthly cost is under $200 for this throughput.

API Gateway
REST API + request validation
Lambda (Order Validator)
Validate payload, check inventory
SQS (Order Queue)
FIFO queue, deduplication
Lambda (Order Processor)
Process payment, create order
DynamoDB
Store order record
EventBridge
Emit OrderCreated event
SNS → Email/SMS
Customer notification

The key design decision: SQS between the validator and processor. This decouples the API response from order processing. The customer gets an immediate "order received" response, and the actual processing happens asynchronously. If the processor fails, the message goes back to the queue — no lost orders.

# SAM template for the order processing pipeline
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31

Resources:
  OrderApi:
    Type: AWS::Serverless::Api
    Properties:
      StageName: prod
      TracingEnabled: true

  OrderValidatorFunction:
    Type: AWS::Serverless::Function
    Properties:
      Handler: validator.handler
      Runtime: python3.12
      MemorySize: 256
      Timeout: 10
      Environment:
        Variables:
          ORDER_QUEUE_URL: !Ref OrderQueue
      Policies:
        - SQSSendMessagePolicy:
            QueueName: !GetAtt OrderQueue.QueueName
      Events:
        PostOrder:
          Type: Api
          Properties:
            RestApiId: !Ref OrderApi
            Path: /orders
            Method: POST

  OrderQueue:
    Type: AWS::SQS::Queue
    Properties:
      QueueName: orders.fifo
      FifoQueue: true
      ContentBasedDeduplication: true
      VisibilityTimeout: 120
      RedrivePolicy:
        deadLetterTargetArn: !GetAtt OrderDLQ.Arn
        maxReceiveCount: 3

  OrderDLQ:
    Type: AWS::SQS::Queue
    Properties:
      QueueName: orders-dlq.fifo
      FifoQueue: true
      MessageRetentionPeriod: 1209600  # 14 days

  OrderProcessorFunction:
    Type: AWS::Serverless::Function
    Properties:
      Handler: processor.handler
      Runtime: python3.12
      MemorySize: 512
      Timeout: 60
      Events:
        SQSEvent:
          Type: SQS
          Properties:
            Queue: !GetAtt OrderQueue.Arn
            BatchSize: 10
            FunctionResponseTypes:
              - ReportBatchItemFailures

Mitigation Strategies

Provisioned Concurrency — When to Use It

Only use provisioned concurrency for latency-sensitive synchronous APIs. At $0.0000041667/GB-second, keeping 10 instances of a 512MB function warm costs ~$54/month. That's worth it for a checkout API, not for a background processor.

# Provisioned concurrency with auto-scaling
Resources:
  MyFunctionAlias:
    Type: AWS::Lambda::Alias
    Properties:
      FunctionName: !Ref MyFunction
      FunctionVersion: !GetAtt MyFunction.Version
      Name: live
      ProvisionedConcurrencyConfig:
        ProvisionedConcurrentExecutions: 10

  AutoScalingTarget:
    Type: AWS::ApplicationAutoScaling::ScalableTarget
    Properties:
      MaxCapacity: 100
      MinCapacity: 5
      ResourceId: !Sub function:${MyFunction}:live
      ScalableDimension: lambda:function:ProvisionedConcurrency
      ServiceNamespace: lambda

  AutoScalingPolicy:
    Type: AWS::ApplicationAutoScaling::ScalingPolicy
    Properties:
      PolicyName: LambdaProvisionedConcurrencyUtilization
      PolicyType: TargetTrackingScaling
      ScalableTargetId: !Ref AutoScalingTarget
      TargetTrackingScalingPolicyConfiguration:
        TargetValue: 0.7
        PredefinedMetricSpecification:
          PredefinedMetricType: LambdaProvisionedConcurrencyUtilization

SnapStart for Java: This is a game-changer. It takes a snapshot of the initialized function and restores it on cold start. We went from 3.2s cold starts to 350ms. Enable it with one line:

SnapStart:
  ApplyOn: PublishedVersions

Visibility Timeout Trap

Set your visibility timeout to at least 6x your Lambda timeout. If your Lambda times out at 60s but visibility timeout is 30s, the message becomes visible again while the first invocation is still running — you get duplicate processing. I've seen this cause double-charges in payment systems.

Dead Letter Queue Setup

Every SQS queue needs a DLQ. Period. Set maxReceiveCount: 3 — if a message fails 3 times, it's a poison pill. Send it to the DLQ and alert on it. We have a Lambda that monitors DLQ depth and pages on-call if it exceeds 10 messages.

# Lambda to monitor DLQ depth — triggered every 5 minutes
import boto3
import os

sqs = boto3.client('sqs')
sns = boto3.client('sns')

def handler(event, context):
    response = sqs.get_queue_attributes(
        QueueUrl=os.environ['DLQ_URL'],
        AttributeNames=['ApproximateNumberOfMessages']
    )
    depth = int(response['Attributes']['ApproximateNumberOfMessages'])

    if depth > 10:
        sns.publish(
            TopicArn=os.environ['ALERT_TOPIC'],
            Subject=f'DLQ Alert: {depth} messages in dead letter queue',
            Message=f'DLQ {os.environ["DLQ_URL"]} has {depth} unprocessed messages. Investigate immediately.'
        )

EventBridge: The Backbone of Event-Driven Architecture

EventBridge replaced SNS as my default event bus. It gives you schema registry, content-based filtering, cross-account events, and archive/replay — all things SNS can't do.

# EventBridge rule with content-based filtering
Resources:
  OrderCreatedRule:
    Type: AWS::Events::Rule
    Properties:
      EventBusName: orders
      EventPattern:
        source:
          - "com.myapp.orders"
        detail-type:
          - "OrderCreated"
        detail:
          orderTotal:
            - numeric: [">=", 1000]
          region:
            - "us-east-1"
            - "eu-west-1"
      Targets:
        - Arn: !GetAtt HighValueOrderFunction.Arn
          Id: high-value-handler
EventBridge 256KB Limit

Events are capped at 256KB. If you're passing large payloads (images, documents), store the data in S3 and pass the S3 key in the event. I've seen teams hit this limit with order events that include full product catalogs — don't embed data, reference it.

Step Functions: Orchestration vs Choreography

Use Step Functions when you need orchestration — a central coordinator that manages the workflow. Use EventBridge when you need choreography — independent services reacting to events.

Orchestration (Step Functions)

  • Order fulfillment with rollback
  • Multi-step approval workflows
  • ETL pipelines with error handling
  • Saga pattern for distributed transactions

Choreography (EventBridge)

  • Notification fanout
  • Audit logging
  • Analytics event streaming
  • Loosely coupled microservices

Step Functions Express Workflows are the hidden gem — they cost $1 per million state transitions (vs $25 for Standard) and support up to 5 minutes execution. Perfect for synchronous request-response patterns.

Real Cost Comparison: Lambda vs ECS Fargate

I ran both architectures in parallel for 30 days on a real API doing 1,000 requests/minute with 200ms average duration.

$47/mo
Lambda (1K req/min, 200ms avg, 256MB)
$73/mo
Fargate (2 tasks, 0.5 vCPU, 1GB)

Lambda wins at this scale. But at 10K req/min constant, the math flips:

$470/mo
Lambda (10K req/min, 200ms avg, 256MB)
$146/mo
Fargate (4 tasks, 1 vCPU, 2GB)
The Crossover Point

In my experience, Lambda becomes more expensive than Fargate at roughly 3,000-5,000 sustained requests/minute, depending on function duration and memory. Below that, Lambda wins on cost and operational simplicity. Above that, containers win on cost.

Production Pitfalls I've Hit

Lambda Concurrency Throttling

Default account limit is 1,000 concurrent executions across ALL functions. A batch job consumed 800 concurrent executions and throttled our production API. Fix: set reserved concurrency on critical functions and request a limit increase to 3,000.

SQS Message Size Limit (256KB)

We tried passing full order payloads through SQS. Worked fine until a customer ordered 200+ items. Fix: use the SQS Extended Client Library — it stores the payload in S3 and passes a pointer through SQS.

Lambda 15-Minute Timeout

A report generation Lambda kept timing out on large datasets. You can't extend beyond 15 minutes. Fix: moved to Step Functions with Map state — split the dataset into chunks, process in parallel, aggregate results.

API Gateway 29-Second Timeout

API Gateway has a hard 29-second timeout you cannot change. Our PDF generation took 45 seconds. Fix: return a 202 Accepted immediately, process async, notify via WebSocket when done.

EventBridge Delivery Failures

EventBridge doesn't retry on Lambda throttling by default. We lost events during a traffic spike. Fix: configure a DLQ on the EventBridge rule target and set retry policy with MaximumRetryAttempts: 3.

Key Takeaways

Serverless Architecture Principles

  • Decouple everything with queues — SQS between every async step
  • Every queue gets a DLQ — no exceptions
  • Set reserved concurrency on critical Lambda functions
  • Use EventBridge over SNS for new event-driven architectures
  • Step Functions for orchestration, EventBridge for choreography
  • Monitor DLQ depth, Lambda throttles, and iterator age for SQS
  • Know your limits: 256KB messages, 15-min Lambda, 29s API Gateway
  • Cost model: Lambda for bursty, Fargate for steady-state
