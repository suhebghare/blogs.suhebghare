Geo-Blocking vs Rate Limiting – What Works?

We Tested Both Under Real Attack Conditions

Every security team eventually faces the same question: should we geo-block suspicious countries or rate-limit aggressively? After running both strategies in production for 8 months on an e-commerce platform handling 12M requests/day, I have real numbers — and the answer isn't what most people expect.

Spoiler: neither approach alone is sufficient. But the data clearly shows which one gives you better protection with fewer casualties.

Geo-Blocking: The Blunt Instrument

Geo-blocking is conceptually simple: identify countries that generate attack traffic but no revenue, and block them entirely. We analyzed 90 days of WAF logs and identified 12 countries that accounted for 67% of malicious traffic but less than 0.1% of purchases.

Our Geo-Block List

After correlating attack origin data with sales data, we blocked these countries at the WAF level:

{
  "Name": "GeoBlockHighRiskCountries",
  "Priority": 5,
  "Statement": {
    "GeoMatchStatement": {
      "CountryCodes": [
        "RU", "CN", "KP", "IR", "VN", "ID",
        "TH", "PH", "BD", "PK", "NG", "UA"
      ]
    }
  },
  "Action": { "Block": {} },
  "VisibilityConfig": {
    "SampledRequestsEnabled": true,
    "CloudWatchMetricsEnabled": true,
    "MetricName": "GeoBlockHighRisk"
  }
}

⚠️ The Hidden Cost

That 0.3% of blocked legitimate users translated to roughly $18K/year in lost revenue. These were expats, travelers, and remote workers accessing our site from blocked countries. We discovered this through customer support tickets — people emailing "your site doesn't work when I'm traveling."

Geo-Blocking Pros and Cons

  • ✅ Immediate, dramatic reduction in attack traffic
  • ✅ Zero computational overhead — blocked at the edge before any processing
  • ✅ Simple to implement and maintain
  • Blocks legitimate users from those countries (expats, travelers, VPN users)
  • Doesn't stop attackers who use VPNs or proxies in allowed countries
  • Can violate business requirements if you have international customers
  • Creates a false sense of security — 33% of attacks still get through

Rate Limiting: The Precision Scalpel

Rate limiting restricts how many requests a single client can make within a time window. It doesn't care where the traffic comes from — it cares about behavior. We implemented rate limiting at multiple levels.

AWS WAF Rate-Based Rule

{
  "Name": "GlobalRateLimit",
  "Priority": 2,
  "Statement": {
    "RateBasedStatement": {
      "Limit": 300,
      "AggregateKeyType": "IP"
    }
  },
  "Action": { "Block": {} },
  "VisibilityConfig": {
    "SampledRequestsEnabled": true,
    "CloudWatchMetricsEnabled": true,
    "MetricName": "GlobalRateLimit"
  }
}

Endpoint-Specific Rate Limits

Different endpoints need different thresholds. A product listing page can tolerate 300 requests/5min, but a login endpoint should allow far fewer.

{
  "Name": "LoginRateLimit",
  "Priority": 3,
  "Statement": {
    "RateBasedStatement": {
      "Limit": 20,
      "AggregateKeyType": "IP",
      "ScopeDownStatement": {
        "ByteMatchStatement": {
          "SearchString": "/api/auth/login",
          "FieldToMatch": { "UriPath": {} },
          "TextTransformations": [
            { "Priority": 0, "Type": "LOWERCASE" }
          ],
          "PositionalConstraint": "STARTS_WITH"
        }
      }
    }
  },
  "Action": { "Block": {} },
  "VisibilityConfig": {
    "SampledRequestsEnabled": true,
    "CloudWatchMetricsEnabled": true,
    "MetricName": "LoginRateLimit"
  }
}

Sliding Window vs Fixed Window

AWS WAF uses a sliding window for rate-based rules (evaluated every 30 seconds over a 5-minute window). This is important to understand because it affects how quickly limits kick in.

Algorithm How It Works Pros Cons
Fixed Window Counter resets at fixed intervals (e.g., every 5 min) Simple, predictable Burst at window boundary (2x limit possible)
Sliding Window Rolling window, evaluated continuously No boundary burst, smoother enforcement Slightly more complex, higher memory usage
💡 AWS WAF Evaluation Delay

AWS WAF rate-based rules have a 30-second evaluation interval. This means an attacker can send up to 30 seconds of traffic before the rule kicks in. For login endpoints, combine WAF rate limiting with application-level throttling for instant enforcement.

Dynamic Rate Limits by User Tier

Not all users should have the same rate limit. We implemented tiered rate limiting using custom headers set by our application:

  • Anonymous users: 100 requests/5 min
  • Authenticated users: 300 requests/5 min
  • Premium/API partners: 1,000 requests/5 min
  • Internal services: Unlimited (allowlisted IPs)

The Hybrid Strategy: Best of Both Worlds

After running both approaches independently, we settled on a hybrid strategy that combines the strengths of each:

1. Geo-block high-risk countries on SENSITIVE endpoints only (login, payment, admin)
2. Rate limit ALL endpoints globally (300 req/5min per IP)
3. Aggressive rate limits on auth endpoints (20 req/5min per IP)
4. CAPTCHA challenge for geo-blocked users who need access (via CloudFront Function)

Real Attack Scenario Walkthrough

Here's how our hybrid strategy handled a real distributed brute-force attack in January 2024:

14:00 — Attack Begins

Login endpoint receives 200K requests/hour from 15,000 unique IPs across 40 countries. Each IP sends 10-15 requests/5min — below our global rate limit but above our login-specific limit.

14:02 — Layer 1: Geo-Blocking Fires

8,400 IPs (56%) are from geo-blocked countries hitting the login endpoint. Blocked immediately. Attack volume drops to 88K requests/hour.

14:05 — Layer 2: Login Rate Limit Fires

Remaining 6,600 IPs exceed the 20 req/5min login-specific rate limit within 5 minutes. 5,800 IPs blocked. Attack volume drops to 12K requests/hour.

14:10 — Layer 3: Bot Control Detects Pattern

AWS Bot Control identifies the remaining 800 IPs as automated based on TLS fingerprinting and request timing patterns. All blocked. Attack effectively neutralized.

14:15 — Total Time to Full Mitigation: 15 minutes

No manual intervention required. On-call engineer reviewed the CloudWatch dashboard and confirmed all layers worked as expected. Zero legitimate users affected.

Implementation Checklist

If you're choosing between geo-blocking and rate limiting, start with rate limiting. It's more precise, has dramatically lower false positive rates, and doesn't require you to make assumptions about where your attackers are. Add geo-blocking as a second layer for sensitive endpoints only.

  1. Deploy global rate limiting (300 req/5min) in Count mode for 72 hours
  2. Analyze WAF logs — identify your actual traffic patterns per endpoint
  3. Set endpoint-specific rate limits (login: 20, API: 100, static: 500)
  4. Switch to Block mode after validation
  5. Analyze attack origin data for 30 days to identify geo-block candidates
  6. Cross-reference with sales/analytics data to quantify revenue impact
  7. Apply geo-blocking to sensitive endpoints only, with CAPTCHA fallback
  8. Set up CloudWatch alarms on both block rates and false positive indicators

Key Takeaways

  • Rate limiting wins on precision: 89% attack reduction with 0.01% false positives vs geo-blocking's 67% reduction with 0.3% false positives
  • Geo-blocking has hidden costs: $18K/year in lost revenue from blocked legitimate users
  • The hybrid approach is optimal: 96% attack reduction with 0.005% false positives
  • Always start with rate limiting — it's the safer, more effective first step
  • Geo-block sensitive endpoints only — never block entire countries from your whole site
  • Measure everything — you can't optimize what you don't measure. Log all WAF actions and query with Athena weekly
