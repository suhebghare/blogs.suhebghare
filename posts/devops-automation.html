What to Automate First

Every team has a list of things they want to automate. The mistake is starting with the most technically interesting one instead of the highest ROI one. Here's the framework we use: frequency × time-per-occurrence × error-rate.

Task Frequency Time Each Error Rate Monthly Cost Automate?
Deploy to production 10/week 45 min 8% 30 hours Yes — first
Provision new service 3/month 4 hours 15% 12 hours Yes — second
DR failover test 1/month 8 hours 25% 8 hours Yes — high error rate
SSL cert renewal 4/year 30 min 5% 0.5 hours Yes — outage risk
One-off data migration 1/year 2 days 10% 1.3 hours No — too rare

The Automation Pyramid

Automate bottom-up. Each layer depends on the one below it being solid:

Layer 5: Operational Automation (auto-scaling, self-healing)
Layer 4: Deployment Automation (GitOps, canary, rollback)
Layer 3: Testing Automation (unit, integration, e2e, security)
Layer 2: CI/CD Pipelines (build, scan, package)
Layer 1: Infrastructure Provisioning (IaC, GitOps)
Don't skip layers

We've seen teams try to build auto-scaling (Layer 5) before they have reliable deployments (Layer 4). The auto-scaler scales up broken code. Fix the foundation first.

Real Automation Wins

Win 1: Automated DR Testing — Saves 8 Hours/Month

Our DR test used to be a manual, all-hands event. Now it runs every Sunday at 3am:

# .github/workflows/dr-test.yml
name: DR Failover Test
on:
  schedule:
    - cron: '0 3 * * 0'  # Every Sunday 3am UTC
  workflow_dispatch:       # Manual trigger option

jobs:
  dr-test:
    runs-on: self-hosted
    environment: dr-test
    steps:
      - name: Failover database to replica
        run: |
          aws rds failover-db-cluster \
            --db-cluster-identifier production-cluster \
            --target-db-instance-identifier production-replica-1

      - name: Wait for failover
        run: |
          aws rds wait db-instance-available \
            --db-instance-identifier production-replica-1
          sleep 60

      - name: Run health checks
        run: |
          for endpoint in checkout payments inventory; do
            status=$(curl -s -o /dev/null -w "%{http_code}" \
              "https://${endpoint}.internal.company.com/health")
            if [ "$status" != "200" ]; then
              echo "FAIL: ${endpoint} returned ${status}"
              exit 1
            fi
            echo "PASS: ${endpoint} healthy"
          done

      - name: Run synthetic transactions
        run: |
          python scripts/synthetic_checkout.py --env dr-test
          python scripts/synthetic_payment.py --env dr-test

      - name: Failback to primary
        if: always()
        run: |
          aws rds failover-db-cluster \
            --db-cluster-identifier production-cluster \
            --target-db-instance-identifier production-primary

      - name: Report results
        if: always()
        run: |
          python scripts/post_dr_report.py \
            --status ${{ job.status }} \
            --slack-channel "#sre-alerts" \
            --pagerduty-service dr-testing

✅ Result

DR test went from a stressful 8-hour manual process (that we skipped 40% of the time) to an automated weekly test that runs while we sleep. We've caught 3 failover issues that would have been outages.

Win 2: Automated Dependency Updates — CVEs Caught in 24h vs 3 Months

We use Renovate Bot to automatically create PRs for dependency updates. The key is the automerge config for patch versions:

// renovate.json
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "extends": ["config:recommended"],
  "schedule": ["every weekday"],
  "platformAutomerge": true,
  "packageRules": [
    {
      "description": "Auto-merge patch updates if tests pass",
      "matchUpdateTypes": ["patch", "pin", "digest"],
      "automerge": true,
      "automergeType": "pr",
      "requiredStatusChecks": ["build", "test", "security-scan"]
    },
    {
      "description": "Group minor updates weekly",
      "matchUpdateTypes": ["minor"],
      "groupName": "minor-updates",
      "schedule": ["before 9am on monday"]
    },
    {
      "description": "Major updates need manual review",
      "matchUpdateTypes": ["major"],
      "automerge": false,
      "labels": ["major-update", "needs-review"]
    },
    {
      "description": "Security updates get priority",
      "matchCategories": ["security"],
      "automerge": true,
      "schedule": ["at any time"],
      "prPriority": 10,
      "labels": ["security"]
    }
  ],
  "vulnerabilityAlerts": {
    "enabled": true,
    "labels": ["security", "vulnerability"]
  }
}

Win 3: GitHub Actions Reusable Workflows

Instead of copying CI configs across 47 repos, we maintain reusable workflows that all services inherit:

# .github/workflows/reusable-build.yml (in shared repo)
name: Reusable Build & Deploy
on:
  workflow_call:
    inputs:
      service_name:
        required: true
        type: string
      environment:
        required: true
        type: string
        default: staging
      run_e2e:
        required: false
        type: boolean
        default: false
    secrets:
      AWS_ACCESS_KEY_ID:
        required: true
      AWS_SECRET_ACCESS_KEY:
        required: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: |
            ${{ env.ECR_REGISTRY }}/${{ inputs.service_name }}:${{ github.sha }}
            ${{ env.ECR_REGISTRY }}/${{ inputs.service_name }}:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max

  security-scan:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Trivy vulnerability scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ${{ env.ECR_REGISTRY }}/${{ inputs.service_name }}:${{ github.sha }}
          severity: CRITICAL,HIGH
          exit-code: 1

  deploy:
    needs: [build, security-scan]
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}
    steps:
      - name: Update ArgoCD application
        run: |
          argocd app set ${{ inputs.service_name }} \
            --parameter image.tag=${{ github.sha }}
          argocd app sync ${{ inputs.service_name }} --async

Each service's workflow is now 10 lines:

# In each service repo: .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [main]

jobs:
  deploy:
    uses: our-org/shared-workflows/.github/workflows/reusable-build.yml@main
    with:
      service_name: checkout-service
      environment: production
      run_e2e: true
    secrets: inherit

Infrastructure Automation: Terraform + Atlantis

All infrastructure changes go through GitOps with Atlantis. No one runs terraform apply locally:

Engineer opens PR with Terraform changes
Atlantis runs terraform plan automatically
Plan output posted as PR comment
2 approvals required
Comment "atlantis apply" to deploy
State locked during apply
# atlantis.yaml (repo-level config)
version: 3
projects:
  - name: production-vpc
    dir: terraform/vpc
    workspace: production
    autoplan:
      when_modified: ["*.tf", "*.tfvars"]
      enabled: true
    apply_requirements: [approved, mergeable]

  - name: production-eks
    dir: terraform/eks
    workspace: production
    autoplan:
      when_modified: ["*.tf", "*.tfvars"]
      enabled: true
    apply_requirements: [approved, mergeable]

Operational Automation

Auto-Scaling Schedules

Our traffic is predictable: 3x during business hours, 0.5x at night. Instead of reactive HPA alone, we use scheduled scaling:

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: checkout-service
  annotations:
    keda.sh/scaled-object: "true"
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: checkout-service
  minReplicas: 3
  maxReplicas: 30
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
---
# KEDA ScaledObject for scheduled scaling
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: checkout-scheduled
spec:
  scaleTargetRef:
    name: checkout-service
  triggers:
    - type: cron
      metadata:
        timezone: America/New_York
        start: "0 8 * * 1-5"   # 8am weekdays
        end: "0 20 * * 1-5"    # 8pm weekdays
        desiredReplicas: "10"   # Pre-scale for business hours

Automation Anti-Patterns

❌
Automating broken processes

If your deploy process is flaky, automating it just makes it fail faster. Fix the process first, then automate it.

❌
No runbook for when automation fails

Every automated process needs a manual fallback. When Atlantis is down, can you still deploy Terraform? When Renovate creates a broken PR, who notices?

❌
No alerting on automation failure

Our DR test ran silently for 3 weeks with a broken health check script. Nobody noticed because we weren't alerting on test failures. Now every automation has a "did it run and succeed?" alert.

❌
Automating without measuring

If you can't measure the before/after, you can't prove the automation was worth building. Track time saved, error rate reduction, and frequency.

2/week → 15/day
Deployment frequency
8% → 1.2%

Where to Start

  1. Audit your team's time. For one week, track every manual task. Categorize by frequency and time spent.
  2. Pick the top 3 by ROI. Use the frequency × time × error-rate formula.
  3. Automate one thing end-to-end. Don't half-automate 5 things. Fully automate 1 thing, prove value, then move to the next.
  4. Add monitoring to every automation. Alert on failure, track success rate, measure time saved.
  5. Write the manual fallback. Before automating, document the manual process. That document becomes your runbook for when automation breaks.

The goal of automation isn't to eliminate humans from the loop. It's to eliminate the boring, repetitive, error-prone parts so humans can focus on the interesting problems. Automate the toil, not the thinking.
