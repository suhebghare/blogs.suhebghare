Why We Built an IDP

Onboarding a new engineer took 3 weeks. Not because the work was complex — because they had to navigate 14 different tools, request access to 6 AWS accounts, figure out which Helm chart to use, and beg the platform team for a namespace. Meanwhile, 40% of our engineering time was spent on infrastructure toil: creating repos, setting up pipelines, provisioning databases, configuring monitoring.

We built an Internal Developer Platform in 6 months. Today, 200+ engineers use it daily. Onboarding takes 2 hours. Infrastructure tickets dropped 70%.

What an IDP Is (and Isn't)

✅ An IDP Is

  • A self-service layer on top of existing infrastructure
  • Golden paths that encode best practices
  • A product built for internal developers
  • Opinionated defaults with escape hatches
  • A way to reduce cognitive load on developers

❌ An IDP Is Not

  • A replacement for Kubernetes or AWS
  • A PaaS (developers still own their services)
  • A ticket system with a UI
  • A one-size-fits-all solution
  • Something you buy off the shelf

The Golden Path

A developer runs one command (or clicks one button in Backstage) and gets everything they need for a production-ready service:

Developer clicks "Create Service" in Backstage
GitHub repo created from template
CI/CD pipeline configured (GitHub Actions)
EKS namespace + RBAC provisioned
Grafana dashboards auto-created
PagerDuty service + escalation policy
ArgoCD Application registered

Total time: 4 minutes. Previously: 3-5 days of tickets and waiting.

Backstage Software Template

This is the template that powers the "Create Service" flow. It defines the input form, the scaffolding steps, and the integrations:

apiVersion: scaffolder.backstage.io/v1beta3
kind: Template
metadata:
  name: microservice-template
  title: Production Microservice
  description: Creates a production-ready microservice with CI/CD, monitoring, and deployment
  tags:
    - recommended
    - golang
    - kubernetes
spec:
  owner: platform-team
  type: service

  parameters:
    - title: Service Details
      required:
        - name
        - team
        - description
      properties:
        name:
          title: Service Name
          type: string
          pattern: '^[a-z][a-z0-9-]*$'
          maxLength: 30
        team:
          title: Owning Team
          type: string
          enum: [checkout, payments, inventory, platform, data]
        description:
          title: Description
          type: string
          maxLength: 200
        language:
          title: Language
          type: string
          default: golang
          enum: [golang, python, nodejs]

    - title: Infrastructure
      properties:
        needs_database:
          title: Needs PostgreSQL database?
          type: boolean
          default: false
        needs_redis:
          title: Needs Redis cache?
          type: boolean
          default: false
        needs_sqs:
          title: Needs SQS queue?
          type: boolean
          default: false

  steps:
    - id: scaffold
      name: Generate Code
      action: fetch:template
      input:
        url: ./skeleton/${{ parameters.language }}
        values:
          name: ${{ parameters.name }}
          team: ${{ parameters.team }}
          description: ${{ parameters.description }}

    - id: create-repo
      name: Create GitHub Repository
      action: publish:github
      input:
        repoUrl: github.com?owner=our-org&repo=${{ parameters.name }}
        defaultBranch: main
        protectDefaultBranch: true
        requireCodeOwnerReviews: true

    - id: create-namespace
      name: Provision Kubernetes Namespace
      action: kubernetes:apply
      input:
        manifest:
          apiVersion: v1
          kind: Namespace
          metadata:
            name: ${{ parameters.name }}
            labels:
              team: ${{ parameters.team }}
              managed-by: backstage

    - id: create-argocd-app
      name: Register with ArgoCD
      action: argocd:create-application
      input:
        appName: ${{ parameters.name }}
        repoUrl: https://github.com/our-org/${{ parameters.name }}
        path: deploy/
        namespace: ${{ parameters.name }}
        cluster: production

    - id: create-database
      name: Provision Database
      if: ${{ parameters.needs_database }}
      action: kubernetes:apply
      input:
        manifest:
          apiVersion: database.crossplane.io/v1alpha1
          kind: PostgreSQLInstance
          metadata:
            name: ${{ parameters.name }}-db
            namespace: ${{ parameters.name }}
          spec:
            parameters:
              storageGB: 20
              version: "15"
            compositionRef:
              name: production-postgresql

    - id: register-catalog
      name: Register in Backstage Catalog
      action: catalog:register
      input:
        repoContentsUrl: ${{ steps['create-repo'].output.repoContentsUrl }}
        catalogInfoPath: /catalog-info.yaml

Crossplane Composition for Self-Service RDS

Developers request a database by creating a simple Kubernetes resource. Crossplane handles the actual AWS provisioning:

apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: production-postgresql
spec:
  compositeTypeRef:
    apiVersion: database.crossplane.io/v1alpha1
    kind: PostgreSQLInstance
  resources:
    - name: rds-instance
      base:
        apiVersion: rds.aws.crossplane.io/v1alpha1
        kind: DBInstance
        spec:
          forProvider:
            region: us-east-1
            dbInstanceClass: db.t3.medium
            engine: postgres
            masterUsername: app_admin
            allocatedStorage: 20
            storageEncrypted: true
            publiclyAccessible: false
            deletionProtection: true
            backupRetentionPeriod: 7
            multiAZ: true
            vpcSecurityGroupIds:
              - sg-0abc123def456
            dbSubnetGroupName: production-db-subnet
            tags:
              - key: managed-by
                value: crossplane
              - key: environment
                value: production
          writeConnectionSecretToRef:
            namespace: crossplane-system
      patches:
        - fromFieldPath: spec.parameters.storageGB
          toFieldPath: spec.forProvider.allocatedStorage
        - fromFieldPath: spec.parameters.version
          toFieldPath: spec.forProvider.engineVersion
        - fromFieldPath: metadata.labels[team]
          toFieldPath: spec.forProvider.tags[2].value
          transforms:
            - type: string
              string:
                fmt: "team-%s"
Why Crossplane over Terraform for self-service?

Crossplane uses Kubernetes CRDs, which means developers interact with infrastructure using the same kubectl they already know. No Terraform state files, no plan/apply workflow, no separate CI pipeline. The platform team defines the Composition (the guardrails), and developers just create a simple resource.

What the Developer Experience Looks Like

Minute 0 — Developer opens Backstage

Clicks "Create" → selects "Production Microservice" template → fills in name, team, language, and infrastructure needs.

Minute 1 — Scaffolding completes

GitHub repo created with CI/CD pipeline, Dockerfile, Helm chart, and catalog-info.yaml. Branch protection enabled.

Minute 2 — Infrastructure provisioned

Kubernetes namespace created. ArgoCD application registered. If database requested, Crossplane starts provisioning RDS (takes ~8 min).

Minute 3 — Observability ready

Grafana dashboard created from template. Prometheus ServiceMonitor configured. PagerDuty service created with team's escalation policy.

Minute 4 — Developer pushes first commit

GitHub Actions builds the image, pushes to ECR, ArgoCD deploys to the namespace. Service is live.

Lessons Learned

✅ What Worked

  • Start with the most painful workflow, not the most impressive feature. We started with "create a new service" because it was the #1 source of tickets. Tempting to build a fancy service mesh dashboard first — don't.
  • Treat the IDP as a product. We ran user interviews, tracked adoption metrics, and iterated based on feedback. The platform team had a product manager.
  • Opinionated defaults with escape hatches. 90% of services use the golden path. The 10% that need custom configs can still override — but they have to justify it.
  • Backstage as the single entry point. One URL for everything: create services, view docs, check deployments, see who owns what.

❌ What Didn't Work

  • Building everything before launching. Our first attempt took 4 months and nobody used it because we built features nobody asked for. V2 launched in 6 weeks with just "create service" and iterated from there.
  • Forcing adoption. Mandating IDP usage created resentment. We switched to making it so good that teams chose it voluntarily. Adoption went from 30% to 85% in 2 months.
  • Ignoring existing workflows. Some teams had working Terraform setups. We built import tools instead of forcing migration.

Where to Start

  1. Survey your developers. Ask: "What takes the most time when you start a new project?" The top answer is your first golden path.
  2. Deploy Backstage. Even without templates, the service catalog alone provides value by answering "who owns this service?"
  3. Build one template. The "create a new service" template. Make it work end-to-end for one language.
  4. Measure adoption. Track how many services are created through the platform vs manually. Target 80% within 3 months.
  5. Iterate based on tickets. Every infra ticket is a feature request for your IDP.

An IDP isn't a project — it's a product. Ship the smallest useful thing, measure adoption, and iterate. The goal isn't a perfect platform; it's a platform that developers actually use.
