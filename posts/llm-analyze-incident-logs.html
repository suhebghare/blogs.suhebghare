Using LLMs to Analyze Incident Logs

The 3am Problem

It's 3:12am. PagerDuty fires. Your checkout service is returning 500s. You SSH into the bastion, pull CloudWatch logs, and stare at 10,000+ log lines from the last 30 minutes. Where do you even start?

This was our reality every other week. Our average RCA time was 45 minutes — not because the fix was complex, but because finding the needle in the log haystack took forever. We built a system that pipes incident logs through GPT-4 with a structured prompt, and it cut our RCA time to 8 minutes.

Architecture

The system is event-driven. When PagerDuty creates an incident, a webhook triggers a Lambda function that pulls relevant logs, sends them to GPT-4, and posts the analysis to a Slack thread.

PagerDuty Incident
Webhook → API Gateway
Lambda (Log Fetcher)
CloudWatch Logs Insights
GPT-4 Analysis
Slack Thread

Step 1: PagerDuty Webhook Setup

PagerDuty sends a webhook on incident creation. We filter for high-urgency incidents only — no point analyzing a warning-level CPU alert:

# PagerDuty webhook payload (simplified)
{
  "event": {
    "event_type": "incident.triggered",
    "data": {
      "id": "P1234ABC",
      "title": "checkout-service: 500 error rate > 5%",
      "urgency": "high",
      "service": {
        "name": "checkout-service"
      },
      "created_at": "2024-03-15T03:12:00Z"
    }
  }
}

Step 2: The Lambda Function

The Lambda function does three things: extracts the service name from the PagerDuty payload, queries CloudWatch Logs Insights for the relevant time window, and sends the logs to GPT-4.

import boto3
import openai
import json
import os
import requests
from datetime import datetime, timedelta

logs_client = boto3.client('logs')
SLACK_WEBHOOK = os.environ['SLACK_WEBHOOK_URL']
OPENAI_API_KEY = os.environ['OPENAI_API_KEY']

SERVICE_LOG_GROUP_MAP = {
    'checkout-service': '/ecs/checkout-service',
    'payment-service': '/ecs/payment-service',
    'inventory-service': '/ecs/inventory-service',
}

def handler(event, context):
    body = json.loads(event['body'])
    incident = body['event']['data']

    if incident.get('urgency') != 'high':
        return {'statusCode': 200, 'body': 'Skipped: low urgency'}

    service_name = incident['service']['name']
    log_group = SERVICE_LOG_GROUP_MAP.get(service_name)
    if not log_group:
        return {'statusCode': 200, 'body': f'No log group mapped for {service_name}'}

    # Fetch logs from 15 minutes before incident
    incident_time = datetime.fromisoformat(
        incident['created_at'].replace('Z', '+00:00')
    )
    start_time = incident_time - timedelta(minutes=15)

    logs = fetch_logs(log_group, start_time, incident_time)
    analysis = analyze_with_gpt4(logs, service_name, incident['title'])
    post_to_slack(analysis, incident)

    return {'statusCode': 200, 'body': 'Analysis posted'}

Step 3: CloudWatch Logs Insights Query

We don't send all 10,000 lines to GPT-4. We use CloudWatch Logs Insights to pre-filter for errors, exceptions, and status codes:

def fetch_logs(log_group, start_time, end_time):
    query = """
    fields @timestamp, @message
    | filter @message like /(?i)(error|exception|fatal|timeout|refused|5\d{2})/
    | sort @timestamp desc
    | limit 200
    """
    response = logs_client.start_query(
        logGroupName=log_group,
        startTime=int(start_time.timestamp()),
        endTime=int(end_time.timestamp()),
        queryString=query
    )
    query_id = response['queryId']

    # Poll for results (Logs Insights is async)
    import time
    while True:
        result = logs_client.get_query_results(queryId=query_id)
        if result['status'] == 'Complete':
            break
        time.sleep(1)

    log_lines = []
    for row in result['results']:
        timestamp = next(f['value'] for f in row if f['field'] == '@timestamp')
        message = next(f['value'] for f in row if f['field'] == '@message')
        log_lines.append(f"[{timestamp}] {message}")

    return "\n".join(log_lines)
Why 200 lines?

GPT-4's context window can handle much more, but we found that 200 pre-filtered error lines give the best signal-to-noise ratio. Sending 2,000 lines increases cost 10x and the analysis quality actually decreases — the model starts hedging with "multiple possible causes."

Step 4: The Prompt Template

This is where the magic happens. A bad prompt gives you "there are errors in the logs." A good prompt gives you actionable RCA. Here's what we use after 4 months of iteration:

ANALYSIS_PROMPT = """You are a senior SRE analyzing production incident logs.

SERVICE: {service_name}
INCIDENT: {incident_title}
TIME WINDOW: {start_time} to {end_time}

LOGS:
{logs}

Analyze these logs and provide:

1. **ROOT CAUSE**: What is the most likely root cause? Be specific.
   Cite exact log lines that support your conclusion.

2. **TIMELINE**: Reconstruct the failure timeline.
   When did the first error appear? Did it cascade?

3. **BLAST RADIUS**: Which components are affected?

4. **IMMEDIATE ACTION**: What should the on-call engineer do RIGHT NOW?
   Be specific — exact commands, not "check the database."

5. **CONFIDENCE**: Rate your confidence in this analysis (HIGH/MEDIUM/LOW)
   and explain what additional data would increase confidence.

Rules:
- Do NOT speculate about causes not supported by the logs
- If logs are insufficient, say so explicitly
- Prefer the simplest explanation that fits the evidence
- If you see a pattern you've seen before, name it
"""
def analyze_with_gpt4(logs, service_name, incident_title):
    openai.api_key = OPENAI_API_KEY

    response = openai.chat.completions.create(
        model="gpt-4",
        messages=[{
            "role": "user",
            "content": ANALYSIS_PROMPT.format(
                service_name=service_name,
                incident_title=incident_title,
                start_time="T-15min",
                end_time="incident time",
                logs=logs
            )
        }],
        max_tokens=800,
        temperature=0.1  # Low temperature = more deterministic
    )
    return response.choices[0].message.content

Step 5: Slack Integration

The analysis posts to a dedicated incident channel with threading:

def post_to_slack(analysis, incident):
    payload = {
        "blocks": [
            {
                "type": "header",
                "text": {
                    "type": "plain_text",
                    "text": f"🤖 AI Log Analysis: {incident['title']}"
                }
            },
            {
                "type": "section",
                "text": {
                    "type": "mrkdwn",
                    "text": analysis
                }
            },
            {
                "type": "context",
                "elements": [{
                    "type": "mrkdwn",
                    "text": f"⚠️ AI-generated analysis. Verify before acting. "
                            f"Incident: {incident['id']}"
                }]
            }
        ]
    }
    requests.post(SLACK_WEBHOOK, json=payload)

What LLMs Are Good At (and Bad At)

✅ Strengths

  • Pattern recognition — spotting connection timeouts, OOM patterns, retry storms across hundreds of log lines
  • Summarization — turning 200 log lines into a 5-sentence narrative
  • Timeline reconstruction — ordering events and identifying cascade patterns
  • Known failure modes — recognizing common patterns like connection pool exhaustion, DNS resolution failures, certificate expiry

❌ Weaknesses

  • Causation vs correlation — "errors started at the same time" doesn't mean one caused the other
  • Novel failure modes — if it hasn't seen the pattern in training data, it guesses poorly
  • Infrastructure context — it doesn't know your network topology, deployment schedule, or recent changes
  • Confidence calibration — it says "HIGH confidence" even when it's wrong

Prompt Engineering Tips for Log Analysis

  1. Set temperature to 0.1-0.2. You want deterministic analysis, not creative writing.
  2. Ask for evidence. "Cite exact log lines" forces the model to ground its analysis in data instead of hallucinating.
  3. Include the confidence rating. It won't be perfectly calibrated, but it makes the model hedge appropriately on ambiguous cases.
  4. Pre-filter logs. Sending only error-level logs improves analysis quality more than sending everything.
  5. Add service context. We append a one-paragraph description of each service's architecture to the prompt. This helps the model understand what "normal" looks like.
  6. Use "Rules" in the prompt. Explicit constraints like "do NOT speculate" measurably reduce hallucination in our testing.

Real Example: Database Connection Pool Exhaustion

Here's an actual (sanitized) analysis the system produced at 2:47am:

🤖 AI Analysis Output

ROOT CAUSE: Database connection pool exhaustion on checkout-service. Log line [02:41:03] ERROR: Unable to acquire connection from pool — timeout after 30000ms appears 47 times starting at 02:41. This was preceded by a spike in slow queries: [02:38:15] WARN: Query execution time 12847ms exceeds threshold.

TIMELINE: 02:38 — slow queries begin → 02:41 — connection pool saturated → 02:42 — HTTP 500s cascade to API gateway → 02:43 — health checks fail → 02:44 — ALB marks targets unhealthy.

IMMEDIATE ACTION: 1) Check RDS Performance Insights for long-running queries: aws rds describe-db-instances --db-instance-identifier checkout-db 2) If a specific query is blocking, kill it via pg_terminate_backend(pid) 3) Temporarily increase pool size: restart with DB_POOL_SIZE=50 (current: 20).

CONFIDENCE: HIGH — classic connection pool exhaustion pattern with clear evidence chain.

The on-call engineer confirmed this was exactly right. The fix took 6 minutes instead of the usual 40+ minutes of log diving.

Limitations and Honest Assessment

When It Fails

About 15% of the time, the analysis is wrong or unhelpful. The most common failure mode: the root cause is in a different service's logs that we didn't query. We're working on cross-service log correlation, but it significantly increases cost and complexity.

This system is a first responder, not a replacement for human judgment. It gives the on-call engineer a starting point — a hypothesis to validate, not a conclusion to trust blindly. The "⚠️ AI-generated analysis. Verify before acting." disclaimer in every Slack message is there for a reason.

The best use of LLMs in incident response isn't replacing engineers — it's giving them a 30-second head start on a problem that used to take 30 minutes to understand.
