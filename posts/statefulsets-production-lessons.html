When to Use StatefulSets

StatefulSets exist for workloads that need one or more of these guarantees:

  • Stable network identity: Each pod gets a predictable DNS name (redis-0.redis-headless.ns.svc.cluster.local)
  • Ordered deployment and scaling: Pods are created sequentially (0, 1, 2) and terminated in reverse order
  • Persistent storage: Each pod gets its own PVC that survives pod restarts and rescheduling

If your workload doesn't need any of these, use a Deployment. StatefulSets add complexity that isn't worth it for stateless services.

PVC Management

StorageClass Selection

Choosing the right StorageClass directly impacts performance and cost:

StorageClassEBS TypeIOPSCost (100GB)Use Case
gp3-standardgp33,000 (baseline)$8/moRedis AOF, general databases
gp3-high-perfgp316,000 (provisioned)$73/moKafka, high-throughput writes
io2-criticalio264,000 (provisioned)$650/moPostgreSQL primary, latency-critical
 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3-standard
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  fsType: ext4
  encrypted: "true"
reclaimPolicy: Retain  # CRITICAL: don't delete PVs on PVC deletion
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
⚠️ Always Use reclaimPolicy: Retain

The default Delete policy destroys the EBS volume when the PVC is deleted. For stateful workloads, this means permanent data loss. We learned this when a developer deleted a test StatefulSet and lost 2 weeks of Elasticsearch indices. Use Retain and clean up volumes manually.

VolumeClaimTemplates

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
spec:
  volumeClaimTemplates:
    - metadata:
        name: redis-data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: gp3-standard
        resources:
          requests:
            storage: 50Gi

Each pod gets its own PVC: redis-data-redis-0, redis-data-redis-1, redis-data-redis-2. These PVCs persist even if the StatefulSet is deleted (with Retain policy).

PVC Retention Policy (Kubernetes 1.27+)

spec:
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain   # keep PVCs when StatefulSet is deleted
    whenScaled: Delete    # delete PVCs when scaling down

This is a game-changer. Before 1.27, scaling down from 5 to 3 replicas left orphaned PVCs (redis-data-redis-3, redis-data-redis-4) that you had to clean up manually. Now Kubernetes handles it.

Ordered vs Parallel Pod Management

spec:
  podManagementPolicy: OrderedReady  # default — sequential
  # or
  podManagementPolicy: Parallel      # all pods start simultaneously

OrderedReady (default): Pods start one at a time. Pod-1 doesn't start until Pod-0 is Running and Ready. Use this for databases where the primary must be up before replicas join.

Parallel: All pods start simultaneously. Use this for workloads where pods are independent (e.g., Elasticsearch data nodes after master election).

Headless Service and DNS

apiVersion: v1
kind: Service
metadata:
  name: redis-headless
spec:
  clusterIP: None  # headless — no load balancing
  selector:
    app: redis
  ports:
    - port: 6379
      targetPort: 6379

With a headless service, each pod gets a DNS A record:

  • redis-0.redis-headless.production.svc.cluster.local
  • redis-1.redis-headless.production.svc.cluster.local
  • redis-2.redis-headless.production.svc.cluster.local

Clients can connect to specific pods by name. Redis Sentinel uses this to discover and monitor individual Redis instances.

The Hard Lessons

Lesson 1: Rolling Update Stuck on Unhealthy Pod

🚨 Real Incident

We updated our Kafka StatefulSet with a new image. Pod kafka-4 was terminated and recreated, but the new version had a config error that prevented it from joining the cluster. The readiness probe failed. Kubernetes waited for kafka-4 to become Ready before proceeding to kafka-3. The rolling update was stuck. For 2 hours, we had a partially-updated Kafka cluster with mixed versions.

Fix: Set spec.updateStrategy.rollingUpdate.maxUnavailable: 1 (Kubernetes 1.24+) and monitor rolling updates with alerts on kube_statefulset_status_update_revision != kube_statefulset_status_current_revision for more than 15 minutes.

For emergency recovery: kubectl rollout undo statefulset/kafka or patch the StatefulSet to use the previous image.

Lesson 2: PVCs Not Deleted When StatefulSet Deleted

Deleting a StatefulSet does not delete its PVCs. This is by design (data safety), but it means orphaned PVCs accumulate. We had 47 orphaned PVCs costing $180/month before we noticed.

# Find orphaned PVCs (PVCs not bound to any running pod)
kubectl get pvc -A --no-headers | while read ns name status rest; do
  if [ "$status" = "Bound" ]; then
    pv=$(kubectl get pvc $name -n $ns -o jsonpath='{.spec.volumeName}')
    pod=$(kubectl get pods -n $ns --field-selector=status.phase=Running \
      -o json | jq -r ".items[].spec.volumes[]?.persistentVolumeClaim.claimName" \
      | grep "^${name}$")
    if [ -z "$pod" ]; then
      echo "ORPHANED: $ns/$name ($pv)"
    fi
  fi
done

Lesson 3: Pod Anti-Affinity Is Critical for HA

Without anti-affinity, Kubernetes might schedule all 3 Redis pods on the same node. If that node fails, you lose your entire Redis cluster.

spec:
  template:
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values: ["redis"]
              topologyKey: kubernetes.io/hostname

Use requiredDuringScheduling for critical stateful workloads. This guarantees each pod runs on a different node. For less critical workloads, preferredDuringScheduling is more flexible.

Lesson 4: Backup Strategy for PVCs

EBS snapshots are your backup mechanism. We use Velero for automated PVC backups:

apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: redis-backup
  namespace: velero
spec:
  schedule: "0 */6 * * *"  # every 6 hours
  template:
    includedNamespaces:
      - production
    includedResources:
      - persistentvolumeclaims
      - persistentvolumes
    labelSelector:
      matchLabels:
        app: redis
    snapshotVolumes: true
    ttl: 168h  # retain for 7 days

Real Redis Sentinel StatefulSet

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
  namespace: production
spec:
  serviceName: redis-headless
  replicas: 3
  podManagementPolicy: OrderedReady
  updateStrategy:
    type: RollingUpdate
  selector:
    matchLabels:
      app: redis
  volumeClaimTemplates:
    - metadata:
        name: redis-data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: gp3-standard
        resources:
          requests:
            storage: 50Gi
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain
    whenScaled: Delete
  template:
    metadata:
      labels:
        app: redis
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values: ["redis"]
              topologyKey: kubernetes.io/hostname
      tolerations:
        - key: "workload"
          operator: "Equal"
          value: "memory-optimized"
          effect: "NoSchedule"
      nodeSelector:
        node-group: memory-optimized
      containers:
        - name: redis
          image: redis:7.2-alpine
          ports:
            - containerPort: 6379
          command: ["redis-server", "/etc/redis/redis.conf"]
          resources:
            requests:
              cpu: "500m"
              memory: "2Gi"
            limits:
              cpu: "1"
              memory: "4Gi"
          volumeMounts:
            - name: redis-data
              mountPath: /data
            - name: redis-config
              mountPath: /etc/redis
          readinessProbe:
            exec:
              command: ["redis-cli", "ping"]
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            exec:
              command: ["redis-cli", "ping"]
            initialDelaySeconds: 30
            periodSeconds: 15
      volumes:
        - name: redis-config
          configMap:
            name: redis-config

When to Use an Operator Instead

Raw StatefulSets work for simple setups. For complex operational tasks (automated failover, backup scheduling, version upgrades, cluster rebalancing), use an operator:

  • 🐘 PostgreSQL: CloudNativePG or Zalando Postgres Operator
  • 📨 Kafka: Strimzi Operator
  • 🔍 Elasticsearch: ECK (Elastic Cloud on Kubernetes)
  • 🔴 Redis: Redis Operator by Spotahome or Redis Enterprise Operator

Operators encode operational knowledge (failover procedures, backup logic, scaling rules) into code. They handle the scenarios that would otherwise require 3 AM manual intervention.

✅ Key Takeaway

StatefulSets are powerful but unforgiving. Always use reclaimPolicy: Retain, always set pod anti-affinity, always have a backup strategy, and always monitor rolling updates. If your stateful workload needs automated failover or complex lifecycle management, skip raw StatefulSets and use an operator from day one. The operational overhead of managing StatefulSets manually at 3 AM isn't worth the simplicity.
