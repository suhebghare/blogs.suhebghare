Terraform at Scale: Lessons from 50+ AWS Accounts

I've managed Terraform across 50+ AWS accounts, 200+ state files, and teams of 30+ engineers. The patterns that work at 5 accounts break at 50. Here's what I've learned about structuring Terraform for real organizations.

Project Structure: Monorepo vs Polyrepo

Monorepo (What We Use)

  • All Terraform in one repo
  • Shared modules, consistent tooling
  • Easier cross-team code review
  • Single CI/CD pipeline
  • Gets slow at very large scale (1000+ resources)

Polyrepo

  • Separate repo per service/team
  • Independent deploy cycles
  • Harder to share modules
  • Module versioning via git tags
  • Better for autonomous teams

Directory Layout That Scales

terraform/
├── modules/                    # Reusable modules

One State File Per Component Per Environment

The #1 mistake I see: everything in one state file. When your single state has 500 resources, terraform plan takes 8 minutes and a failed apply can leave you in a broken state. Split by component: VPC has its own state, EKS has its own state, RDS has its own state. Each plan takes seconds.

State Management: The Foundation

# backend.tf — every component gets this
terraform {
  backend "s3" {
    bucket         = "mycompany-terraform-state"
    key            = "production/us-east-1/eks/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

# State locking with DynamoDB
resource "aws_dynamodb_table" "terraform_locks" {
  name         = "terraform-locks"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"

  attribute {
    name = "LockID"
    type = "S"
  }
}

Cross-State Data Sources

Components need to reference each other. The EKS cluster needs the VPC ID. Use terraform_remote_state or better — data sources.

# Option 1: Remote state (tightly coupled)
data "terraform_remote_state" "vpc" {
  backend = "s3"
  config = {
    bucket = "mycompany-terraform-state"
    key    = "production/us-east-1/vpc/terraform.tfstate"
    region = "us-east-1"
  }
}

resource "aws_eks_cluster" "main" {
  vpc_config {
    subnet_ids = data.terraform_remote_state.vpc.outputs.private_subnet_ids
  }
}

# Option 2: Data sources (loosely coupled — preferred)
data "aws_vpc" "main" {
  tags = { Name = "production-vpc" }
}

data "aws_subnets" "private" {
  filter {
    name   = "vpc-id"
    values = [data.aws_vpc.main.id]
  }
  tags = { Tier = "private" }
}
Prefer Data Sources Over Remote State

Remote state creates a hard dependency between state files. If someone refactors the VPC module and changes output names, your EKS plan breaks. Data sources query AWS directly — they're resilient to Terraform refactoring.

Module Design: Reusable vs Environment-Specific

# modules/eks-cluster/variables.tf — with validation
variable "cluster_name" {
  type        = string
  description = "Name of the EKS cluster"
  validation {
    condition     = can(regex("^[a-z][a-z0-9-]{2,39}$", var.cluster_name))
    error_message = "Cluster name must be lowercase alphanumeric, 3-40 chars."
  }
}

variable "cluster_version" {
  type        = string
  default     = "1.29"
  description = "Kubernetes version"
  validation {
    condition     = contains(["1.28", "1.29", "1.30"], var.cluster_version)
    error_message = "Supported versions: 1.28, 1.29, 1.30."
  }
}

variable "node_groups" {
  type = map(object({
    instance_types = list(string)
    min_size       = number
    max_size       = number
    desired_size   = number
    capacity_type  = optional(string, "ON_DEMAND")
    labels         = optional(map(string), {})
    taints = optional(list(object({
      key    = string
      value  = string
      effect = string
    })), [])
  }))
  description = "Map of node group configurations"
}

# modules/eks-cluster/main.tf
resource "aws_eks_cluster" "this" {
  name     = var.cluster_name
  version  = var.cluster_version
  role_arn = aws_iam_role.cluster.arn

  vpc_config {
    subnet_ids              = var.subnet_ids
    endpoint_private_access = true
    endpoint_public_access  = var.enable_public_access
    security_group_ids      = [aws_security_group.cluster.id]
  }

  encryption_config {
    provider { key_arn = var.kms_key_arn }
    resources = ["secrets"]
  }

  enabled_cluster_log_types = ["api", "audit", "authenticator"]
}

Module Versioning

# Pin module versions — never use main branch
module "eks" {
  source  = "git::https://github.com/mycompany/terraform-modules.git//eks-cluster?ref=v2.3.1"
  # Or from Terraform registry:
  # source  = "terraform-aws-modules/eks/aws"
  # version = "~> 20.0"

  cluster_name    = "production-eks"
  cluster_version = "1.29"
  subnet_ids      = data.aws_subnets.private.ids
}

CI/CD Pipeline: Plan on PR, Apply on Merge

PR Created
terraform fmt + validate
Plan + Cost Estimate
terraform plan + Infracost
Review
Plan output as PR comment
Merge to Main
terraform apply -auto-approve
Drift Detection
Scheduled plan (daily)
# .github/workflows/terraform.yml
name: Terraform
on:
  pull_request:
    paths: ['terraform/**']
  push:
    branches: [main]
    paths: ['terraform/**']

jobs:
  plan:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: 1.7.0

      - name: Terraform Init
        run: terraform init -backend-config=backend.hcl
        working-directory: terraform/environments/production/us-east-1/eks

      - name: Terraform Plan
        id: plan
        run: terraform plan -no-color -out=tfplan
        working-directory: terraform/environments/production/us-east-1/eks

      - name: Cost Estimation
        uses: infracost/actions/setup@v3
        with:
          api-key: ${{ secrets.INFRACOST_API_KEY }}

      - name: Comment PR
        uses: actions/github-script@v7
        with:
          script: |
            const plan = `${{ steps.plan.outputs.stdout }}`;
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `### Terraform Plan\n\`\`\`\n${plan}\n\`\`\``
            });

  apply:
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init && terraform apply -auto-approve
        working-directory: terraform/environments/production/us-east-1/eks

Drift Detection and Handling

Drift happens when someone makes a manual change in the AWS console. It's inevitable. The question is how fast you detect it.

Real Drift Incident

An engineer manually changed a security group rule in the console to debug a connectivity issue. Forgot to revert it. Two weeks later, terraform apply on an unrelated change reverted the security group — breaking production. We now run terraform plan daily in CI and alert on any drift.

# Daily drift detection (scheduled GitHub Action)
name: Drift Detection
on:
  schedule:
    - cron: '0 8 * * *'  # 8 AM UTC daily

jobs:
  detect-drift:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        component: [vpc, eks, rds, iam]
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - name: Check Drift
        id: plan
        run: |
          terraform init
          terraform plan -detailed-exitcode -no-color 2>&1 | tee plan.txt
          echo "exitcode=$?" >> $GITHUB_OUTPUT
        working-directory: terraform/environments/production/us-east-1/${{ matrix.component }}
        continue-on-error: true

      - name: Alert on Drift
        if: steps.plan.outputs.exitcode == '2'
        run: |
          curl -X POST "${{ secrets.SLACK_WEBHOOK }}" \
            -H 'Content-Type: application/json' \
            -d "{\"text\":\"⚠️ Terraform drift detected in ${{ matrix.component }}\"}"

Common Mistakes I've Seen

Everything in One State File

500+ resources, 8-minute plans, blast radius of the entire infrastructure. Split by component and environment. Each state should have 20-50 resources max.

No Module Versioning

Using source = "../modules/vpc" means any module change affects all environments simultaneously. Use git tags: ?ref=v1.2.0. Promote versions: dev → staging → production.

Manual Changes Bypassing Terraform

Console changes cause drift. Enforce with SCPs that deny console access to Terraform-managed resources, or at minimum run daily drift detection.

Hardcoded Values Instead of Variables

AMI IDs, account numbers, CIDR blocks hardcoded in main.tf. Use variables with validation, locals for computed values, and data sources for dynamic lookups.

No State Locking

Two engineers run terraform apply simultaneously. State corruption. Always use DynamoDB locking with S3 backend. It's one table for all state files.

Testing Modules with Terratest

// test/eks_test.go
package test

import (
    "testing"
    "github.com/gruntwork-io/terratest/modules/terraform"
    "github.com/stretchr/testify/assert"
)

func TestEksCluster(t *testing.T) {
    t.Parallel()
    opts := &terraform.Options{
        TerraformDir: "../modules/eks-cluster",
        Vars: map[string]interface{}{
            "cluster_name":    "test-cluster",
            "cluster_version": "1.29",
            "subnet_ids":      []string{"subnet-abc123"},
        },
    }
    defer terraform.Destroy(t, opts)
    terraform.InitAndApply(t, opts)

    clusterName := terraform.Output(t, opts, "cluster_name")
    assert.Equal(t, "test-cluster", clusterName)
}

Terraform Best Practices Summary

  • One state file per component per environment (20-50 resources each)
  • Version all modules with git tags — never reference main branch
  • Plan on PR with cost estimation, apply on merge
  • Daily drift detection with Slack/PagerDuty alerts
  • Use data sources over remote state for loose coupling
  • Variable validation to catch misconfigurations early
  • DynamoDB state locking — always, no exceptions
  • Test modules with Terratest before promoting to production
