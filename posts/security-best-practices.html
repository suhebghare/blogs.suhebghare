A Comprehensive Checklist from 8 Years of Cloud Security

After 8 years of building and securing cloud-native applications on AWS, I've distilled the most impactful security practices into a layered checklist. This isn't theoretical — every item here is something I've either implemented in production or learned the hard way after an incident.

The checklist is organized by layer, from identity (the most common attack vector) to detection and response (your safety net when prevention fails).

Layer 1: Identity — Who can access what?
Layer 2: Network — What can talk to what?
Layer 3: Data — Is everything encrypted?
Layer 4: Compute — Are workloads hardened?
Layer 5: Application — Is the code secure?
Layer 6: Detection — Can you see attacks?
Layer 7: Response — Can you react fast?

Layer 1: Identity & Access Management

Identity is the #1 attack vector in cloud environments. Over 60% of cloud breaches involve compromised credentials or excessive permissions.

Least Privilege IAM

  • ✅ No IAM users with long-lived access keys — use AWS SSO/Identity Center for human access
  • ✅ Service accounts use IRSA (IAM Roles for Service Accounts) in EKS
  • ✅ IAM policies scoped to specific resources, never Resource: "*" for write operations
  • ✅ Use IAM Access Analyzer to identify unused permissions
# Find unused IAM roles (no activity in 90 days)
aws iam generate-service-last-accessed-details \
  --arn "arn:aws:iam::123456789:role/my-role"

# Enable IAM Access Analyzer
aws accessanalyzer create-analyzer \
  --analyzer-name "account-analyzer" \
  --type ACCOUNT

No Long-Lived Credentials

# IRSA setup for EKS service accounts
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-app
  namespace: production
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/my-app-role
---
# Pod automatically gets temporary credentials via IRSA
# No access keys stored anywhere

MFA Everywhere

# IAM policy requiring MFA for all actions
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyAllExceptMFASetupWithoutMFA",
      "Effect": "Deny",
      "NotAction": [
        "iam:CreateVirtualMFADevice",
        "iam:EnableMFADevice",
        "iam:GetUser",
        "iam:ListMFADevices",
        "sts:GetSessionToken"
      ],
      "Resource": "*",
      "Condition": {
        "BoolIfExists": {
          "aws:MultiFactorAuthPresent": "false"
        }
      }
    }
  ]
}

Layer 2: Network Security

VPC Design

  • ✅ Separate VPCs for production, staging, and development
  • ✅ Private subnets for all workloads — no EC2 instances in public subnets
  • ✅ NAT Gateway for outbound internet access from private subnets
  • ✅ VPC endpoints for AWS services (S3, DynamoDB, ECR, STS, CloudWatch)

Security Groups: Principle of Least Access

resource "aws_security_group" "app" {
  name_prefix = "app-"
  vpc_id      = aws_vpc.main.id

  # Inbound: only from ALB on app port
  ingress {
    from_port       = 8080
    to_port         = 8080
    protocol        = "tcp"
    security_groups = [aws_security_group.alb.id]
    description     = "ALB to app"
  }

  # Outbound: only to database and AWS services
  egress {
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.rds.id]
    description     = "App to RDS"
  }

  egress {
    from_port       = 443
    to_port         = 443
    protocol        = "tcp"
    prefix_list_ids = [aws_vpc_endpoint.s3.prefix_list_id]
    description     = "App to S3 via VPC endpoint"
  }

  # NO open egress to 0.0.0.0/0
}

VPC Endpoints: Keep Traffic Off the Internet

resource "aws_vpc_endpoint" "s3" {
  vpc_id       = aws_vpc.main.id
  service_name = "com.amazonaws.us-east-1.s3"
  vpc_endpoint_type = "Gateway"
  route_table_ids   = [aws_route_table.private.id]
}

resource "aws_vpc_endpoint" "ecr_api" {
  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.us-east-1.ecr.api"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = aws_subnet.private[*].id
  security_group_ids  = [aws_security_group.vpc_endpoints.id]
  private_dns_enabled = true
}
💡 VPC Endpoints Save Money Too

VPC endpoints for S3 and DynamoDB are free (Gateway type). Interface endpoints cost $0.01/hour + data processing, but they eliminate NAT Gateway data processing charges ($0.045/GB). For ECR image pulls alone, this saved us $300/month.

Layer 3: Data Protection

Encryption at Rest

  • ✅ Account-level default EBS encryption enabled
  • ✅ S3 bucket default encryption with SSE-KMS
  • ✅ RDS encryption enabled (cannot be enabled after creation — plan ahead)
  • ✅ KMS key rotation enabled (automatic annual rotation)
# Enable account-level default EBS encryption
aws ec2 enable-ebs-encryption-by-default

# S3 bucket policy: deny unencrypted uploads
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnencryptedUploads",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::my-bucket/*",
      "Condition": {
        "StringNotEquals": {
          "s3:x-amz-server-side-encryption": "aws:kms"
        }
      }
    }
  ]
}

No Public S3 Buckets

# Account-level S3 Block Public Access
aws s3control put-public-access-block \
  --account-id 123456789 \
  --public-access-block-configuration \
    BlockPublicAcls=true,\
    IgnorePublicAcls=true,\
    BlockPublicPolicy=true,\
    RestrictPublicBuckets=true

Layer 4: Compute Security

IMDSv2 Only

IMDSv1 is the most exploited EC2 vulnerability. It allows SSRF attacks to steal instance credentials. Enforce IMDSv2 (requires a token):

# Enforce IMDSv2 on all new instances
aws ec2 modify-instance-metadata-defaults \
  --http-tokens required \
  --http-put-response-hop-limit 1

No SSH — Use SSM Session Manager

# SSM Session Manager — no SSH keys, no port 22, full audit trail
aws ssm start-session --target i-0123456789abcdef0

# All sessions logged to CloudWatch and S3 automatically

Container Security

# Kubernetes SecurityContext — non-root, read-only filesystem
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 1000
      containers:
        - name: app
          image: my-app:v1.2.3@sha256:abc123...
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - name: tmp
              mountPath: /tmp
      volumes:
        - name: tmp
          emptyDir: {}
🚨 Never Run Privileged Containers

A privileged container has full access to the host. If compromised, the attacker owns the node — and potentially the entire cluster. Use allowPrivilegeEscalation: false and capabilities.drop: ["ALL"] on every container. Enforce this with OPA Gatekeeper or Kyverno admission policies.

Layer 5: Application Security

Security Scanning in CI/CD

# GitHub Actions security scanning pipeline
name: Security Scan
on: [pull_request]
jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      # Secret detection
      - uses: gitleaks/gitleaks-action@v2

      # Container image scanning
      - name: Trivy scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: '${{ env.IMAGE }}'
          severity: 'CRITICAL,HIGH'
          exit-code: '1'

      # IaC scanning
      - name: Checkov
        uses: bridgecrewio/checkov-action@master
        with:
          directory: terraform/
          framework: terraform

      # Dependency scanning
      - name: Dependency check
        run: |
          npm audit --audit-level=high
          # Fail on high/critical vulnerabilities

Secrets Detection

# Pre-commit hook with gitleaks
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks

Layer 6: Detection

Enable Everything

Service What It Detects Monthly Cost (typical)
GuardDuty Compromised instances, credential exfiltration, crypto mining $30-100
Security Hub Aggregates findings, compliance scoring $10-30
CloudTrail All AWS API calls (who did what, when) $2-10 (S3 storage)
VPC Flow Logs Network traffic patterns, rejected connections $50-200 (depends on volume)
Config Resource configuration changes, compliance drift $20-50 
# Enable GuardDuty with all protection plans
aws guardduty create-detector \
  --enable \
  --finding-publishing-frequency FIFTEEN_MINUTES \
  --features '[
    {"Name": "S3_DATA_EVENTS", "Status": "ENABLED"},
    {"Name": "EKS_AUDIT_LOGS", "Status": "ENABLED"},

  ]'

Layer 7: Incident Response

Automated Isolation Runbook

When GuardDuty detects a compromised instance, a Lambda function automatically isolates it:

# Lambda auto-remediation for compromised EC2
import boto3

def handler(event, context):
    instance_id = event['detail']['resource']['instanceDetails']['instanceId']
    ec2 = boto3.client('ec2')

    # Create forensic security group (no ingress, no egress)
    sg = ec2.create_security_group(
        GroupName=f'forensic-isolation-{instance_id}',
        Description='Isolation SG for compromised instance',
        VpcId=vpc_id
    )

    # Replace all security groups with isolation SG
    ec2.modify_instance_attribute(
        InstanceId=instance_id,
        Groups=[sg['GroupId']]
    )

    # Create EBS snapshots for forensics
    volumes = ec2.describe_volumes(
        Filters=[{'Name': 'attachment.instance-id', 'Values': [instance_id]}]
    )
    for vol in volumes['Volumes']:
        ec2.create_snapshot(
            VolumeId=vol['VolumeId'],
            Description=f'Forensic snapshot - {instance_id}'
        )

    # Tag instance
    ec2.create_tags(
        Resources=[instance_id],
        Tags=[{'Key': 'SecurityStatus', 'Value': 'ISOLATED'}]
    )

    # Notify security team
    sns = boto3.client('sns')
    sns.publish(
        TopicArn='arn:aws:sns:us-east-1:123456789:security-incidents',
        Subject=f'Instance {instance_id} isolated - GuardDuty finding',
        Message=f'Instance automatically isolated. Review GuardDuty finding.'
    )

Incident Runbooks

Every team should have runbooks for these scenarios: compromised IAM credentials, compromised EC2 instance, exposed S3 bucket, DDoS attack, data exfiltration alert. Write them before you need them — you won't have time during an incident.

Security Posture Summary

Layer Key Actions Effort Impact
Identity SSO + MFA + IRSA + Access Analyzer Medium Critical
Network Private subnets + SGs + VPC endpoints Medium High
Data KMS encryption + no public buckets Low High
Compute IMDSv2 + SSM + non-root containers Low High
Application SAST/DAST + dependency scanning + secrets detection Medium High
Detection GuardDuty + Security Hub + CloudTrail Low Critical
Response Auto-isolation + runbooks + postmortems High Critical

Key Takeaways

  • Start with identity — it's the most common attack vector and the highest-impact fix
  • No long-lived credentials anywhere — use IRSA, SSO, and temporary tokens
  • Encrypt everything by default — enable account-level EBS encryption and S3 block public access
  • IMDSv2 is non-negotiable — IMDSv1 is the most exploited EC2 vulnerability
  • Scan in CI/CD, not after deployment — shift security left
  • Enable GuardDuty — it's cheap and catches things you'd never notice manually
  • Automate incident response — humans are too slow for initial containment
  • Write runbooks before incidents — you won't have time during one
