Why Build an Infrastructure Agent?

Imagine typing "Why is the checkout service slow?" and getting back: pod logs showing OOM kills, a Prometheus query showing memory at 98%, the last deploy that changed memory limits, and a suggested fix — all in 15 seconds. That's what an infrastructure AI agent does.

We built one using LangChain, GPT-4, and a set of tools that wrap kubectl, AWS CLI, and Prometheus. It took 2 weeks to build the v1, and it now handles ~40 diagnostic queries per day from our engineering team. Cost: about $0.12 per interaction.

Agent Architecture: ReAct Pattern

The agent uses the ReAct (Reason + Act) pattern: it thinks about what information it needs, calls a tool to get it, reasons about the result, and decides whether to call another tool or respond. This loop continues until it has enough information to answer.

User Query
LLM Reasons (what do I need?)
Calls Tool (kubectl, Prometheus, etc.)
LLM Analyzes Result
More info needed? → Loop back
Final Answer

Tool Definitions

Each tool is a Python function with a JSON schema that tells the LLM what it does, what parameters it accepts, and when to use it. Here are the 5 tools we run in production:

from langchain.tools import tool
from typing import Optional
import subprocess
import json
import requests

@tool
def get_pod_logs(namespace: str, pod_name: str, lines: int = 50) -> str:
    """Get recent logs from a Kubernetes pod.
    Use when investigating errors, crashes, or unexpected behavior.
    Args:
        namespace: Kubernetes namespace
        pod_name: Name of the pod (supports partial match)
        lines: Number of recent log lines (default 50)
    """
    # Find pod by partial name match
    result = subprocess.run(
        ['kubectl', 'get', 'pods', '-n', namespace,
         '-o', 'jsonpath={.items[*].metadata.name}'],
        capture_output=True, text=True
    )
    pods = result.stdout.split()
    matching = [p for p in pods if pod_name in p]
    if not matching:
        return f"No pods matching '{pod_name}' in namespace '{namespace}'"

    logs = subprocess.run(
        ['kubectl', 'logs', matching[0], '-n', namespace,
         '--tail', str(lines), '--timestamps'],
        capture_output=True, text=True
    )
    return logs.stdout or logs.stderr

@tool
def get_metrics(query: str, duration: str = "15m") -> str:
    """Query Prometheus for metrics.
    Use for checking CPU, memory, error rates, latency, request counts.
    Args:
        query: PromQL query string
        duration: Time range (e.g., '15m', '1h', '6h')
    """
    response = requests.get(
        f"{PROMETHEUS_URL}/api/v1/query",
        params={'query': query, 'time': '', 'timeout': '10s'}
    )
    data = response.json()
    if data['status'] != 'success':
        return f"Query failed: {data.get('error', 'unknown error')}"

    results = data['data']['result']
    if not results:
        return "No data returned for this query"

    formatted = []
    for r in results[:10]:  # Limit to 10 results
        labels = r['metric']
        value = r['value'][1]
        formatted.append(f"{labels}: {value}")
    return "\n".join(formatted)

@tool
def scale_deployment(namespace: str, deployment: str, replicas: int) -> str:
    """Scale a Kubernetes deployment. REQUIRES CONFIRMATION.
    Only use when explicitly asked to scale.
    Args:
        namespace: Kubernetes namespace
        deployment: Deployment name
        replicas: Target replica count (max 20)
    """
    if replicas > 20:
        return "ERROR: Cannot scale above 20 replicas via agent. Use kubectl directly."
    if replicas < 1:
        return "ERROR: Cannot scale to 0 via agent."

    result = subprocess.run(
        ['kubectl', 'scale', 'deployment', deployment,
         '-n', namespace, f'--replicas={replicas}'],
        capture_output=True, text=True
    )
    return result.stdout or result.stderr

@tool
def get_recent_alerts(namespace: Optional[str] = None, hours: int = 6) -> str:
    """Get recent firing alerts from AlertManager.
    Use to understand what's currently broken or degraded.
    Args:
        namespace: Filter by namespace (optional)
        hours: Look back period in hours (default 6)
    """
    response = requests.get(f"{ALERTMANAGER_URL}/api/v2/alerts")
    alerts = response.json()

    if namespace:
        alerts = [a for a in alerts if a['labels'].get('namespace') == namespace]

    formatted = []
    for a in alerts[:15]:
        formatted.append(
            f"[{a['labels'].get('severity', '?')}] {a['labels']['alertname']} "
            f"- {a['annotations'].get('description', 'No description')} "
            f"(namespace: {a['labels'].get('namespace', '?')})"
        )
    return "\n".join(formatted) or "No active alerts"

@tool
def run_kubectl(command: str) -> str:
    """Run a read-only kubectl command.
    ONLY supports: get, describe, top, logs.
    Use for checking pod status, resource usage, events.
    Args:
        command: kubectl command WITHOUT the 'kubectl' prefix
    """
    allowed_verbs = ['get', 'describe', 'top', 'logs']
    parts = command.strip().split()
    if not parts or parts[0] not in allowed_verbs:
        return f"ERROR: Only {allowed_verbs} commands allowed. Got: {parts[0] if parts else 'empty'}"

    result = subprocess.run(
        ['kubectl'] + parts,
        capture_output=True, text=True, timeout=30
    )
    return result.stdout or result.stderr

The Agent Implementation

from langchain.agents import AgentExecutor, create_openai_tools_agent
from langchain_openai import ChatOpenAI
from langchain.prompts import ChatPromptTemplate, MessagesPlaceholder

SYSTEM_PROMPT = """You are an infrastructure diagnostic agent for a Kubernetes-based
platform running on AWS EKS. You have access to tools for querying pods, metrics,
alerts, and logs.

Rules:
1. Always check pod status and recent alerts FIRST before diving into logs.
2. For performance issues, check metrics (CPU, memory, latency) before logs.
3. NEVER run destructive commands. You can only read, not modify.
4. The scale_deployment tool requires explicit user confirmation before use.
5. If you're unsure, say so. Don't guess at root causes without evidence.
6. Always cite the specific data that supports your conclusion.
7. Keep responses concise — engineers want answers, not essays.

Common PromQL queries:
- CPU: rate(container_cpu_usage_seconds_total{{namespace="{ns}"}}[5m])
- Memory: container_memory_usage_bytes{{namespace="{ns}"}}
- Error rate: rate(http_requests_total{{status=~"5..",namespace="{ns}"}}[5m])
- Latency p99: histogram_quantile(0.99, rate(http_request_duration_seconds_bucket{{namespace="{ns}"}}[5m]))
"""

llm = ChatOpenAI(model="gpt-4", temperature=0)
tools = [get_pod_logs, get_metrics, scale_deployment, get_recent_alerts, run_kubectl]

prompt = ChatPromptTemplate.from_messages([
    ("system", SYSTEM_PROMPT),
    MessagesPlaceholder("chat_history", optional=True),
    ("human", "{input}"),
    MessagesPlaceholder("agent_scratchpad"),
])

agent = create_openai_tools_agent(llm, tools, prompt)
executor = AgentExecutor(
    agent=agent,
    tools=tools,
    verbose=True,
    max_iterations=8,       # Prevent infinite loops
    max_execution_time=60,  # 60 second timeout
    handle_parsing_errors=True
)

Real Example: Diagnosing a CrashLoopBackOff

Here's an actual agent session (condensed):

🧑 User: "The payment service pods keep crashing in production"

Agent Thought: I need to check pod status in the payment namespace first.

Tool Call: run_kubectl("get pods -n payments -o wide")

Result: payment-api-7d4f8b-x2k9q — CrashLoopBackOff (3 restarts), payment-api-7d4f8b-m8n3p — Running

Agent Thought: One pod is crash-looping. Let me check its logs.

Tool Call: get_pod_logs("payments", "payment-api-7d4f8b-x2k9q", 30)

Result: java.lang.OutOfMemoryError: Java heap space at line 23

Agent Thought: OOM error. Let me check the memory metrics and limits.

Tool Call: get_metrics("container_memory_usage_bytes{namespace='payments',container='payment-api'}")

Result: 524288000 bytes (500Mi) — matches the 512Mi limit

Final Answer: The payment-api pod x2k9q is in CrashLoopBackOff due to OOM. Memory usage hit the 512Mi limit. The JVM heap is exhausting available memory. Immediate fix: increase memory limit to 768Mi. Root cause: investigate recent code changes that increased memory footprint — check if a new dependency or data structure was added.

Total time: 14 seconds. A human doing this manually: 5-10 minutes of kubectl commands and Grafana dashboard navigation.

Safety Guardrails

Critical: Read-Only by Default

The agent starts with zero write permissions. Every tool that modifies state (scale_deployment) requires explicit user confirmation and has hard limits (max 20 replicas, no scale-to-zero). We added write tools one at a time over 3 months, only after the read-only tools proved reliable.

  • kubectl whitelist — only get, describe, top, logs verbs allowed
  • Replica limits — scale_deployment caps at 20 replicas, minimum 1
  • Timeout — 60-second max execution time prevents runaway tool loops
  • Iteration limit — max 8 tool calls per query prevents infinite reasoning loops
  • Full audit log — every tool call, input, and output is logged to CloudWatch
  • No secrets access — the agent's kubeconfig has a custom RBAC role that excludes Secrets and ConfigMaps
# RBAC role for the agent (read-only, no secrets)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: ai-agent-readonly
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log", "services", "events", "nodes"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets", "statefulsets"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["autoscaling"]
    resources: ["horizontalpodautoscalers"]
    verbs: ["get", "list", "watch"]
  # Explicitly NO access to secrets, configmaps with sensitive data

Lessons Learned

✅ What Worked

  • Start with read-only tools. We ran for 6 weeks with only diagnostic tools before adding any write capability.
  • Specific PromQL examples in the system prompt dramatically improved the agent's ability to write correct queries.
  • Limiting to 8 iterations prevents the agent from going down rabbit holes. If it can't answer in 8 tool calls, a human should take over.
  • Logging every tool call lets us audit what the agent did and improve the system prompt based on real failures.

❌ What Didn't Work

  • Giving the agent too many tools at once. With 12 tools, it got confused about which to use. 5 focused tools work better than 12 broad ones.
  • Using GPT-3.5. It couldn't write correct PromQL queries or parse kubectl output reliably. GPT-4 is worth the cost difference.
  • Letting the agent run kubectl with arbitrary arguments. It tried kubectl delete pod once during testing. The verb whitelist was added that day.

An infrastructure agent isn't about replacing engineers. It's about giving every engineer on your team the diagnostic speed of your best SRE. Start with 3 read-only tools, prove value, then expand carefully.
