PCI-DSS Compliant Architecture Without Touching Card Data

The single most important decision in e-commerce security architecture is this: never touch card data. If cardholder data never enters your environment, your PCI-DSS scope shrinks from 300+ controls to roughly 22. That's the difference between a 6-month compliance project and a 3-week one.

Over the past 4 years, I've built and maintained PCI-compliant architectures for three e-commerce platforms on AWS. Here's the architecture pattern we use, the specific AWS services that make it work, and the compliance automation that keeps auditors happy.

Scope Reduction: Tokenization Strategy

The architecture's foundation is tokenization via Stripe.js (or Braintree, Adyen — any PCI Level 1 provider). Card data flows directly from the customer's browser to Stripe's servers. Your backend only ever sees a token.

1. Customer enters card → Stripe.js (client-side) → Stripe API
2. Stripe returns a payment token (tok_xxx) to the browser
3. Browser sends token to YOUR backend API
4. Your backend calls Stripe API with the token to charge
5. Card data NEVER touches your servers
💡 Why This Matters

With tokenization, you qualify for SAQ-A (Self-Assessment Questionnaire A) — the simplest PCI compliance level. Without it, you need SAQ-D, which has 300+ requirements including quarterly network scans, annual penetration tests, and a Qualified Security Assessor (QSA) audit costing $50K-$200K.

Network Segmentation Architecture

Even with tokenization, the payment processing service needs isolation. A compromised product catalog service should never be able to reach the payment service's database or Stripe API credentials.

Payment Subnet Security Group

resource "aws_security_group" "payment_service" {
  name_prefix = "payment-svc-"
  vpc_id      = aws_vpc.main.id

  # Inbound: only from order service on port 8443
  ingress {
    from_port       = 8443
    to_port         = 8443
    protocol        = "tcp"
    security_groups = [aws_security_group.order_service.id]
  }

  # Outbound: only to Stripe API (HTTPS)
  egress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["13.110.0.0/14"]  # Stripe IP ranges
    description = "Stripe API only"
  }

  # Outbound: to payment database
  egress {
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.payment_db.id]
  }

  # NO general internet access
  # NO access to other services
}

IAM: Least Privilege Per Microservice

Every microservice gets its own IAM role via IRSA (IAM Roles for Service Accounts). The payment service has the most restricted permissions — it can only access its own KMS key, its own database credentials in Secrets Manager, and nothing else.

resource "aws_iam_role" "payment_service" {
  name = "payment-service-role"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Principal = {
        Federated = aws_iam_openid_connect_provider.eks.arn
      }
      Action = "sts:AssumeRoleWithWebIdentity"
      Condition = {
        StringEquals = {
          "${aws_iam_openid_connect_provider.eks.url}:sub" = "system:serviceaccount:production:payment-service"
          "${aws_iam_openid_connect_provider.eks.url}:aud" = "sts.amazonaws.com"
        }
      }
    }]
  })
}

resource "aws_iam_role_policy" "payment_service" {
  name = "payment-service-policy"
  role = aws_iam_role.payment_service.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect   = "Allow"
        Action   = ["kms:Decrypt", "kms:GenerateDataKey"]
        Resource = [aws_kms_key.payment.arn]
      },
      {
        Effect   = "Allow"
        Action   = ["secretsmanager:GetSecretValue"]
        Resource = ["arn:aws:secretsmanager:us-east-1:*:secret:payment/*"]
      }
    ]
  })
}

Encryption Strategy

RDS (at rest) AES-256 via KMS Separate KMS key per environment
S3 (at rest) SSE-KMS Bucket-level default encryption
EBS volumes AES-256 via KMS Account-level default encryption
In transit TLS 1.2+ everywhere ACM certificates, auto-renewed
Application secrets Secrets Manager Automatic rotation every 30 days 
# KMS key per environment — payment service gets its own
resource "aws_kms_key" "payment" {
  description             = "Payment service encryption key"
  deletion_window_in_days = 30
  enable_key_rotation     = true

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid    = "AllowPaymentServiceOnly"
        Effect = "Allow"
        Principal = {
          AWS = aws_iam_role.payment_service.arn
        }
        Action   = ["kms:Decrypt", "kms:GenerateDataKey"]
        Resource = "*"
      },
      {
        Sid    = "AllowKeyAdministration"
        Effect = "Allow"
        Principal = {
          AWS = "arn:aws:iam::123456789:role/SecurityAdmin"
        }
        Action   = "kms:*"
        Resource = "*"
      }
    ]
  })
}

Audit Logging: Immutable Trail

For PCI compliance, you need an immutable audit trail. We use CloudTrail for AWS API calls and application-level audit logs stored in S3 with Object Lock.

resource "aws_s3_bucket" "audit_logs" {
  bucket = "ecommerce-audit-logs-prod"
}

resource "aws_s3_bucket_object_lock_configuration" "audit_logs" {
  bucket = aws_s3_bucket.audit_logs.id
  rule {
    default_retention {
      mode = "COMPLIANCE"
      years = 7  # PCI requires minimum 1 year, we keep 7
    }
  }
}

resource "aws_s3_bucket_versioning" "audit_logs" {
  bucket = aws_s3_bucket.audit_logs.id
  versioning_configuration {
    status = "Enabled"
  }
}
🚨 Object Lock in COMPLIANCE Mode

COMPLIANCE mode means nobody — not even the root account — can delete or modify objects before the retention period expires. Use GOVERNANCE mode if you need the ability to override in emergencies. We use COMPLIANCE for audit logs because PCI auditors specifically ask if logs can be tampered with.

DDoS Protection: WAF + Shield

E-commerce sites are prime DDoS targets, especially during sales events. We layer CloudFront + WAF + Shield Advanced:

  • CloudFront: Absorbs volumetric attacks at the edge (AWS's network handles up to multi-Tbps)
  • WAF: Rate limiting, bot control, and custom rules (see our WAF article for details)
  • Shield Advanced: $3,000/month but includes DDoS response team (DRT), cost protection (AWS credits for scaling during attacks), and advanced detection

Compliance Automation: AWS Config Rules

Manual compliance checks don't scale. We use AWS Config rules mapped to PCI-DSS controls for continuous monitoring:

# Enable PCI-DSS conformance pack
aws configservice put-conformance-pack \
  --conformance-pack-name "PCI-DSS-Operational" \
  --template-s3-uri "s3://aws-config-rules/pci-dss-pack.yaml" \
  --delivery-s3-bucket "config-results-bucket"

Incident Response for Card Data Breach

Even with tokenization, you need a breach response plan. PCI-DSS Requirement 12.10 mandates it. Our plan includes:

  1. Immediate containment: Isolate the payment subnet (modify security groups to deny all traffic)
  2. Forensic preservation: Snapshot all EBS volumes, export CloudTrail and VPC Flow Logs
  3. Notification: Payment processor (Stripe) within 24 hours, card brands within 72 hours, affected customers per local law
  4. Investigation: Engage PCI Forensic Investigator (PFI) — required by card brands for confirmed breaches
  5. Remediation: Rotate all credentials, patch vulnerability, re-assess PCI scope

Penetration testing schedule: PCI-DSS requires annual penetration testing (Requirement 11.3) and quarterly vulnerability scans by an Approved Scanning Vendor (ASV). We run pen tests quarterly and ASV scans monthly — exceeding the minimum keeps auditors happy and catches issues early.

Key Takeaways

  • Never touch card data — use Stripe.js/tokenization to qualify for SAQ-A
  • Isolate the payment service in its own subnet with no internet access except the payment processor
  • Separate IAM role per microservice — the payment service should only access its own resources
  • Encrypt everything — separate KMS keys per environment and per sensitive service
  • Immutable audit logs with S3 Object Lock in COMPLIANCE mode
  • Automate compliance checks with AWS Config conformance packs
  • Have a breach response plan — PCI requires it, and you'll be glad you have it
