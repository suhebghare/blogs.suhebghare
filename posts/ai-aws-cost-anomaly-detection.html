The $50K Wake-Up Call We Almost Missed

Last year, a Lambda function with an infinite retry loop ran for 3 days before anyone noticed. The bill: $47,000 in a single month for a service that normally costs $200. The worst part? We had CloudWatch alarms — they just weren't tuned for cost anomalies. We had alerts for errors and latency, but nobody was watching the spend in real-time.

After that incident, we built a two-layer anomaly detection system: AWS Cost Anomaly Detection (built-in ML) for broad coverage, and a custom Python + Prophet pipeline for service-level forecasting. Six months later, we caught a similar issue — this time in 2 hours instead of 3 days. Estimated savings: $48,000.

Layer 1: AWS Cost Anomaly Detection

Start here. It's free, takes 10 minutes to set up, and catches ~70% of cost anomalies with zero configuration. AWS uses ML models trained on your historical spending patterns.

Setup via AWS CLI

# Create a cost monitor for the entire account
aws ce create-anomaly-monitor \
  --anomaly-monitor '{
    "MonitorName": "account-wide-monitor",
    "MonitorType": "DIMENSIONAL",
    "MonitorDimension": "SERVICE"
  }'

# Create a subscription for alerts
aws ce create-anomaly-subscription \
  --anomaly-subscription '{
    "SubscriptionName": "cost-anomaly-alerts",
    "MonitorArnList": ["arn:aws:ce::123456789012:anomalymonitor/monitor-id"],
    "Subscribers": [
      {
        "Address": "sre-team@company.com",
        "Type": "EMAIL"
      },
      {
        "Address": "arn:aws:sns:us-east-1:123456789012:cost-alerts",
        "Type": "SNS"
      }
    ],
    "Threshold": 100,
    "Frequency": "IMMEDIATE"
  }'
Set the threshold low

We started with a $500 threshold and missed a $300/day anomaly that ran for a week. Now we use $100 for immediate alerts and $50 for daily digest. The noise is minimal — maybe 1-2 false positives per month.

Service-Specific Monitors

Account-wide monitoring catches big spikes, but service-level monitors catch the subtle ones. We create separate monitors for our top 5 cost drivers:

# Monitor specifically for Lambda cost anomalies
aws ce create-anomaly-monitor \
  --anomaly-monitor '{
    "MonitorName": "lambda-cost-monitor",
    "MonitorType": "CUSTOM",
    "MonitorSpecification": {
      "And": null,
      "Or": null,
      "Not": null,
      "Dimensions": {
        "Key": "SERVICE",
        "Values": ["AWS Lambda"],
        "MatchOptions": ["EQUALS"]
      }
    }
  }'

Layer 2: Custom Anomaly Detection with Prophet

AWS Cost Anomaly Detection is great for catching obvious spikes, but it has blind spots: gradual cost creep, anomalies within expected seasonal patterns, and per-tag attribution. For these, we built a custom pipeline.

Architecture

Cost Explorer API (daily pull)
S3 (historical data)
Lambda (Prophet forecast)
SNS → Slack + PagerDuty

Pulling Cost Data Programmatically

import boto3
from datetime import datetime, timedelta

ce = boto3.client('ce')

def get_daily_costs(days=90):
    end = datetime.utcnow().strftime('%Y-%m-%d')
    start = (datetime.utcnow() - timedelta(days=days)).strftime('%Y-%m-%d')

    response = ce.get_cost_and_usage(
        TimePeriod={'Start': start, 'End': end},
        Granularity='DAILY',
        Metrics=['UnblendedCost'],
        GroupBy=[
            {'Type': 'DIMENSION', 'Key': 'SERVICE'},
            {'Type': 'TAG', 'Key': 'team'}
        ]
    )

    costs = []
    for result in response['ResultsByTime']:
        date = result['TimePeriod']['Start']
        for group in result['Groups']:
            service = group['Keys'][0]
            team = group['Keys'][1] if len(group['Keys']) > 1 else 'untagged'
            amount = float(group['Metrics']['UnblendedCost']['Amount'])
            costs.append({
                'date': date,
                'service': service,
                'team': team,
                'cost': amount
            })
    return costs

Prophet Forecasting

Facebook Prophet is ideal for cost forecasting because it handles seasonality (weekday/weekend patterns, monthly cycles) automatically:

from prophet import Prophet
import pandas as pd

def detect_anomalies(cost_data, service_name):
    df = pd.DataFrame(cost_data)
    df = df[df['service'] == service_name]
    df = df.rename(columns={'date': 'ds', 'cost': 'y'})
    df['ds'] = pd.to_datetime(df['ds'])

    model = Prophet(
        changepoint_prior_scale=0.05,
        seasonality_prior_scale=10,
        interval_width=0.95  # 95% confidence interval
    )
    model.add_seasonality(name='weekly', period=7, fourier_order=3)
    model.fit(df[:-1])  # Train on all but last day

    forecast = model.predict(df[['ds']])
    latest = forecast.iloc[-1]
    actual = df.iloc[-1]['y']

    is_anomaly = actual > latest['yhat_upper']
    deviation_pct = ((actual - latest['yhat']) / latest['yhat']) * 100

    return {
        'service': service_name,
        'actual': round(actual, 2),
        'expected': round(latest['yhat'], 2),
        'upper_bound': round(latest['yhat_upper'], 2),
        'is_anomaly': is_anomaly,
        'deviation_pct': round(deviation_pct, 1)
    }

Alert Thresholds: Absolute vs Percentage

This is where most teams get it wrong. You need both types of thresholds:

Threshold Type Value Catches Misses
Absolute only ($500/day) $500 Big spikes on any service A $50/day service jumping to $200/day (300% increase)
Percentage only (20%) 20% Proportional spikes on any service Normal variance on high-spend services triggers false positives
Both (recommended) $500 OR 20% Both big absolute and proportional spikes Very gradual creep (<20% over weeks) 
def should_alert(anomaly_result):
    ABSOLUTE_THRESHOLD = 500  # dollars
    PERCENTAGE_THRESHOLD = 20  # percent

    excess = anomaly_result['actual'] - anomaly_result['expected']

    if excess > ABSOLUTE_THRESHOLD:
        return True, f"${excess:.0f} over expected (absolute threshold)"
    if anomaly_result['deviation_pct'] > PERCENTAGE_THRESHOLD:
        return True, f"{anomaly_result['deviation_pct']}% over expected"
    return False, None

Real Example: The Infinite Retry Loop

Day 0, 14:23 — Deploy goes out

A new version of the order-processor Lambda deploys. A bug in error handling causes failed SQS messages to be retried infinitely instead of going to the DLQ.

Day 0, 16:00 — Prophet detects anomaly

Our custom pipeline runs every 2 hours. Lambda cost for the day is already $180 vs expected $45. Alert fires: "300% over expected, $135 excess."

Day 0, 16:15 — Root cause identified

SRE checks Lambda invocation metrics. order-processor showing 50x normal invocation count. SQS redrive policy was overridden in the deploy.

Day 0, 16:30 — Fix deployed

Rollback + DLQ fix. Total excess cost: ~$200. Without detection, this would have been $1,600/day × 30 days = $48,000.

Tagging Strategy for Anomaly Attribution

Anomaly detection is useless if you can't attribute the cost to a team or service. Tag everything first:

⚠️ Required Tags (enforce via AWS Organizations SCP)

  • team — owning team (e.g., checkout, platform)
  • environment — prod, staging, dev
  • service — application name
  • cost-center — for finance attribution
# SCP to deny resource creation without required tags
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RequireTags",
      "Effect": "Deny",
      "Action": [
        "ec2:RunInstances",
        "lambda:CreateFunction",
        "rds:CreateDBInstance",
        "ecs:CreateService"
      ],
      "Resource": "*",
      "Condition": {
        "Null": {
          "aws:RequestTag/team": "true",
          "aws:RequestTag/environment": "true"
        }
      }
    }
  ]
}

Lessons Learned

✅ What Works

  • Start with AWS Cost Anomaly Detection — it's free and catches 70% of issues
  • Set both absolute AND percentage thresholds — neither alone is sufficient
  • Tag everything before building detection — untagged resources are invisible to attribution
  • Run detection every 2 hours, not daily — a runaway Lambda can burn $1,600 in 24 hours
  • Alert to Slack AND PagerDuty — Slack for awareness, PagerDuty for action on big spikes

❌ Common Mistakes

  • Only checking monthly bills — by then, the damage is done
  • Setting thresholds too high — a $1,000 threshold misses the $300/day leak that costs $9,000/month
  • Ignoring dev/staging accounts — we've seen $5,000/month in forgotten staging resources
  • No automation on detection — alerting without auto-remediation (like stopping idle resources) leaves money on the table

The best time to set up cost anomaly detection was before your last surprise bill. The second best time is today. Start with the free AWS tool, add custom detection for your top 5 cost drivers, and tag everything.
