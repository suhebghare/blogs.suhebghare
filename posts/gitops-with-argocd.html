GitOps with ArgoCD: From Zero to Production-Grade

📅 December 20, 2024 ⏱ 17 min read 👁 1050 reads
👁️1050reads
👍431likes
👎25dislikes

We run ArgoCD across 3 Kubernetes clusters managing 50+ applications. It took us about 6 months to go from "ArgoCD is installed" to "ArgoCD is production-grade." This post covers everything I wish someone had told me at the start — the patterns that work, the ones that don't, and the operational gotchas that only show up at scale.

GitOps Principles (The Non-Negotiables)

GitOps isn't just "store YAML in Git." It's a set of principles that, when followed strictly, give you auditable, reproducible, and recoverable infrastructure:

  • Git is the single source of truth. The desired state of every environment lives in Git. If it's not in Git, it doesn't exist.
  • All changes go through Git. No kubectl apply from laptops. No manual changes in the console. Every change is a commit with an author and a review.
  • The system converges automatically. An agent (ArgoCD) continuously compares Git state to cluster state and reconciles drift.
  • Drift is detected and corrected. If someone manually changes a resource, ArgoCD detects it and reverts it to match Git.
The Hard Truth About GitOps

GitOps adds friction to emergency changes. When production is on fire and you need to change something NOW, going through a PR feels slow. You need a well-defined hotfix process (covered below) or your team will bypass GitOps under pressure, and once they start bypassing it, the whole model breaks down.

ArgoCD Architecture

ArgoCD runs inside your Kubernetes cluster and consists of three main components:

API Server
Exposes the gRPC/REST API and the web UI. Handles authentication, RBAC, and serves as the entry point for all operations.
Repo Server
Clones Git repos, renders Helm charts and Kustomize overlays, and generates the Kubernetes manifests that represent desired state.
Application Controller
The reconciliation loop. Compares desired state (from repo server) to live state (from Kubernetes API) and syncs when they diverge.
Redis
Caching layer for the repo server. Stores rendered manifests to avoid re-cloning and re-rendering on every reconciliation cycle (default: 3 minutes).

Repository Structure

Separate your application code from your deployment manifests. This is critical. Your CI pipeline builds and pushes images. Your GitOps repo defines what runs where.

# App repo (CI pipeline)
app-repo/
├── src/
├── Dockerfile
└── .github/workflows/ci.yml    # Build → Test → Push image to ECR

# GitOps repo (ArgoCD watches this)
gitops-repo/
├── apps/                        # ArgoCD Application definitions
│   ├── api-server.yaml
│   ├── web-frontend.yaml
│   └── background-worker.yaml
├── base/                        # Shared Kubernetes manifests
│   ├── api-server/
│   │   ├── deployment.yaml
│   │   ├── service.yaml
│   │   ├── hpa.yaml
│   │   └── kustomization.yaml
│   └── web-frontend/
│       └── ...
└── overlays/                    # Environment-specific overrides
    ├── dev/
    │   ├── api-server/
    │   │   ├── kustomization.yaml
    │   │   └── replicas-patch.yaml
    │   └── ...
    ├── staging/
    └── production/

App-of-Apps Pattern

Managing 50+ ArgoCD Application resources individually is painful. The app-of-apps pattern uses a single "root" Application that manages all other Applications. You add a new service by adding one YAML file.

# apps/root-app.yaml — The parent Application
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: git@github.com:myorg/gitops-repo.git
    targetRevision: main
    path: apps
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
# apps/api-server.yaml — A child Application
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-server
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: production
  source:
    repoURL: git@github.com:myorg/gitops-repo.git
    targetRevision: main
    path: overlays/production/api-server
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
    retry:
      limit: 3
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m

Now when you want to deploy a new service, you add a YAML file to the apps/ directory. The root app detects it and creates the ArgoCD Application, which then deploys the service. Deletion works the same way — remove the file, and the finalizer cleans up the resources.

ApplicationSet for Multi-Environment

ApplicationSets are the evolution of app-of-apps. Instead of writing one Application YAML per service per environment, you write a template that generates them:

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: all-services
  namespace: argocd
spec:
  generators:
  - matrix:
      generators:
      # All environments
      - list:
          elements:
          - env: dev
            cluster: https://dev-cluster.example.com
          - env: staging
            cluster: https://staging-cluster.example.com
          - env: production
            cluster: https://prod-cluster.example.com
      # All services (auto-discovered from directories)
      - git:
          repoURL: git@github.com:myorg/gitops-repo.git
          revision: main
          directories:
          - path: overlays/*/  # Matches all service dirs
  template:
    metadata:
      name: '{{path.basename}}-{{env}}'
      namespace: argocd
    spec:
      project: '{{env}}'
      source:
        repoURL: git@github.com:myorg/gitops-repo.git
        targetRevision: main
        path: 'overlays/{{env}}/{{path.basename}}'
      destination:
        server: '{{cluster}}'
        namespace: '{{env}}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true

This single ApplicationSet generates an Application for every combination of service × environment. Add a new service directory, and it's automatically deployed to all environments. Add a new environment, and all services are deployed there.

Secrets Management

The biggest challenge in GitOps: you can't store secrets in Git. Here are the two approaches that work in production.

Option 1: Sealed Secrets

Bitnami Sealed Secrets encrypts secrets with a cluster-specific key. The encrypted version is safe to store in Git. Only the controller running in the cluster can decrypt them.

# Encrypt a secret
kubeseal --format yaml --cert pub-cert.pem \
  < secret.yaml > sealed-secret.yaml

# sealed-secret.yaml (safe to commit)
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: api-credentials
  namespace: production
spec:
  encryptedData:
    DB_PASSWORD: AgBy3i4OJSWK+PiTySYZZA9rO...
    API_KEY: AgCtr8QLGHO2tkc+PiTySYZZA9rO...

Sealed Secrets Gotcha: Secrets are encrypted per-cluster and per-namespace. If you move a SealedSecret to a different namespace, it won't decrypt. If you rebuild the cluster without backing up the sealing key, all your secrets are lost. Back up the sealing key to a secure location outside the cluster.

Option 2: External Secrets Operator (Recommended)

External Secrets Operator (ESO) syncs secrets from external stores (AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager) into Kubernetes Secrets. The Git repo only contains a reference to the secret, not the secret itself.

# ClusterSecretStore — connects to AWS Secrets Manager
apiVersion: external-secrets.io/v1beta1
kind: ClusterSecretStore
metadata:
  name: aws-secrets-manager
spec:
  provider:
    aws:
      service: SecretsManager
      region: us-east-1
      auth:
        jwt:
          serviceAccountRef:
            name: external-secrets-sa
            namespace: external-secrets
---
# ExternalSecret — syncs a specific secret
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: api-credentials
  namespace: production
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore
  target:
    name: api-credentials
    creationPolicy: Owner
  data:
  - secretKey: DB_PASSWORD
    remoteRef:
      key: production/api-server
      property: db_password
  - secretKey: API_KEY
    remoteRef:
      key: production/api-server
      property: api_key

I recommend ESO over Sealed Secrets for production. It integrates with your existing secrets management infrastructure, supports rotation, and doesn't have the cluster-specific encryption problem.

Sync Waves and Hooks

When deploying a service that depends on a database migration or a ConfigMap, order matters. Sync waves let you control the order of resource creation:

# Wave -1: Namespace and RBAC (created first)
apiVersion: v1
kind: Namespace
metadata:
  name: production
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
---
# Wave 0: ConfigMaps and Secrets
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-config
  annotations:
    argocd.argoproj.io/sync-wave: "0"
---
# Wave 1: Database migration job
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
  annotations:
    argocd.argoproj.io/sync-wave: "1"
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation
spec:
  template:
    spec:
      containers:
      - name: migrate
        image: api-server:v2.3.1
        command: ["./migrate", "--direction", "up"]
      restartPolicy: Never
---
# Wave 2: Deployment (created after migration completes)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
  annotations:
    argocd.argoproj.io/sync-wave: "2"

The PreSync hook runs the migration job before the main sync. ArgoCD waits for the job to complete successfully before proceeding to wave 2. If the migration fails, the deployment doesn't happen.

Drift Detection and Auto-Sync Policy

ArgoCD checks for drift every 3 minutes by default. When it detects drift, the behavior depends on your sync policy:

PolicyBehaviorUse When
Manual sync ArgoCD shows "OutOfSync" but takes no action Production environments where you want human approval
automated: {} Auto-syncs when Git changes, but doesn't revert manual changes Staging environments
automated: { selfHeal: true } Reverts any manual changes to match Git Environments where drift is never acceptable
automated: { prune: true } Deletes resources that exist in cluster but not in Git Clean environments where orphaned resources are a problem
selfHeal + prune: The Nuclear Option

Enabling both selfHeal and prune means ArgoCD will delete any resource in the namespace that isn't defined in Git. This is powerful but dangerous. If someone accidentally removes a manifest from Git, ArgoCD will delete the live resource. Always use resources-finalizer.argocd.argoproj.io and test in staging first.

RBAC for ArgoCD

ArgoCD has its own RBAC system separate from Kubernetes RBAC. Define who can sync what:

# argocd-rbac-cm ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: argocd
data:
  policy.default: role:readonly
  policy.csv: |
    # Developers can sync dev and staging apps
    p, role:developer, applications, sync, dev/*, allow
    p, role:developer, applications, sync, staging/*, allow
    p, role:developer, applications, get, */*, allow

    # SRE team can sync everything including production
    p, role:sre, applications, *, */*, allow
    p, role:sre, clusters, get, *, allow
    p, role:sre, repositories, *, *, allow

    # Map SSO groups to roles
    g, myorg:developers, role:developer
    g, myorg:sre-team, role:sre

Our Production Setup: 3 Clusters, 50+ Apps

Here's how we structure ArgoCD for a real multi-cluster production environment:

Cluster Layout

Management Cluster: Runs ArgoCD, Prometheus, Grafana, and other platform tools. ArgoCD manages all three clusters from here.

Staging Cluster: Mirror of production. Auto-sync enabled with selfHeal. Developers can sync freely.

Production Cluster: Manual sync only. Requires SRE approval. No auto-prune (safety net).

Deployment Flow

Developer merges PR to app repo
CI builds image, pushes to ECR with git SHA tag
CI updates image tag in gitops-repo (staging overlay)
ArgoCD auto-syncs to staging cluster
Automated tests run against staging
Developer creates PR to promote image tag to production overlay
SRE reviews and approves PR
ArgoCD detects change, shows OutOfSync
SRE clicks Sync in ArgoCD UI (or merges triggers auto-sync)
Production deployment complete

Handling Hotfixes in a GitOps World

This is the question every team asks: "What do we do when production is on fire and we need to deploy a fix NOW?" Here's our process:

  1. Developer pushes hotfix to a branch in the app repo
  2. CI builds the image with a hotfix- prefix tag
  3. Developer creates a PR directly to the production overlay in the gitops repo, updating the image tag
  4. SRE approves the PR (Slack notification with @oncall-sre, expected response time: <5 minutes)
  5. Merge triggers auto-sync to production
  6. Post-incident: The hotfix branch is merged to main through the normal process
Emergency Override

For true emergencies (P0, revenue-impacting), the on-call SRE can sync directly from the ArgoCD UI without waiting for PR approval. This is logged and auditable. The PR is created retroactively. We've used this exactly 3 times in 18 months. Having the escape hatch prevents people from bypassing GitOps entirely.

Monitoring ArgoCD Itself

ArgoCD exposes Prometheus metrics. Monitor these to catch problems before they affect deployments:

# ArgoCD application health
argocd_app_info{health_status="Degraded"} > 0

# Sync failures
increase(argocd_app_sync_total{phase="Error"}[1h]) > 0

# Repo server performance (slow renders block all syncs)
histogram_quantile(0.99,
  sum(rate(argocd_repo_server_request_duration_seconds_bucket[5m])) by (le)
) > 10

# Controller queue depth (backlog of reconciliations)
argocd_app_reconcile_count > 100

# Git fetch failures
increase(argocd_git_request_total{request_type="fetch", result="error"}[5m]) > 0
Repo Server Memory

The repo server clones every Git repo and renders every Helm chart in memory. With 50+ apps and large repos, it can easily OOM. We had to increase the repo server memory to 2Gi and add --parallelismlimit 5 to prevent it from rendering too many charts simultaneously. Monitor container_memory_working_set_bytes{container="repo-server"} closely.

Common Pitfalls

  • Monorepo for app code + GitOps manifests: Every app commit triggers ArgoCD reconciliation even if manifests didn't change. Separate repos.
  • Not pinning Helm chart versions: targetRevision: * means ArgoCD might deploy a new chart version without you knowing. Pin it.
  • Ignoring resource hooks on CRDs: CRDs must be synced before resources that use them. Use sync waves.
  • Too many apps in one ArgoCD instance: Beyond ~200 apps, the controller struggles. Shard across multiple instances or use ApplicationSets with progressive syncs.
  • No backup of ArgoCD itself: If the management cluster dies, you lose all Application definitions. Back up the argocd namespace or store Application YAMLs in Git (which app-of-apps gives you for free).

Key Takeaways

GitOps with ArgoCD is not just "put YAML in Git." It's an operational model that requires thoughtful design around repository structure, secrets management, sync policies, RBAC, and emergency procedures. Start with the app-of-apps pattern, use External Secrets Operator for secrets, enable auto-sync in staging but keep production manual until you trust the system. Define your hotfix process before you need it. And monitor ArgoCD itself — it's infrastructure too, and it can fail in ways that silently block all your deployments.
