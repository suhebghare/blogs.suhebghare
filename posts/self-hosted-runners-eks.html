Why Self-Hosted Runners?

GitHub-hosted runners are convenient — zero setup, always available. But once you're running 200+ CI/CD pipelines across 40 microservices, three problems become impossible to ignore:

  • Cost: At $0.008/minute for Linux runners, our 85,000 monthly build minutes cost ~$6,800/month. Self-hosted on EKS brought that down to ~$2,600/month.
  • Private network access: Integration tests need to hit RDS, ElastiCache, and internal APIs inside our VPC. GitHub-hosted runners can't reach them without exposing services publicly or running a VPN tunnel per job.
  • Custom tooling: Our builds need specific versions of Terraform, Helm, AWS CLI, and internal CLI tools baked into the runner image. Reinstalling these every run added 3-4 minutes per job.

Architecture: Actions Runner Controller on EKS

We use Actions Runner Controller (ARC) — the official Kubernetes controller for GitHub Actions self-hosted runners. It manages runner pods as ephemeral workloads that scale based on workflow demand.

GitHub webhook fires on workflow_job event
ARC webhook server receives the event
ARC controller creates a runner pod
Runner registers with GitHub, picks up the job
Job completes → pod is terminated (ephemeral)

RunnerDeployment vs RunnerSet

ARC offers two CRDs for managing runners:

FeatureRunnerDeploymentRunnerSet
Scaling modelHorizontalRunnerAutoscalerBuilt-in autoscaling
Pod identityRandom namesStable ordinal names
Docker-in-DockerSidecar containerSidecar container
Recommended forMost workloadsStateful build caches

We use RunnerDeployment for 90% of workloads. RunnerSet is only used for our monorepo builds that benefit from persistent build caches on PVCs.

RunnerDeployment YAML

apiVersion: actions.summerwind.dev/v1alpha1
kind: RunnerDeployment
metadata:
  name: org-runners
  namespace: actions-runner-system
spec:
  replicas: 2  # minimum idle runners
  template:
    spec:
      organization: our-org
      labels:
        - self-hosted
        - linux
        - eks
      ephemeral: true
      dockerEnabled: false  # no DinD — use Kaniko
      resources:
        limits:
          cpu: "4"
          memory: "8Gi"
        requests:
          cpu: "2"
          memory: "4Gi"
      nodeSelector:
        node-group: ci-runners
      tolerations:
        - key: "dedicated"
          operator: "Equal"
          value: "ci-runners"
          effect: "NoSchedule"

Autoscaling with HorizontalRunnerAutoscaler

apiVersion: actions.summerwind.dev/v1alpha1
kind: HorizontalRunnerAutoscaler
metadata:
  name: org-runners-autoscaler
  namespace: actions-runner-system
spec:
  scaleTargetRef:
    kind: RunnerDeployment
    name: org-runners
  minReplicas: 2
  maxReplicas: 30
  scaleUpTriggers:
    - githubEvent:
        workflowJob: {}
      amount: 1
      duration: "5m"

This webhook-based autoscaler reacts to workflow_job events in real time. When a job is queued, it scales up by 1 runner within seconds. The duration field keeps the runner alive for 5 minutes after creation to handle burst scenarios.

The 5 Pitfalls We Hit in Production

Pitfall 1: Runner Pods Getting OOMKilled

🚨 Real Incident

Our Java microservice builds were getting killed mid-compilation. kubectl describe pod showed OOMKilled with exit code 137. The runner itself uses ~500MB, but gradle build was consuming 6GB+ for large projects.

Fix: Profile your heaviest builds first. We set runner memory limits to 8Gi after discovering that Gradle + parallel test execution peaked at 7.2GB. Set JAVA_OPTS=-Xmx4g in the runner environment to cap JVM heap separately.

Pitfall 2: Docker-in-Docker Security Issues

Running Docker inside runner pods requires privileged mode — a massive security risk. A compromised build could escape the container and access the host node.

💡 Solution: Use Kaniko

Kaniko builds container images in userspace without a Docker daemon. No privileged mode needed. We replaced all docker build steps with Kaniko executor and saw zero security findings in our next audit.

# GitHub Actions step using Kaniko
- name: Build and push image
  run: |
    /kaniko/executor \
      --context=. \
      --dockerfile=Dockerfile \
      --destination=$ECR_REPO:$GITHUB_SHA \
      --cache=true \
      --cache-repo=$ECR_REPO/cache

Pitfall 3: Shared /tmp Causing Flaky Tests

Multiple test suites writing to /tmp with hardcoded filenames caused intermittent failures. Two parallel jobs on the same runner pod would overwrite each other's temp files.

Fix: Set ephemeral: true in the RunnerDeployment so each job gets a fresh pod. This eliminated all shared-state flakiness. The tradeoff is slightly slower cold starts (~15 seconds for pod scheduling), but reliability is worth it.

Pitfall 4: GitHub Rate Limiting Webhook Events

During peak hours (9-11 AM when all teams push), we'd see 50+ workflow_job events per minute. GitHub's webhook delivery has retry logic, but ARC's webhook server was dropping events under load.

Fix: Increased ARC webhook server replicas to 3 and added an HPA targeting 70% CPU. Also configured GitHub webhook to use a dedicated ALB endpoint with connection draining.

Pitfall 5: Runner Pod Scheduled on Prod Node Group

🚨 Real Incident: Resource Contention

A CI runner pod requesting 4 CPU / 8Gi memory got scheduled on a production node group because we forgot to add nodeSelector in the initial deployment. The runner consumed resources meant for production workloads, causing latency spikes on our payment service during a build storm. P99 latency went from 120ms to 2.3 seconds for 12 minutes.

Fix: Dedicated node group with taints. Runners must have matching tolerations or they won't schedule there. Production nodes reject runner pods entirely.

Node Group Strategy for CI Runners

# Terraform — dedicated spot node group for CI runners
resource "aws_eks_node_group" "ci_runners" {
  cluster_name    = aws_eks_cluster.main.name
  node_group_name = "ci-runners-spot"
  node_role_arn   = aws_iam_role.node.arn
  subnet_ids      = var.private_subnet_ids
  capacity_type   = "SPOT"
  instance_types  = ["m5.xlarge", "m5a.xlarge", "m6i.xlarge", "m6a.xlarge"]

  scaling_config {
    desired_size = 2
    min_size     = 1
    max_size     = 15
  }

  taint {
    key    = "dedicated"
    value  = "ci-runners"
    effect = "NO_SCHEDULE"
  }

  labels = {
    "node-group" = "ci-runners"
  }
}

✅ Key Takeaway

Self-hosted runners on EKS make sense when you exceed ~20,000 build minutes/month, need VPC access, or require custom tooling. Below that threshold, GitHub-hosted runners are simpler and the cost difference doesn't justify the operational overhead.

Monitoring and Observability

We track runner health with Prometheus metrics exported by ARC:

  • github_runner_status — idle, active, or offline runners
  • github_runner_job_duration_seconds — build time per workflow
  • kube_pod_container_status_restarts_total — OOMKill detection
  • kube_pod_status_phase — pending pods indicate scaling lag

Grafana dashboard alerts fire when: pending pods exceed 5 for more than 2 minutes (scaling issue), OOMKill count exceeds 3 in 10 minutes, or runner registration failures spike.

Lessons Learned

Start with ephemeral runners. The slight cold-start penalty is worth the elimination of state-related bugs. We wasted 2 weeks debugging flaky tests before switching to ephemeral mode.

Never run DinD in production. Privileged containers are a security audit failure waiting to happen. Kaniko or Buildah are drop-in replacements for 95% of use cases.

Taints are non-negotiable. Without taints on your CI node group, the Kubernetes scheduler will happily place runner pods on production nodes. We learned this the hard way during a payment service incident.
