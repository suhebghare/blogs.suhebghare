Handling Credential Stuffing Attacks in AWS

500K Requests Per Hour — And Every One Had Valid Credentials

At 2:17 AM on a Tuesday, our CloudWatch alarm fired: the 401 response rate on our login endpoint had spiked from a baseline of 3% to 47% in under 10 minutes. By the time the on-call engineer opened their laptop, attackers were testing 500,000 stolen credential pairs per hour against our authentication API.

This is the story of how we detected, mitigated, and permanently defended against a credential stuffing attack — and the $2,400 in AWS costs it racked up before we stopped it.

Detection: How We Knew We Were Under Attack

The first signal was a CloudWatch metric alarm on our API Gateway 4xx error rate. We had set a threshold of 15% — well above our normal 3% baseline — and it triggered at 2:17 AM.

CloudWatch Alarm Configuration

aws cloudwatch put-metric-alarm \
  --alarm-name "LoginEndpoint-High401Rate" \
  --metric-name "4XXError" \
  --namespace "AWS/ApiGateway" \
  --statistic "Average" \
  --period 300 \
  --threshold 15 \
  --comparison-operator "GreaterThanThreshold" \
  --evaluation-periods 2 \
  --alarm-actions "arn:aws:sns:us-east-1:123456789:security-alerts" \
  --dimensions Name=ApiName,Value=AuthAPI Name=Stage,Value=prod

Athena Query That Confirmed the Attack

Once alerted, we ran this Athena query against our WAF logs to understand the attack pattern:

SELECT
  httpRequest.clientIp,
  httpRequest.country,
  COUNT(*) as request_count,
  COUNT(CASE WHEN responseCodeSent = 401 THEN 1 END) as failed_logins,
  COUNT(CASE WHEN responseCodeSent = 200 THEN 1 END) as successful_logins,
  ROUND(COUNT(CASE WHEN responseCodeSent = 401 THEN 1 END) * 100.0 / COUNT(*), 2) as failure_rate
FROM waf_logs
WHERE httpRequest.uri LIKE '/api/auth/login%'
  AND from_unixtime(timestamp/1000) > current_timestamp - interval '2' hour
GROUP BY httpRequest.clientIp, httpRequest.country
HAVING COUNT(*) > 50
ORDER BY request_count DESC
LIMIT 50;

The results were clear: 3,200 unique IPs, each sending 150-200 requests per hour, all targeting /api/auth/login. The failure rate was 96% — classic credential stuffing using a breached database.

🚨 The Scary Part

Of the 500K login attempts per hour, approximately 4% were succeeding. That's 20,000 successful logins per hour with stolen credentials. By the time we detected the attack (37 minutes in), 1,247 customer accounts had been accessed. The attackers were harvesting saved payment methods and loyalty points.

Mitigation: The Four Defense Layers

We implemented four layers of defense in 48 hours, starting with the fastest to deploy:

Layer 1: WAF Rate Limiting → Immediate (deployed in 15 min)
Layer 2: IP Reputation Blocking → 30 minutes
Layer 3: CAPTCHA on Repeated Failures → 4 hours
Layer 4: Cognito Advanced Security → 48 hours

Layer 1: WAF Rate Limiting on Login Endpoint

First priority — throttle the attack volume. We deployed a rate-based rule scoped specifically to the login endpoint:

{
  "Name": "LoginEndpointRateLimit",
  "Priority": 1,
  "Statement": {
    "RateBasedStatement": {
      "Limit": 100,
      "AggregateKeyType": "IP",
      "ScopeDownStatement": {
        "AndStatement": {
          "Statements": [
            {
              "ByteMatchStatement": {
                "SearchString": "/api/auth/login",
                "FieldToMatch": { "UriPath": {} },
                "TextTransformations": [
                  { "Priority": 0, "Type": "LOWERCASE" }
                ],
                "PositionalConstraint": "STARTS_WITH"
              }
            },
            {
              "ByteMatchStatement": {
                "SearchString": "POST",
                "FieldToMatch": { "Method": {} },
                "TextTransformations": [
                  { "Priority": 0, "Type": "NONE" }
                ],
                "PositionalConstraint": "EXACTLY"
              }
            }
          ]
        }
      }
    }
  },
  "Action": { "Block": {} },
  "VisibilityConfig": {
    "SampledRequestsEnabled": true,
    "CloudWatchMetricsEnabled": true,
    "MetricName": "LoginEndpointRateLimit"
  }
}

This immediately cut attack traffic by 78%. But 700 IPs were staying under the 100 req/5min threshold by rotating slowly.

Layer 2: IP Reputation Blocking

We enabled the AWS-managed IP reputation list and added a custom IP set with the top 500 attacking IPs identified from our Athena query:

# Create IP set with attacking IPs
aws wafv2 create-ip-set \
  --name "CredentialStuffingAttackerIPs" \
  --scope REGIONAL \
  --ip-address-version IPV4 \
  --addresses "203.0.113.0/24" "198.51.100.0/24" ...

# Add to WAF rule
{
  "Name": "BlockAttackerIPs",
  "Priority": 0,
  "Statement": {
    "IPSetReferenceStatement": {
      "ARN": "arn:aws:wafv2:us-east-1:123456789:regional/ipset/CredentialStuffingAttackerIPs/abc123"
    }
  },
  "Action": { "Block": {} }
}

Layer 3: CAPTCHA on Repeated Failures

For the remaining slow-and-low attackers, we implemented a CAPTCHA challenge that triggers after 3 failed login attempts from the same IP within 10 minutes. This was done at the application level using AWS WAF's CAPTCHA action:

{
  "Name": "CaptchaAfterFailedLogins",
  "Priority": 4,
  "Statement": {
    "RateBasedStatement": {
      "Limit": 5,
      "AggregateKeyType": "IP",
      "ScopeDownStatement": {
        "ByteMatchStatement": {
          "SearchString": "/api/auth/login",
          "FieldToMatch": { "UriPath": {} },
          "TextTransformations": [
            { "Priority": 0, "Type": "LOWERCASE" }
          ],
          "PositionalConstraint": "STARTS_WITH"
        }
      }
    }
  },
  "Action": {
    "Captcha": {
      "CustomRequestHandling": {
        "InsertHeaders": [
          {
            "Name": "x-captcha-required",
            "Value": "true"
          }
        ]
      }
    }
  }
}

Layer 4: Cognito Advanced Security

For long-term protection, we enabled Cognito's advanced security features including compromised credential detection and adaptive authentication:

aws cognito-idp set-risk-configuration \
  --user-pool-id us-east-1_AbCdEfGhI \
  --compromised-credentials-risk-configuration '{
    "EventFilter": ["SIGN_IN"],
    "Actions": {
      "EventAction": "BLOCK"
    }
  }' \
  --account-takeover-risk-configuration '{
    "NotifyConfiguration": {
      "SourceArn": "arn:aws:ses:us-east-1:123456789:identity/security@example.com",
      "NoActionEmail": { "Subject": "Login from new device", "TextBody": "We noticed a login..." },
      "MfaEmail": { "Subject": "MFA required", "TextBody": "Additional verification needed..." },
      "BlockEmail": { "Subject": "Login blocked", "TextBody": "A suspicious login was blocked..." }
    },
    "Actions": {
      "HighAction": { "EventAction": "BLOCK", "Notify": true },
      "MediumAction": { "EventAction": "MFA_REQUIRED", "Notify": true },
      "LowAction": { "EventAction": "NO_ACTION", "Notify": false }
    }
  }'

Notification Pipeline

We built an automated notification pipeline so the security team gets alerted within minutes of an attack starting:

Detection → Notification Flow:

WAF Logs → CloudWatch Metric Filter (401 rate) → CloudWatch Alarm → SNS Topic → Lambda → PagerDuty + Slack

# CloudWatch Metric Filter for 401 responses on login
aws logs put-metric-filter \
  --log-group-name "/aws/apigateway/auth-api" \
  --filter-name "Login401Rate" \
  --filter-pattern '{ $.status = 401 && $.path = "/api/auth/login" }' \
  --metric-transformations \
    metricName=Login401Count,metricNamespace=Security/Auth,metricValue=1

⚠️ Set AWS Budget Alarms

We now have AWS Budget alarms set at 150% of daily expected spend. A credential stuffing attack is also a financial attack — every request costs you money. Rate limiting at the WAF level (before API Gateway) is critical because it stops the cost accumulation at the edge.

Long-Term Prevention Strategy

After the incident, we implemented these permanent defenses:

1. Breached Password Detection

Cognito's compromised credentials feature checks passwords against known breach databases during sign-in. If a user's credentials appear in a breach, they're forced to reset their password.

2. MFA Enforcement

We rolled out mandatory MFA for all accounts with saved payment methods. This single change makes credential stuffing nearly useless — even if the password is correct, the attacker can't complete the MFA challenge.

aws cognito-idp set-user-pool-mfa-config \
  --user-pool-id us-east-1_AbCdEfGhI \
  --mfa-configuration ON \
  --software-token-mfa-configuration Enabled=true

3. Device Fingerprinting

We implemented device fingerprinting using Cognito's device tracking. New devices trigger a step-up authentication challenge, and we track device trust scores over time.

4. Login Anomaly Detection

A Lambda function analyzes login patterns in real-time: impossible travel (login from New York, then Tokyo 5 minutes later), unusual login times, and velocity checks (same account from multiple IPs).

Post-Incident Timeline

Hour 0-1: Emergency Response

WAF rate limiting deployed. Attack volume reduced 78%. Compromised accounts identified and force-logged-out via Cognito admin API.

Hour 1-4: Immediate Hardening

IP reputation blocking enabled. CAPTCHA challenge deployed on login. All 1,247 compromised accounts locked and password reset emails sent.

Hour 4-24: Investigation

Full Athena analysis of attack patterns. Identified the credential list source (a 2023 breach of a gaming platform). Confirmed no payment data was exfiltrated — attackers were harvesting loyalty points.

Hour 24-48: Permanent Defenses

Cognito advanced security enabled. MFA rollout initiated. Device fingerprinting deployed. Budget alarms configured.

Key Takeaways

  • Monitor 401 rates, not just 5xx. Credential stuffing doesn't cause server errors — it causes authentication failures
  • Rate limit at the WAF level to stop cost accumulation before requests hit API Gateway/Lambda
  • MFA is the ultimate defense — it makes stolen passwords useless
  • Credential stuffing is a financial attack — every request costs you money. Set budget alarms
  • Layer your defenses: WAF rate limiting + IP reputation + CAPTCHA + Cognito advanced security
  • Have an Athena query ready — you don't want to be writing SQL at 2 AM during an incident
  • Force password resets for compromised accounts immediately, don't wait for the investigation to complete

Since implementing all four defense layers, we've had zero successful credential stuffing attacks in 10 months. The WAF blocks an average of 180K credential stuffing attempts per day, and Cognito's compromised credential detection has forced 12,000 users to update breached passwords.
