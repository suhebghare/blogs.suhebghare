Can AI Replace On-Call Engineers?

👁️ 500 reads

We Tested It for 6 Months. Here's the Honest Answer.

Every vendor pitch says the same thing: "AI will handle your on-call." After hearing this at three conferences, we decided to actually test it. For 6 months, we ran an AI-assisted on-call system alongside our human rotation across 3 EKS clusters, 47 microservices, and ~120 pages/month.

The short answer: No, AI cannot replace on-call engineers. The longer answer: AI handled 34% of pages without human intervention, and that 34% was transformative for team morale. But the other 66% — the ones that actually matter — still need a human.

What We Tested

We built auto-remediation for the most common, well-understood failure modes — the ones where the runbook is "do this exact thing every time":

Issue Auto-Remediation Success Rate Frequency
CrashLoopBackOff (OOM) Restart pod with increased memory limit 89% ~15/month
Redis cache full Flush expired keys, alert if persists 95% ~8/month
HPA max replicas hit Temporarily increase max, scale up node group 92% ~12/month
Certificate expiry warning Trigger cert-manager renewal 100% ~3/month
Disk pressure on nodes Clean docker images, evict pods if needed 78% ~5/month

The Auto-Remediation Engine

The system listens to PagerDuty webhooks, matches the alert to a known runbook, executes the remediation, and verifies the fix. If verification fails, it escalates to a human with full context of what it tried.

import subprocess
import json
import time
import requests

RUNBOOKS = {
    'KubePodCrashLooping': {
        'match': lambda alert: 'CrashLoopBackOff' in alert.get('details', ''),
        'remediate': 'restart_pod_with_bump',
        'verify': 'check_pod_running',
        'max_attempts': 2,
        'cooldown_minutes': 30
    },
    'RedisMemoryHigh': {
        'match': lambda alert: alert.get('service') == 'redis',
        'remediate': 'flush_expired_redis_keys',
        'verify': 'check_redis_memory',
        'max_attempts': 1,
        'cooldown_minutes': 60
    },
    'HPAMaxedOut': {
        'match': lambda alert: 'HPA' in alert.get('title', '') and 'max' in alert.get('title', ''),
        'remediate': 'bump_hpa_max',
        'verify': 'check_hpa_status',
        'max_attempts': 1,
        'cooldown_minutes': 120
    }
}

def handle_alert(alert):
    for name, runbook in RUNBOOKS.items():
        if runbook['match'](alert):
            # Check cooldown
            if recently_remediated(name, runbook['cooldown_minutes']):
                escalate(alert, f"Cooldown active for {name}. Needs human.")
                return

            for attempt in range(runbook['max_attempts']):
                result = execute_remediation(runbook['remediate'], alert)
                time.sleep(30)  # Wait for effect

                if verify_fix(runbook['verify'], alert):
                    log_success(name, alert, attempt + 1)
                    resolve_pagerduty(alert)
                    notify_slack(alert, f"✅ Auto-resolved: {name} (attempt {attempt + 1})")
                    return

            # All attempts failed — escalate with context
            escalate(alert, f"Auto-remediation failed after {runbook['max_attempts']} attempts")
            return

    # No matching runbook — escalate immediately
    escalate(alert, "No auto-remediation available")

Example: Pod Restart with Memory Bump

def restart_pod_with_bump(alert):
    namespace = alert['labels']['namespace']
    deployment = alert['labels']['deployment']

    # Get current memory limit
    result = subprocess.run([
        'kubectl', 'get', 'deployment', deployment,
        '-n', namespace,
        '-o', 'jsonpath={.spec.template.spec.containers[0].resources.limits.memory}'
    ], capture_output=True, text=True)

    current_mem = result.stdout  # e.g., "512Mi"
    new_mem = bump_memory(current_mem)  # 512Mi → 768Mi (1.5x)

    # Patch deployment with new limit
    patch = json.dumps({
        "spec": {"template": {"spec": {"containers": [{
            "name": deployment,
            "resources": {"limits": {"memory": new_mem}}
        }]}}}
    })
    subprocess.run([
        'kubectl', 'patch', 'deployment', deployment,
        '-n', namespace,
        '--type', 'strategic',
        '-p', patch
    ])
    return {'old_memory': current_mem, 'new_memory': new_mem}

What AI Is Good At

✅
Pattern matching known runbooks

If the failure mode is documented and the fix is deterministic, AI executes it faster and more consistently than a sleepy human at 3am.

✅
Correlating metrics across services

AI can check CPU, memory, error rates, and latency across 47 services in seconds. A human checks 2-3 dashboards and makes assumptions.

✅
Drafting postmortems

We feed the incident timeline to GPT-4 and get a first draft in 30 seconds. It's 70% accurate and saves 2 hours of writing.

✅
Providing context to the human

Even when AI can't fix the problem, it can gather logs, metrics, recent deploys, and related alerts — giving the human a 5-minute head start.

What AI Cannot Do

❌
Novel failure modes

When a Kubernetes API server bug caused intermittent 409 conflicts on pod scheduling, the AI had no runbook to match. It escalated correctly, but a human had to diagnose from scratch.

❌
Cross-system reasoning

"The payment service is slow because the fraud detection service is calling a third-party API that's rate-limiting us, which is causing timeouts that back up the queue." AI doesn't connect these dots.

❌
Blast radius judgment

"Should we restart the database primary during peak traffic?" This requires understanding business context, customer impact, and risk tolerance that AI doesn't have.

❌
Communication and coordination

Major incidents require updating stakeholders, coordinating across teams, making trade-off decisions. AI can draft the status page update, but a human decides what to say.

The Hybrid Model That Actually Works

After 6 months of iteration, here's the model we settled on:

Alert Fires
AI Triages (match runbook?)
Known Issue → Auto-Remediate → Verify → Resolve
Unknown → Gather Context → Escalate to Human with Full Brief
The Key Insight

AI doesn't replace the on-call engineer. It replaces the first 10 minutes of every incident — the part where you're rubbing your eyes, opening your laptop, and trying to figure out what's happening. For known issues, those 10 minutes are the entire incident. For unknown issues, those 10 minutes of context gathering are the most valuable gift you can give a half-awake engineer.

Safety Guardrails

We learned these the hard way (yes, the AI made things worse once before we added guardrails):

  • Cooldown periods — if the same remediation ran in the last 30-120 minutes, escalate instead of retrying
  • Blast radius limits — AI can restart 1 pod, not an entire deployment. It can scale up, never scale down.
  • No data mutations — AI never touches databases, never deletes anything, never modifies config maps in production
  • Verification required — every remediation must have a verification step. If verification fails, escalate immediately.
  • Full audit log — every action the AI takes is logged to a dedicated Slack channel and CloudWatch
  • Kill switch — one Slack command (/ai-oncall disable) turns off all auto-remediation instantly

Ethical Considerations

⚠️ Who Is Responsible When AI Makes It Worse?

This isn't hypothetical. In month 2, the AI restarted a pod that was in CrashLoopBackOff due to a config error. The restart didn't help (same config), but the restart caused a brief connection drop that cascaded to 3 dependent services. Total impact: 45 seconds of elevated errors across 3 services.

Our answer: the team that configured the auto-remediation is responsible. AI is a tool. The engineer who wrote the runbook and set the guardrails owns the outcome. This is why we require peer review for all auto-remediation rules.

The Verdict

Claim Reality
"AI will replace on-call" No. It handles 34% of pages — the easy, repetitive ones.
"AI will reduce on-call burden" Yes. Significantly. Our engineers sleep through the night more often.
"AI can handle production incidents" Only known, well-documented ones with deterministic fixes.
"AI is dangerous for production" Only without guardrails. With proper limits, it's safer than a tired human.

AI won't replace your on-call engineers. But on-call engineers with AI will replace on-call engineers without it. The competitive advantage isn't automation — it's giving your humans superpowers.
