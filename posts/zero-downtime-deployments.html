Zero-Downtime Deployments: The Complete Playbook

📅 January 15, 2025 ⏱ 16 min read 👁 1240 reads
👁️1240reads
👍487likes
👎31dislikes

I've deployed to production thousands of times across dozens of services. The ones that went wrong — the ones that woke me up at 2am — almost always came down to the same handful of misconfigurations. This post is the playbook I wish I had when I started. Every config here has been tested in production clusters running 200+ pods.

The Incident That Started This Post

In 2023, a missing readinessProbe on a payment service caused a 5-minute outage during a routine deploy. Kubernetes routed traffic to pods that hadn't finished loading their connection pools. 2,300 requests returned 502s. Revenue impact: ~$18,000. The fix was 8 lines of YAML.

Why "Zero Downtime" Is Harder Than It Sounds

Most teams think they have zero-downtime deployments because they use RollingUpdate. They don't. There's a gap between when Kubernetes considers a pod "ready" and when your application is actually ready to serve traffic. There's another gap between when a pod receives SIGTERM and when it stops getting traffic. Both gaps cause errors.

True zero-downtime requires getting three things right simultaneously:

  • Readiness gates — don't send traffic until the app is genuinely ready
  • Graceful shutdown — finish in-flight requests before dying
  • Deployment strategy — always have enough healthy pods to handle load

Strategy 1: Rolling Updates (The Default)

Rolling updates replace pods incrementally. Kubernetes creates new pods, waits for them to be ready, then terminates old ones. It's the default strategy and works for 80% of use cases — if configured correctly.

The Deployment Manifest That Actually Works

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # Create 1 extra pod during rollout
      maxUnavailable: 0   # Never reduce below desired count
  template:
    spec:
      terminationGracePeriodSeconds: 45
      containers:
      - name: api
        image: api-server:v2.3.1
        ports:
        - containerPort: 8080
        readinessProbe:
          httpGet:
            path: /healthz/ready
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 5
          failureThreshold: 3
          successThreshold: 1
        livenessProbe:
          httpGet:
            path: /healthz/live
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 10
          failureThreshold: 3
        lifecycle:
          preStop:
            exec:
              command: ["/bin/sh", "-c", "sleep 10"]
        resources:
          requests:
            cpu: 250m
            memory: 256Mi
          limits:
            cpu: 500m
            memory: 512Mi

Why maxUnavailable: 0 Matters

Setting maxUnavailable: 0 with maxSurge: 1 means Kubernetes will always create a new pod before terminating an old one. You'll briefly run 5 pods instead of 4, but you'll never drop below 4 healthy pods. The tradeoff is slightly slower rollouts (each pod must become ready before the next one starts) and slightly higher resource usage during deploys.

Tuning for Speed vs Safety

For non-critical services, maxSurge: 25% and maxUnavailable: 25% gives faster rollouts. For anything handling payments, auth, or user data, use maxSurge: 1, maxUnavailable: 0. The extra 30 seconds per deploy is worth it.

The preStop Hook: The Most Overlooked Config

When Kubernetes sends SIGTERM to a pod, two things happen simultaneously: the pod is removed from the Service endpoints, and the container receives the signal. The problem? Endpoint removal isn't instant — kube-proxy and ingress controllers need time to update their routing tables. If your app shuts down immediately on SIGTERM, it'll miss requests that are still being routed to it.

The sleep 10 in the preStop hook gives the network layer time to catch up. Your app keeps running and serving requests for 10 seconds after SIGTERM, by which point all load balancers have stopped sending new traffic.

SIGTERM sent to pod
preStop hook: sleep 10s
Endpoints updated (kube-proxy, ingress)
No new traffic arrives
App receives SIGTERM after sleep
App drains in-flight requests
Pod terminates

Readiness Probes: Separate /ready from /live

This is where most teams get it wrong. They use the same endpoint for both probes. A liveness probe failure restarts the pod. A readiness probe failure removes it from the service. These are fundamentally different actions.

Your /healthz/ready endpoint should check:

  • Database connection pool is initialized
  • Cache is warmed (if applicable)
  • Downstream dependencies are reachable
  • Application has finished startup tasks

Your /healthz/live endpoint should only check:

  • The process is running
  • It's not deadlocked
  • It can respond to HTTP requests
Don't Check Dependencies in Liveness Probes

If your liveness probe checks the database and the DB goes down, Kubernetes will restart all your pods simultaneously. Now you have a cascading failure instead of a degraded service. Liveness = "is this process healthy?" Readiness = "can this process serve traffic?"

Strategy 2: Blue/Green Deployments

Blue/green runs two identical environments. You deploy to the inactive one, test it, then switch traffic. The advantage: instant rollback by switching back. The cost: double the resources during deployment.

# Blue deployment (current production)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server-blue
  labels:
    app: api-server
    version: blue
spec:
  replicas: 4
  selector:
    matchLabels:
      app: api-server
      version: blue
  template:
    metadata:
      labels:
        app: api-server
        version: blue
    spec:
      containers:
      - name: api
        image: api-server:v2.3.0
---
# Green deployment (new version)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server-green
  labels:
    app: api-server
    version: green
spec:
  replicas: 4
  selector:
    matchLabels:
      app: api-server
      version: green
  template:
    metadata:
      labels:
        app: api-server
        version: green
    spec:
      containers:
      - name: api
        image: api-server:v2.3.1
---
# Service — switch by changing selector
apiVersion: v1
kind: Service
metadata:
  name: api-server
spec:
  selector:
    app: api-server
    version: blue  # Change to 'green' to switch
  ports:
  - port: 80
    targetPort: 8080

The switch is a single kubectl patch:

kubectl patch svc api-server -p '{"spec":{"selector":{"version":"green"}}}'

Rollback is the same command with "version":"blue". Takes under a second.

Strategy 3: Canary Deployments

Canary sends a small percentage of traffic to the new version. If metrics look good, you gradually increase. If not, you roll back with minimal blast radius. This is the gold standard for high-traffic services.

With Argo Rollouts, canary becomes declarative:

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: api-server
spec:
  replicas: 10
  strategy:
    canary:
      steps:
      - setWeight: 10
      - pause: { duration: 5m }
      - setWeight: 30
      - pause: { duration: 5m }
      - setWeight: 60
      - pause: { duration: 5m }
      - setWeight: 100
      canaryMetadata:
        labels:
          role: canary
      stableMetadata:
        labels:
          role: stable
      analysis:
        templates:
        - templateName: success-rate
        startingStep: 2
        args:
        - name: service-name
          value: api-server

The AnalysisTemplate queries Prometheus to validate the canary:

apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  args:
  - name: service-name
  metrics:
  - name: success-rate
    interval: 60s
    successCondition: result[0] >= 0.99
    provider:
      prometheus:
        address: http://prometheus:9090
        query: |
          sum(rate(http_requests_total{
            service="{{args.service-name}}",
            status=~"2..",
            role="canary"
          }[2m])) /
          sum(rate(http_requests_total{
            service="{{args.service-name}}",
            role="canary"
          }[2m]))

PodDisruptionBudgets: Don't Skip This

A PDB tells Kubernetes how many pods must remain available during voluntary disruptions (node drains, cluster upgrades, spot instance reclamation). Without a PDB, a node drain can kill all your pods at once.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-server-pdb
spec:
  minAvailable: 3    # Or use maxUnavailable: 1
  selector:
    matchLabels:
      app: api-server
PDB + maxUnavailable: 0 Gotcha

If you set minAvailable equal to your replica count and maxUnavailable: 0 in your deployment, node drains will hang forever. The drain can't evict pods because the PDB won't allow it, and the deployment can't create new pods on other nodes because it's already at max replicas. Set minAvailable to replicas - 1.

Strategy Comparison

Criteria Rolling Update Blue/Green Canary
Rollback Speed ~2-5 min (redeploy) <1 sec (switch selector) ~10 sec (set weight 0)
Resource Overhead Low (maxSurge pods) High (2x resources) Low-Medium
Blast Radius Gradual (per pod) All-or-nothing Controlled (% traffic)
Complexity Low (built-in) Medium High (needs Argo/Istio)
DB Migration Safe ⚠️ Needs care ⚠️ Needs care ⚠️ Needs care
Best For Most services Critical, stateless High-traffic, metrics-rich

When to Use Each Strategy

Rolling
Internal APIs, background workers, services with <100 RPS. Low overhead, good enough for most workloads.
Blue/Green
Payment services, auth services, anything where instant rollback is worth 2x cost. Also great for major version upgrades.
Canary
Customer-facing APIs with >1000 RPS, services with good observability, anything where you need data-driven confidence before full rollout.
Recreate
Only for dev/staging or services that can't run two versions simultaneously (some stateful workloads, single-writer databases).

The Database Migration Problem

None of these strategies solve database migrations. If v2 requires a schema change that breaks v1, you'll have downtime regardless of your deployment strategy. The solution is expand-and-contract migrations:

  1. Expand: Add new columns/tables without removing old ones. Deploy v2 that writes to both old and new schemas.
  2. Migrate: Backfill data from old schema to new schema.
  3. Contract: Deploy v3 that only uses the new schema. Remove old columns in a later migration.

This adds complexity but it's the only way to do truly zero-downtime schema changes. Tools like gh-ost (GitHub's online schema migration for MySQL) and pgroll (for PostgreSQL) help automate this.

The Complete Checklist

  • Separate readiness and liveness probe endpoints
  • Readiness probe checks actual application readiness (DB pool, cache, etc.)
  • Liveness probe only checks process health — never external dependencies
  • preStop hook with sleep 10-15s for graceful shutdown
  • terminationGracePeriodSeconds > preStop sleep + drain time
  • maxUnavailable: 0 for critical services
  • PodDisruptionBudget with minAvailable = replicas - 1
  • Resource requests set (required for scheduling during rollouts)
  • Application handles SIGTERM gracefully (drain connections, finish requests)
  • Database migrations are backward-compatible

Monitoring Your Deployments

You need to know when a deployment is causing errors. These Prometheus queries are what I run on every deploy:

# Error rate during rollout
sum(rate(http_requests_total{status=~"5.."}[1m]))
  /
sum(rate(http_requests_total[1m]))

# P99 latency spike detection
histogram_quantile(0.99,
  sum(rate(http_request_duration_seconds_bucket[2m])) by (le)
)

# Pod restart count (catches CrashLoopBackOff)
sum(increase(kube_pod_container_status_restarts_total{
  namespace="production"
}[5m])) by (pod)
Results After Implementing This Playbook

After standardizing these patterns across 47 microservices: deployment-related incidents dropped from ~3/month to 0 over 6 months. Average deploy time increased by 45 seconds (due to maxUnavailable: 0), but we eliminated all deployment-related pages. The team stopped fearing Friday deploys.

Key Takeaways

Zero-downtime deployments aren't about picking the right strategy — they're about getting the fundamentals right. A properly configured rolling update with correct readiness probes, preStop hooks, and PDBs will outperform a poorly configured canary deployment every time. Start with the basics, measure your error rates during deploys, and only add complexity (canary, blue/green) when you have a specific problem that rolling updates can't solve.
