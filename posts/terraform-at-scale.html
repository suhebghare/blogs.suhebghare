Terraform at Scale: Managing 500+ Resources Without Losing Your Mind

📅 January 5, 2025 ⏱ 15 min read 👁 910 reads
👁️910reads
👍401likes
👎31dislikes

When your Terraform codebase manages 50 resources, everything is fine. When it manages 500+, everything breaks — terraform plan takes 12 minutes, state files are 40MB, one bad merge can destroy production resources, and nobody understands the module hierarchy anymore. I've managed Terraform at this scale across 3 AWS accounts with 800+ resources. Here's what I learned.

The Module Structure That Scales

The single biggest mistake teams make is putting everything in one state file. The second biggest is creating too many tiny modules. You need a middle ground: split by blast radius and team ownership.

infrastructure/
├── modules/                    # Reusable building blocks
│   ├── vpc/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   ├── outputs.tf
│   │   └── README.md
│   ├── eks-cluster/
│   ├── rds/
│   ├── s3-bucket/
│   └── iam-role/
├── environments/
│   ├── dev/
│   │   ├── networking/         # VPC, subnets, NAT gateways
│   │   │   ├── main.tf
│   │   │   ├── backend.tf      # Separate state file
│   │   │   └── terraform.tfvars
│   │   ├── compute/            # EKS, node groups, ASGs
│   │   │   ├── main.tf
│   │   │   ├── backend.tf
│   │   │   └── terraform.tfvars
│   │   ├── data/               # RDS, ElastiCache, S3
│   │   └── security/           # IAM, KMS, WAF
│   ├── staging/
│   │   └── ... (same structure)
│   └── production/
│       └── ... (same structure)
└── global/                     # Shared across environments
    ├── iam/
    ├── route53/
    └── ecr/

Each directory under an environment has its own state file. This gives you:

  • Blast radius isolation: A bad networking change can't accidentally destroy your database
  • Faster plans: Planning 50 resources takes 30 seconds, not 12 minutes
  • Team ownership: The platform team owns networking, the app team owns compute
  • Independent deploys: Teams don't block each other with state locks

Remote State with S3 + DynamoDB Locking

If you're using local state files, stop reading and fix that first. Remote state with locking is non-negotiable for any team larger than one person.

# backend.tf — every stack gets one
terraform {
  backend "s3" {
    bucket         = "myorg-terraform-state"
    key            = "production/networking/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-state-lock"
    # Enable state file versioning on the S3 bucket!
  }
}
# Bootstrap: Create the state bucket and lock table
# (Do this once, manually or with a separate bootstrap stack)

resource "aws_s3_bucket" "terraform_state" {
  bucket = "myorg-terraform-state"
}

resource "aws_s3_bucket_versioning" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id
  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "aws:kms"
    }
  }
}

resource "aws_dynamodb_table" "terraform_lock" {
  name         = "terraform-state-lock"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"

  attribute {
    name = "LockID"
    type = "S"
  }
}
Enable Versioning on Your State Bucket

S3 versioning is your last line of defense against state corruption. When (not if) someone runs terraform apply with the wrong variables and corrupts the state, you can restore a previous version. I've done this twice in production. Both times, versioning saved us from a multi-hour recovery.

Workspaces vs Separate State Files

Terraform workspaces let you use the same code with different state files. Sounds great in theory. In practice, I've seen it cause more problems than it solves.

Approach Pros Cons Use When
Workspaces DRY code, single source of truth Easy to apply to wrong workspace, all envs share code changes, hard to have env-specific resources Identical environments (e.g., ephemeral review apps)
Separate dirs Clear isolation, env-specific configs, independent deploys Code duplication, drift between environments Production workloads where envs differ
Terragrunt DRY + isolation, generates backend configs, dependency management Extra tool to learn, adds complexity Large orgs with many environments and stacks

My recommendation: use separate directories with shared modules for production workloads. Use Terragrunt if you have more than 3 environments or 10+ stacks.

Terragrunt for DRY Configs

Terragrunt wraps Terraform and eliminates the duplication problem. Instead of copying backend.tf and provider.tf into every directory, you define them once:

# terragrunt.hcl (root)
remote_state {
  backend = "s3"
  generate = {
    path      = "backend.tf"
    if_exists = "overwrite_terragrunt"
  }
  config = {
    bucket         = "myorg-terraform-state"
    key            = "${path_relative_to_include()}/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-state-lock"
  }
}

generate "provider" {
  path      = "provider.tf"
  if_exists = "overwrite_terragrunt"
  contents  = <<EOF
provider "aws" {
  region = "us-east-1"
  default_tags {
    tags = {
      ManagedBy   = "terraform"
      Environment = "${basename(get_terragrunt_dir())}"
    }
  }
}
EOF
}
# environments/production/networking/terragrunt.hcl
include "root" {
  path = find_in_parent_folders()
}

terraform {
  source = "../../../modules/vpc"
}

inputs = {
  vpc_cidr           = "10.0.0.0/16"
  availability_zones = ["us-east-1a", "us-east-1b", "us-east-1c"]
  environment        = "production"
}

Now terragrunt run-all plan from the production directory plans all stacks in dependency order. terragrunt run-all apply applies them. The state key is automatically derived from the directory path.

CI/CD Pipeline for Terraform

The golden rule: plan on PR, apply on merge. Nobody should run terraform apply from their laptop against production.

GitHub Actions Pipeline

name: Terraform
on:
  pull_request:
    paths: ['infrastructure/**']
  push:
    branches: [main]
    paths: ['infrastructure/**']

jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      stacks: ${{ steps.changes.outputs.stacks }}
    steps:
    - uses: actions/checkout@v4
    - id: changes
      run: |
        # Detect which stacks changed
        CHANGED=$(git diff --name-only ${{ github.event.before }} HEAD \
          | grep '^infrastructure/environments/' \
          | cut -d'/' -f1-4 | sort -u | jq -R -s -c 'split("\n")[:-1]')
        echo "stacks=$CHANGED" >> $GITHUB_OUTPUT

  plan:
    needs: detect-changes
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    strategy:
      matrix:
        stack: ${{ fromJson(needs.detect-changes.outputs.stacks) }}
    steps:
    - uses: actions/checkout@v4
    - uses: hashicorp/setup-terraform@v3
      with:
        terraform_version: 1.7.0
    - name: Terraform Plan
      working-directory: ${{ matrix.stack }}
      run: |
        terraform init -input=false
        terraform plan -input=false -no-color -out=tfplan
    - name: Comment Plan on PR
      uses: actions/github-script@v7
      with:
        script: |
          // Post plan output as PR comment
          // (truncated for brevity)

  apply:
    needs: detect-changes
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production  # Requires approval
    strategy:
      matrix:
        stack: ${{ fromJson(needs.detect-changes.outputs.stacks) }}
      max-parallel: 1  # Apply one stack at a time
    steps:
    - uses: actions/checkout@v4
    - uses: hashicorp/setup-terraform@v3
      with:
        terraform_version: 1.7.0
    - name: Terraform Apply
      working-directory: ${{ matrix.stack }}
      run: |
        terraform init -input=false
        terraform apply -input=false -auto-approve
Atlantis vs GitHub Actions

Atlantis is purpose-built for Terraform CI/CD and handles plan/apply workflows, locking, and PR comments out of the box. GitHub Actions gives you more flexibility but requires more setup. For teams with <5 stacks, GitHub Actions is fine. For 10+ stacks with multiple teams, Atlantis pays for itself in reduced configuration and better locking semantics.

Importing Existing Resources

When you inherit infrastructure that was created manually (ClickOps), you need to import it into Terraform state without recreating it.

# Step 1: Write the resource block
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  enable_dns_support   = true

  tags = {
    Name = "production-vpc"
  }
}

# Step 2: Import into state
terraform import aws_vpc.main vpc-0abc123def456

# Step 3: Run plan — fix any drift
terraform plan
# You'll likely see tag changes or minor attribute differences.
# Update your .tf file to match reality, then plan again until clean.

For Terraform 1.5+, use import blocks for a declarative approach:

import {
  to = aws_vpc.main
  id = "vpc-0abc123def456"
}

# Then run: terraform plan -generate-config-out=generated.tf
# This generates the resource block for you

State Surgery: mv, rm, and When You Need Them

State surgery is dangerous but sometimes necessary. Common scenarios:

Renaming a Resource

# You renamed aws_instance.web to aws_instance.api in code
# Without state mv, Terraform will destroy web and create api
terraform state mv aws_instance.web aws_instance.api

Moving a Resource to a Module

# You refactored aws_s3_bucket.logs into module.storage
terraform state mv aws_s3_bucket.logs module.storage.aws_s3_bucket.logs

Removing a Resource from State (Without Destroying It)

# You want Terraform to stop managing this resource
# but don't want to delete it from AWS
terraform state rm aws_iam_role.legacy_role
Incident: State File Corruption and Recovery

In 2023, a CI pipeline ran two terraform apply commands concurrently against the same state (the DynamoDB lock had been accidentally removed during a "cleanup"). The state file ended up with duplicate resource entries and orphaned references. Plan showed 47 resources to destroy.

Recovery steps:

  1. Immediately locked the state: terraform force-unlock then manual DynamoDB lock
  2. Downloaded the corrupted state: terraform state pull > corrupted.tfstate
  3. Restored previous version from S3 versioning (thank god we had it enabled)
  4. Compared the two states to identify the 3 resources that were actually created by the concurrent apply
  5. Imported those 3 resources into the restored state
  6. Ran terraform plan — clean, no changes
  7. Re-enabled DynamoDB locking and added a CI check to prevent concurrent runs

Total recovery time: 2 hours. Without S3 versioning, it would have been a full day of manual state reconstruction.

The Cost of Plan Time at Scale

Every terraform plan makes API calls to your cloud provider to check the current state of every resource. At 500+ resources in a single state file, this takes 8-15 minutes. That's 8-15 minutes per PR, per push, per developer.

12 min
Average plan time with 500 resources in one state file
45 sec
Average plan time after splitting into 10 stacks of ~50 resources
$2,400/mo
Estimated developer time wasted waiting for plans (team of 8, 5 plans/day each)
87%
Reduction in CI pipeline time after state splitting

Additional techniques to speed up plans:

  • Target specific resources: terraform plan -target=module.networking during development (never in CI)
  • Parallelism tuning: terraform plan -parallelism=20 (default is 10)
  • Provider caching: Use plugin_cache_dir to avoid re-downloading providers
  • State file size: Remove unused data sources and outputs that force unnecessary API calls

Terraform Best Practices at Scale

  • Pin provider versions exactly: version = "= 5.31.0", not "~> 5.0"
  • Pin Terraform version in required_version and in CI
  • Use .terraform.lock.hcl and commit it to version control
  • Tag every resource with ManagedBy = "terraform" and Environment
  • Never use count for resources that might be reordered — use for_each with stable keys
  • Keep modules small and focused — one module per logical component
  • Document every module with a README and example usage
  • Run terraform fmt and terraform validate in CI as a pre-check
  • Use tflint and checkov for linting and security scanning
  • Never store secrets in .tfvars — use AWS Secrets Manager or SSM Parameter Store with data sources

Key Takeaways

Terraform at scale is a state management problem, not a code problem. Split your state files by blast radius and team ownership. Use remote state with locking and versioning — no exceptions. Automate plan and apply through CI/CD so nobody runs Terraform from their laptop. And enable S3 versioning on your state bucket before you need it, because you will need it. The investment in structure pays off exponentially as your infrastructure grows.
