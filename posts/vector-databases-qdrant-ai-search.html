Introduction: Why Our Elasticsearch Search Was Failing

Our e-commerce platform had 2.3 million products and an Elasticsearch cluster that handled keyword search well enough — until customers started searching the way they actually think. "Comfortable shoes for standing all day" returned zero results because no product had that exact phrase. "Something like an AirPod but cheaper" returned AirPod cases. "Gift for a 10-year-old who likes science" returned nothing useful.

The problem isn't Elasticsearch. It's that keyword search matches words, not meaning. A customer searching for "laptop for video editing" needs results that include "MacBook Pro M3" and "Dell XPS with RTX 4070" — even though those product titles share zero keywords with the query.

Vector search solves this by converting both queries and products into numerical representations (embeddings) that capture semantic meaning, then finding the closest matches in that mathematical space. We chose Qdrant as our vector database after evaluating Pinecone, Weaviate, and Milvus. This post covers the full production journey: architecture, indexing pipeline, query flow, scaling to 2.3M vectors, and the mistakes that cost us 3 days of degraded search.

How Embeddings Work (The 60-Second Version)

Skip this if you already know embeddings. For everyone else: an embedding model converts text into a list of numbers (a vector) where similar meanings produce similar numbers.

// "Running shoes for marathon training" → [0.23, -0.87, 0.45, ..., 0.12]  (1536 numbers)
// "Marathon running footwear"           → [0.21, -0.85, 0.44, ..., 0.11]  (very similar!)
// "Kitchen blender 600W"               → [-0.67, 0.34, -0.12, ..., 0.89] (very different)

The distance between two vectors tells you how semantically similar they are. "Running shoes for marathon training" and "Marathon running footwear" will be close together in vector space. "Kitchen blender" will be far away. That's the entire concept. The embedding model (we use OpenAI's text-embedding-3-small) handles the conversion; the vector database handles storing and searching billions of these vectors efficiently.

Component Breakdown

Indexing Path (Async)

  • Debezium captures product changes from PostgreSQL
  • Events published to SQS
  • Lambda generates embeddings via OpenAI API
  • Lambda upserts vectors + payload into Qdrant
  • Latency: 2-5 seconds from DB change to searchable

Query Path (Sync)

  • User query → Search API
  • API generates query embedding (OpenAI, ~80ms)
  • Parallel: Qdrant vector search + Elasticsearch keyword search
  • Results merged with reciprocal rank fusion
  • Total latency: ~120ms end-to-end

The Indexing Pipeline: Getting 2.3M Products Into Qdrant

Step 1: Create the Collection

import { QdrantClient } from "@qdrant/js-client-rest";

const qdrant = new QdrantClient({ url: process.env.QDRANT_URL, apiKey: process.env.QDRANT_API_KEY });

await qdrant.createCollection("products", {
  vectors: {
    size: 1536,           // text-embedding-3-small dimension
    distance: "Cosine",   // Cosine similarity for normalized embeddings
  },
  optimizers_config: {
    indexing_threshold: 20000,  // Build HNSW index after 20K vectors
  },
  on_disk_payload: true,  // Keep payloads on disk to save RAM for vectors
});

Step 2: Generate Embeddings and Upsert

import OpenAI from "openai";

const openai = new OpenAI();

async function indexProduct(product) {
  // Build the text to embed — this is the most important decision
  const textToEmbed = [
    product.name,
    product.category,
    product.brand,
    product.description?.slice(0, 500),  // Truncate long descriptions
    product.tags?.join(", "),
  ].filter(Boolean).join(". ");

  const embedding = await openai.embeddings.create({
    model: "text-embedding-3-small",
    input: textToEmbed,
  });

  await qdrant.upsert("products", {
    points: [{
      id: product.id,
      vector: embedding.data[0].embedding,
      payload: {
        name: product.name,
        category: product.category,
        brand: product.brand,
        price: product.price,
        in_stock: product.inStock,
        rating: product.avgRating,
        image_url: product.imageUrl,
        updated_at: new Date().toISOString(),
      },
    }],
  });
}
What Text to Embed Matters More Than Which Model

We spent 2 weeks A/B testing embedding models (text-embedding-3-small vs text-embedding-3-large vs Cohere embed-v3). The difference was marginal (~2% relevance improvement for 6x the cost). Then we spent 1 day improving the text we embed — adding category, brand, and tags to the product name — and relevance jumped 18%. Optimize your input text before upgrading your model.

Step 3: Bulk Indexing for Initial Load

// Bulk indexing 2.3M products — batched to avoid rate limits
async function bulkIndex(products) {
  const BATCH_SIZE = 100;       // OpenAI embedding batch limit
  const CONCURRENCY = 5;        // Parallel batches
  const QDRANT_BATCH = 500;     // Qdrant upsert batch size

  let vectorBuffer = [];
  let processed = 0;

  for (let i = 0; i < products.length; i += BATCH_SIZE * CONCURRENCY) {
    const chunk = products.slice(i, i + BATCH_SIZE * CONCURRENCY);
    const batches = [];

    for (let j = 0; j < chunk.length; j += BATCH_SIZE) {
      batches.push(chunk.slice(j, j + BATCH_SIZE));
    }

    // Parallel embedding calls
    const results = await Promise.all(
      batches.map((batch) =>
        openai.embeddings.create({
          model: "text-embedding-3-small",
          input: batch.map((p) => buildEmbeddingText(p)),
        })
      )
    );

    // Collect points
    for (let b = 0; b < results.length; b++) {
      for (let k = 0; k < results[b].data.length; k++) {
        const product = batches[b][k];
        vectorBuffer.push({
          id: product.id,
          vector: results[b].data[k].embedding,
          payload: buildPayload(product),
        });
      }
    }

    // Flush to Qdrant in larger batches
    while (vectorBuffer.length >= QDRANT_BATCH) {
      const batch = vectorBuffer.splice(0, QDRANT_BATCH);
      await qdrant.upsert("products", { points: batch });
      processed += batch.length;
      console.log(`Indexed ${processed}/${products.length}`);
    }
  }

  // Flush remaining
  if (vectorBuffer.length > 0) {
    await qdrant.upsert("products", { points: vectorBuffer });
  }
}

// Full index: ~45 minutes for 2.3M products at 5 concurrent batches

The Query Flow: From User Input to Results

Basic Semantic Search

async function semanticSearch(query, filters = {}, limit = 20) {
  // Generate query embedding
  const embedding = await openai.embeddings.create({
    model: "text-embedding-3-small",
    input: query,
  });

  // Build Qdrant filter from user-facing filters
  const must = [];
  if (filters.category) {
    must.push({ key: "category", match: { value: filters.category } });
  }
  if (filters.minPrice || filters.maxPrice) {
    must.push({
      key: "price",
      range: {
        gte: filters.minPrice || 0,
        lte: filters.maxPrice || 999999,
      },
    });
  }
  if (filters.inStockOnly) {
    must.push({ key: "in_stock", match: { value: true } });
  }

  const results = await qdrant.search("products", {
    vector: embedding.data[0].embedding,
    limit,
    filter: must.length > 0 ? { must } : undefined,
    with_payload: true,
    score_threshold: 0.35,  // Minimum relevance — below this, results are noise
  });

  return results.map((r) => ({
    id: r.id,
    score: r.score,
    ...r.payload,
  }));
}

Hybrid Search: Vectors + Keywords

Pure vector search misses exact matches. If a customer searches for "SKU-12345" or "Nike Air Max 90", keyword search is better. We run both in parallel and merge results:

async function hybridSearch(query, filters, limit = 20) {
  // Run vector and keyword search in parallel
  const [vectorResults, keywordResults] = await Promise.all([
    semanticSearch(query, filters, limit),
    elasticsearchSearch(query, filters, limit),
  ]);

  // Reciprocal Rank Fusion — merges two ranked lists
  const scores = new Map();
  const K = 60; // RRF constant

  vectorResults.forEach((r, i) => {
    const rrf = 1 / (K + i + 1);
    scores.set(r.id, (scores.get(r.id) || 0) + rrf * 0.6); // 60% weight to vectors
  });

  keywordResults.forEach((r, i) => {
    const rrf = 1 / (K + i + 1);
    scores.set(r.id, (scores.get(r.id) || 0) + rrf * 0.4); // 40% weight to keywords
  });

  // Sort by combined score, return top N
  const merged = [...scores.entries()]
    .sort((a, b) => b[1] - a[1])
    .slice(0, limit);

  // Hydrate with full product data
  return hydrateProducts(merged.map(([id]) => id));
}
Why 60/40 and Not 50/50?

We A/B tested ratios from 30/70 to 80/20. The 60% vector / 40% keyword split won because: (1) most searches are natural language where vectors excel, (2) exact-match searches like brand names and SKUs still need keyword coverage, and (3) going above 70% vector caused "Nike Air Max" to return competing brands that are semantically similar but not what the customer wanted.

Use Case 2: FAQ / Support Bot

We index 1,200 FAQ articles and support docs. When a customer asks a question, we find the most relevant articles and feed them to an LLM as context (RAG pattern).

async function answerQuestion(question) {
  // Find relevant FAQ articles
  const articles = await semanticSearch(question, {}, 5);

  if (articles.length === 0 || articles[0].score < 0.4) {
    return { answer: null, escalate: true }; // No good match — route to human
  }

  // Use top articles as context for LLM
  const context = articles
    .map((a) => `## ${a.title}\n${a.content}`)
    .join("\n\n");

  const response = await anthropic.messages.create({
    model: "claude-sonnet-4-20250514",
    max_tokens: 300,
    messages: [{
      role: "user",
      content: `Answer this customer question using ONLY the provided context. If the context doesn't contain the answer, say "I don't have information about that."

Context:
${context}

Question: ${question}`,
    }],
  });

  return {
    answer: response.content[0].text,
    sources: articles.slice(0, 3).map((a) => ({ id: a.id, title: a.title, score: a.score })),
    escalate: false,
  };
}

Use Case 3: "Similar Products" Recommendations

The simplest and highest-ROI use case. Given a product the customer is viewing, find the most similar products. No ML pipeline needed — just query Qdrant with the product's existing vector.

async function getSimilarProducts(productId, limit = 8) {
  // Use the product's own vector to find neighbors
  const results = await qdrant.search("products", {
    vector_name: undefined, // default vector
    // Search by existing point ID — no embedding call needed
    ...(await getPointVector(productId)),
    limit: limit + 1, // +1 because the product itself will be the top result
    filter: {
      must: [{ key: "in_stock", match: { value: true } }],
      must_not: [{ has_id: [productId] }], // Exclude the product itself
    },
    with_payload: true,
  });

  return results;
}

// Alternative: use Qdrant's recommend API for better results
async function getRecommendations(productId, limit = 8) {
  return qdrant.recommend("products", {
    positive: [productId],   // "More like this"
    negative: [],            // Could add products the user dismissed
    limit,
    filter: { must: [{ key: "in_stock", match: { value: true } }] },
    with_payload: true,
  });
}

Scaling Challenges: What Broke at 2M+ Vectors

Challenge 1: Memory — Vectors Eat RAM

Each 1536-dimension float32 vector is 6KB. At 2.3 million vectors, that's ~14GB just for vectors, plus the HNSW index (~20GB), plus payloads. Our initial single-node Qdrant with 16GB RAM OOMed at 800K vectors.

The OOM That Took Down Search for 3 Hours

We hit 800K vectors on a 16GB node. Qdrant OOMed during HNSW index optimization, the pod restarted, tried to rebuild the index on startup, OOMed again — crash loop. We had to scale the node to 32GB, wait for recovery, then migrate to a 3-node cluster. Lesson: capacity plan for 2x your expected vector count from day one.

Challenge 2: Embedding API Latency in the Query Path

Every search query needs an embedding before Qdrant can search. The OpenAI embedding API adds 60-120ms to every query. At P99, it's 250ms. For a search bar with autocomplete, that's too slow.

Fix: Query embedding cache. We cache query embeddings in Redis with a 1-hour TTL. Popular queries ("nike shoes", "iphone case", "laptop") get cache hits 70% of the time.

import { createHash } from "crypto";

async function getQueryEmbedding(query) {
  const normalized = query.toLowerCase().trim();
  const cacheKey = `emb:${createHash("sha256").update(normalized).digest("hex").slice(0, 16)}`;

  const cached = await redis.get(cacheKey);
  if (cached) return JSON.parse(cached);

  const result = await openai.embeddings.create({
    model: "text-embedding-3-small",
    input: normalized,
  });

  const vector = result.data[0].embedding;
  await redis.setex(cacheKey, 3600, JSON.stringify(vector)); // 1 hour TTL
  return vector;
}

Challenge 3: Keeping Vectors in Sync with the Catalog

Products change constantly — prices update, items go out of stock, descriptions get edited. The vector in Qdrant must reflect the current state. We use Debezium CDC to capture every change:

// SQS consumer for Debezium CDC events
async function handleProductChange(event) {
  const { op, after, before } = event;

  if (op === "d") {
    // Product deleted — remove from Qdrant
    await qdrant.delete("products", { points: [before.id] });
    return;
  }

  if (op === "c" || op === "u") {
    const product = after;

    // Only re-embed if text fields changed (not just price/stock)
    const textChanged =
      op === "c" ||
      before.name !== after.name ||
      before.description !== after.description ||
      before.category !== after.category;

    if (textChanged) {
      // Full re-index: new embedding + new payload
      await indexProduct(product);
    } else {
      // Payload-only update: just update price/stock/rating (no embedding call)
      await qdrant.setPayload("products", {
        points: [product.id],
        payload: {
          price: product.price,
          in_stock: product.inStock,
          rating: product.avgRating,
          updated_at: new Date().toISOString(),
        },
      });
    }
  }
}
Payload-Only Updates Save 90% of Embedding Costs

Most product changes are price and stock updates, not description changes. By separating payload updates (free, instant) from vector updates (requires embedding API call), we reduced our daily embedding API calls from ~150K to ~15K. That's ~$40/month saved on embeddings alone.

Cost Optimization Levers

What Saved Us Money

  • text-embedding-3-small over 3-large: 6x cheaper, 2% relevance difference
  • Query embedding cache: 70% hit rate = 70% fewer API calls
  • Payload-only updates: 90% of product changes don't need re-embedding
  • on_disk_payload: true: Keeps payloads on SSD, saves ~8GB RAM per node
  • Quantization: Scalar quantization reduces memory 4x with ~2% recall loss

Where We Didn't Cut Corners

  • 3-node cluster: Replication factor 2 for availability
  • r6g.xlarge (32GB): Enough RAM for vectors + HNSW in memory
  • gp3 storage: WAL writes need consistent IOPS
  • No quantization on FAQ collection: 1,200 vectors — memory savings negligible, recall matters

Quantization: The Biggest Cost Lever

If you're hitting memory limits, scalar quantization is the first thing to try. It converts float32 vectors to uint8, reducing memory by 4x with minimal recall loss:

// Enable scalar quantization on existing collection
await qdrant.updateCollection("products", {
  quantization_config: {
    scalar: {
      type: "int8",
      quantile: 0.99,      // Clip outliers
      always_ram: true,     // Keep quantized vectors in RAM, full vectors on disk
    },
  },
});

// Search with oversampling to compensate for quantization
const results = await qdrant.search("products", {
  vector: queryVector,
  limit: 20,
  params: {
    quantization: {
      rescore: true,       // Re-score top results with full vectors
      oversampling: 2.0,   // Fetch 2x candidates, then re-rank
    },
  },
});

Common Mistakes (We Made All of Them)

❌ Mistake 1: Embedding Only the Product Name

Our first version embedded just the product title: "Nike Air Max 90 Men's Running Shoe." The vector captured "Nike shoe" but missed that it's cushioned, good for daily training, and available in 12 colors. Adding category, brand, key features, and a truncated description to the embedding text improved relevance by 18%.

Fix: Embed a rich text representation: name + category + brand + features + description[:500]

❌ Mistake 2: No Score Threshold

Without a minimum score threshold, Qdrant always returns results — even if they're irrelevant. A search for "quantum physics textbook" on our e-commerce site returned kitchen appliances (the least-bad match in a catalog with no textbooks). Users saw garbage results and lost trust in search.

Fix: Set score_threshold: 0.35 for cosine similarity. Below that, show "No results found" with suggestions instead of irrelevant products.

❌ Mistake 3: Not Monitoring Embedding Drift

OpenAI updated their embedding model in January 2026. Our indexed vectors were from the old model. New query embeddings from the updated model were in a slightly different vector space. Search relevance degraded by ~12% over 2 weeks before we noticed.

Fix: Pin the model version (text-embedding-3-small is versioned). Monitor search relevance with a weekly eval set of 200 query-result pairs. If relevance drops below threshold, trigger a full re-index.

❌ Mistake 4: Filtering After Search Instead of During

Our first implementation searched Qdrant for 100 results, then filtered by category and price in the application layer. This meant if only 3 of the top 100 results matched the filter, the user saw 3 results. Qdrant supports filtering during search — it only considers vectors that match the filter, so you always get the requested number of results.

Fix: Always use Qdrant's built-in filter parameter. It uses payload indexes for fast filtering without scanning all vectors.

❌ Mistake 5: Single-Node Qdrant in Production

We ran a single Qdrant pod for 4 months. When it OOMed during HNSW optimization, search was down for 3 hours. There was no replica to fail over to. The pod restarted, tried to rebuild the index, and OOMed again in a crash loop.

Fix: Minimum 3 nodes with replication factor 2 for any production workload. Use a PodDisruptionBudget to prevent Kubernetes from evicting more than 1 node at a time.

Best Practices

  1. Invest in what you embed, not which model you use. The text you convert to vectors matters 10x more than the embedding model. Add category, brand, features, and tags to your embedding text.
  2. Use hybrid search (vectors + keywords). Pure vector search misses exact matches. Pure keyword search misses semantic matches. Combine them with reciprocal rank fusion.
  3. Set a score threshold. Irrelevant results are worse than no results. 0.35 cosine similarity is a good starting point — tune it with your eval set.
  4. Filter during search, not after. Use Qdrant's payload filtering. Create payload indexes on fields you filter frequently (category, price, in_stock).
  5. Cache query embeddings. Popular queries repeat constantly. A Redis cache with 1-hour TTL eliminates 70% of embedding API calls.
  6. Separate payload updates from vector updates. Price and stock changes don't need re-embedding. Use setPayload for metadata-only updates.
  7. Plan for 2x your expected vector count. HNSW index optimization needs headroom. OOMing during optimization is a crash loop you don't want.
  8. Monitor embedding drift. Pin your model version. Run a weekly relevance eval. If the model changes, re-index everything.
  9. Start with scalar quantization if memory is tight. 4x memory reduction with <1% recall loss. Enable rescore for accuracy.
  10. Run at least 3 nodes with replication factor 2. Single-node Qdrant in production is a ticking time bomb.

Conclusion

Vector search isn't a replacement for keyword search — it's the missing layer that makes search understand intent. Our customers don't search in keywords. They search in thoughts: "something warm for winter hiking" or "gift for a teenager who likes cooking." Vector databases make that work.

After 8 months in production, Qdrant handles 2.3 million product vectors with 23ms P95 query latency at $680/month. The hybrid search (Qdrant + Elasticsearch) improved search conversion by 34%. The FAQ bot deflects 40% of support tickets. The "similar products" recommendations increased average order value by 12%.

The technology is mature enough for production. The hard parts aren't the vector database itself — they're the surrounding infrastructure: keeping vectors in sync with your source of truth, managing embedding API costs, monitoring relevance drift, and capacity planning for memory. Get those right, and vector search is one of the highest-ROI infrastructure investments you can make.

The best search doesn't match words — it understands what the customer actually wants. Vector databases are how you build that understanding into your product, at scale, without a PhD in machine learning.
