Two Years with Cluster Autoscaler, Then We Switched

We ran Cluster Autoscaler (CA) on our production EKS clusters for 2 years. It worked. Pods got scheduled, nodes scaled up, costs were manageable. But as we grew from 40 to 180 microservices, the cracks became impossible to ignore: slow scale-up times during traffic spikes, wasted capacity from rigid node group definitions, and a Terraform codebase with 12 different ASG configurations that nobody wanted to touch.

We migrated to Karpenter over 6 weeks. Here's the honest comparison.

How Cluster Autoscaler Works

CA watches for pods that can't be scheduled (Pending state), then increases the desired count of an Auto Scaling Group (ASG). The fundamental constraint: you pre-define node groups with fixed instance types.

Pod enters Pending state (no node has capacity)
CA detects unschedulable pod
CA evaluates which ASG/node group can fit the pod
CA increases ASG desired count
ASG launches EC2 instance (from pre-defined types)
Node joins cluster → pod gets scheduled

The problem: CA can only choose from instance types you've pre-configured in each node group. If you defined m5.xlarge and m5.2xlarge, that's all it can launch — even if m6i.xlarge is 15% cheaper and available in your AZ.

How Karpenter Works

Karpenter bypasses ASGs entirely. It calls the EC2 API directly, evaluating pod requirements in real time and selecting the optimal instance type from a broad pool.

Pod enters Pending state
Karpenter evaluates pod's resource requests, nodeSelector, tolerations, topology spread
Karpenter queries EC2 for available instance types + spot pricing
Karpenter selects optimal instance (right-sized, cheapest available)
Karpenter launches EC2 instance directly (no ASG)
Node joins cluster → pod gets scheduled

kind: NodePool
metadata:
  name: general-workloads
spec:
  template:
    metadata:
      labels:
        workload-type: general
    spec:
      requirements:
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64"]
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["m", "c", "r"]
        - key: karpenter.k8s.aws/instance-generation
          operator: Gt
          values: ["4"]
        - key: karpenter.k8s.aws/instance-size
          operator: In
          values: ["large", "xlarge", "2xlarge"]
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 60s
    budgets:
      - nodes: "20%"
  limits:
    cpu: "200"
    memory: "400Gi"
  weight: 50

Consolidation: The Killer Feature

Karpenter's consolidation policy automatically replaces underutilized nodes with smaller, cheaper ones. CA's scale-down is conservative — it only removes empty nodes or nodes where all pods can be rescheduled. Karpenter actively bin-packs.

💡 Real Example

After a traffic spike, we had 8 x m5.2xlarge nodes running at 30% utilization. Karpenter consolidated them into 3 x m6i.xlarge nodes within 10 minutes, saving $0.85/hour. Over a month of daily traffic patterns, consolidation alone saved us ~$400/month.

Spot Instance Diversification

This is where Karpenter truly shines. CA is limited to the instance types in your ASG launch template. Karpenter evaluates 15+ instance types across multiple families and picks the cheapest available spot instance.

Migration Strategy: Running Both

We didn't do a big-bang migration. Here's our 6-week plan:

Week 1-2: Install Karpenter alongside CA

Deployed Karpenter with a NodePool targeting only non-critical workloads (dev, staging). CA continued managing production node groups. Both coexisted without conflict.

Week 3-4: Migrate batch and CI workloads

Moved CI runners and batch jobs to Karpenter-managed nodes. Validated spot interruption handling and consolidation behavior. Removed 4 ASG definitions.

Week 5: Migrate production workloads

Added production NodePool with tighter constraints (on-demand for critical services, spot for stateless). Drained CA-managed nodes gradually.

Week 6: Decommission CA

Removed CA deployment, deleted remaining ASGs, cleaned up Terraform. Final validation: all workloads running on Karpenter-managed nodes.

Gotchas We Hit

1. Consolidation Too Aggressive

⚠️ Watch Out

Default consolidation was moving pods every few minutes during variable traffic. Services with long startup times (Java apps, 45-second boot) experienced brief availability dips during consolidation. Fix: set consolidateAfter: 300s for production NodePools and use disruption budgets of nodes: "10%".

2. IRSA Permissions Setup

Karpenter needs broad EC2 permissions — ec2:RunInstances, ec2:CreateFleet, ec2:TerminateInstances, iam:PassRole, and more. The IAM policy is ~40 actions. We missed ec2:CreateTags initially, which caused silent failures where nodes launched but weren't tagged for cost allocation.

3. Monitoring Gaps

CA has well-known Prometheus metrics. Karpenter's metrics are different. We built custom Grafana dashboards tracking:

  • karpenter_nodes_created — node launch rate
  • karpenter_nodes_terminated — consolidation/interruption rate
  • karpenter_pods_startup_duration_seconds — scheduling latency
  • karpenter_nodeclaims_disrupted — disruption events

When to Stick with Cluster Autoscaler

Karpenter isn't always the right choice. Stick with CA if:

  • 🔒 You need strict instance type control (compliance requirements)
  • 📋 Your org mandates ASG-based scaling for audit trails
  • 🏗️ You're running EKS on Outposts (Karpenter doesn't support it)
  • 👥 Your team is small and CA is working fine — migration has a cost
✅ Bottom Line

If you're running 50+ nodes and spending more than $5,000/month on EKS compute, Karpenter will likely save you 15-25% through better bin packing and spot diversification. The migration is straightforward if you run both side-by-side. The scale-up speed improvement alone justified the switch for us — 45 seconds vs nearly 3 minutes means fewer timeout errors during traffic spikes.
