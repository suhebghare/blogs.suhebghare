Introduction: From Chatbots to Autonomous Agents

A year ago, I wrote about building an AI agent for infrastructure using LangChain and GPT-4. That agent was essentially a chatbot with kubectl access — you asked a question, it ran some commands, and gave you an answer. Useful, but limited.

What we're building now is fundamentally different. MCP-based infrastructure agents don't just answer questions — they execute multi-step remediation workflows. They detect a pod in CrashLoopBackOff, correlate it with a recent deployment, check if the rollback is safe, request human approval, execute the rollback, verify the fix, and update the incident channel. All through a standardized protocol that works across any combination of tools.

The difference between a diagnostic chatbot and an automation agent is the action loop. This post covers how we built that loop, the guardrails that keep it from destroying production, and the observability stack that lets us trust it.

Diagnostic Agent (v1)

  • Human asks a question
  • Agent reads data from tools
  • Agent returns an answer
  • Human decides what to do
  • Human executes the fix

Automation Agent (v2 — MCP)

  • Trigger: alert, schedule, or human request
  • Agent reads data across multiple MCP servers
  • Agent proposes a remediation plan
  • Human approves (or auto-approved for safe actions)
  • Agent executes, verifies, and reports

Why MCP Changes the Agent Architecture

Our v1 agent used LangChain tools — Python functions wrapping subprocess calls to kubectl and curl requests to Prometheus. It worked, but had three problems that MCP solves:

Problem LangChain v1 MCP v2
Tool discovery Hardcoded in Python. Adding a tool = code change + redeploy. Dynamic. Agent discovers available tools at runtime from MCP servers.
Credential management Kubeconfig and AWS keys baked into the agent's environment. Each MCP server manages its own credentials. Agent never sees them.
Multi-cluster One agent per cluster. Separate deployments for prod/staging. One agent, multiple MCP servers. Route by environment parameter.

The architectural shift: the agent becomes a pure reasoning engine. It doesn't know how to talk to Kubernetes or AWS. It knows how to reason about problems and call tools. The MCP servers handle all the infrastructure interaction.

Trigger (PagerDuty Alert / Slack Command / Cron Schedule)
Agent Controller (manages the reasoning loop)
LLM (Claude / GPT-4 — decides which tools to call)
MCP Client (routes tool calls to the right MCP server)
MCP Servers: K8s-prod | K8s-staging | AWS | Prometheus | GitHub | PagerDuty | Slack
Infrastructure (EKS clusters, AWS APIs, monitoring, CI/CD)

The Agent Loop: How It Actually Works

The core of the agent is a loop that alternates between LLM reasoning and MCP tool execution. Here's the production implementation:

import anthropic
from mcp import ClientSession
from mcp.client.stdio import stdio_client
import json, asyncio

class InfraAgent:
    def __init__(self, mcp_servers: dict[str, str]):
        self.client = anthropic.Anthropic()
        self.sessions: dict[str, ClientSession] = {}
        self.server_configs = mcp_servers  # {"kubernetes": "path/to/k8s-mcp", ...}
        self.tools = []
        self.max_iterations = 10
        self.action_log = []

    async def connect_servers(self):
        """Connect to all MCP servers and discover their tools."""
        for name, cmd in self.server_configs.items():
            session = await self._connect(name, cmd)
            self.sessions[name] = session
            server_tools = await session.list_tools()
            for tool in server_tools.tools:
                self.tools.append({
                    "name": f"{name}__{tool.name}",  # namespace tools by server
                    "description": tool.description,
                    "input_schema": tool.inputSchema,
                    "_server": name,
                    "_tool": tool.name,
                })

    async def run(self, task: str, context: dict = None) -> dict:
        """Execute the agent loop for a given task."""
        messages = [{"role": "user", "content": self._build_prompt(task, context)}]

        for iteration in range(self.max_iterations):
            response = self.client.messages.create(
                model="claude-sonnet-4-20250514",
                max_tokens=4096,
                system=AGENT_SYSTEM_PROMPT,
                tools=self._format_tools_for_claude(),
                messages=messages,
            )

            # If the LLM wants to call tools
            if response.stop_reason == "tool_use":
                tool_results = []
                for block in response.content:
                    if block.type == "tool_use":
                        result = await self._execute_tool(block)
                        tool_results.append(result)

                messages.append({"role": "assistant", "content": response.content})
                messages.append({"role": "user", "content": tool_results})

            # If the LLM is done reasoning
            elif response.stop_reason == "end_turn":
                final_text = next(
                    (b.text for b in response.content if hasattr(b, "text")), ""
                )
                return {
                    "result": final_text,
                    "iterations": iteration + 1,
                    "actions": self.action_log,
                }

        return {"result": "Agent hit max iterations", "iterations": self.max_iterations}

    async def _execute_tool(self, tool_block) -> dict:
        """Route a tool call to the correct MCP server."""
        server_name, tool_name = tool_block.name.split("__", 1)
        session = self.sessions[server_name]

        # Classify the action
        action_class = classify_action(server_name, tool_name, tool_block.input)

        # If it's a write action, require approval
        if action_class == "write":
            approved = await self._request_approval(
                server_name, tool_name, tool_block.input
            )
            if not approved:
                return {"type": "tool_result", "tool_use_id": tool_block.id,
                        "content": "Action rejected by operator. Suggest alternative."}

        result = await session.call_tool(tool_name, tool_block.input)
        self.action_log.append({
            "server": server_name, "tool": tool_name,
            "input": tool_block.input, "class": action_class,
        })
        return {"type": "tool_result", "tool_use_id": tool_block.id,
                "content": result.content[0].text}

Real-World Agent Workflows

Workflow 1: Automated Pod Restart with Verification

This is the most common automation — a pod is stuck, the agent restarts it and confirms the fix. Sounds simple, but the verification step is where most naive implementations fail.

Why This Matters

A dumb automation script would have restarted the pod, watched it crash again, restarted it again, and paged the on-call engineer after 3 failed attempts. The agent diagnosed the actual root cause in 4 tool calls and escalated correctly. The difference is the reasoning loop — the agent doesn't just execute a runbook, it investigates.

The Guardrail System: Preventing Dangerous Actions

This is the section that matters most. An agent with write access to production Kubernetes is a loaded gun. Here's how we make it safe.

Action Classification

Every tool call is classified before execution. The classification determines whether it runs immediately, requires approval, or is blocked entirely.

ACTION_RULES = {
    # READ — always allowed, no approval needed
    "read": {
        "kubernetes": ["get_pods", "get_events", "get_pod_logs", "describe_deployment",
                       "get_hpa", "get_nodes", "search_logs", "get_node_capacity"],
        "prometheus": ["query", "query_range", "get_alerts"],
        "aws": ["describe_instances", "get_cost_breakdown", "describe_vpc_endpoints",
                "query_cloudtrail"],
        "pagerduty": ["get_incidents", "get_oncall"],
        "github": ["list_recent_deployments", "get_commit", "get_pr"],
    },
    # WRITE — requires human approval via Slack
    "write": {
        "kubernetes": ["restart_deployment", "scale_deployment", "patch_hpa",
                       "patch_nodepool"],
        "aws": ["modify_asg_capacity"],
        "github": ["create_issue", "trigger_workflow"],
        "pagerduty": ["acknowledge_incident", "add_note"],
        "slack": ["post_message"],
    },
    # BLOCKED — never allowed, regardless of approval
    "blocked": {
        "kubernetes": ["delete_pod", "delete_deployment", "delete_namespace",
                       "apply_manifest", "exec_into_pod"],
        "aws": ["terminate_instance", "delete_security_group", "modify_iam_role"],
    },
}

def classify_action(server: str, tool: str, args: dict) -> str:
    for classification, rules in ACTION_RULES.items():
        if server in rules and tool in rules[server]:
            return classification

    # Unknown tools are blocked by default
    return "blocked"

The Approval Workflow

Write actions trigger a Slack message to the on-call channel with a 5-minute approval window:

async def _request_approval(self, server, tool, args) -> bool:
    """Send approval request to Slack, wait for response."""
    approval_id = str(uuid.uuid4())[:8]

    # Post to Slack with action buttons
    await slack_client.post_message(
        channel=ONCALL_CHANNEL,
        blocks=[
            {"type": "header", "text": {"type": "plain_text",
                "text": f"🤖 Agent Action Requires Approval [{approval_id}]"}},
            {"type": "section", "text": {"type": "mrkdwn",
                "text": f"*Server:* {server}\n*Tool:* {tool}\n*Args:*\n```{json.dumps(args, indent=2)}```"}},
            {"type": "actions", "elements": [
                {"type": "button", "text": {"type": "plain_text", "text": "✅ Approve"},
                 "action_id": f"approve_{approval_id}", "style": "primary"},
                {"type": "button", "text": {"type": "plain_text", "text": "❌ Reject"},
                 "action_id": f"reject_{approval_id}", "style": "danger"},
            ]},
        ],
    )

    # Wait for response (max 5 minutes)
    result = await approval_store.wait(approval_id, timeout=300)
    return result == "approved"
Hard Rules We Never Bend
  • No delete operations. Ever. Not even with approval. Deleting a namespace, deployment, or pod is never an agent action. If something needs deleting, a human does it.
  • No exec into pods. Shell access is a human-only operation. The agent reads logs, it doesn't open shells.
  • No IAM modifications. The agent cannot change who has access to what. Period.
  • No manifest applies. The agent doesn't create or modify Kubernetes resources from YAML. It uses specific, scoped operations (scale, restart, patch HPA).
  • Unknown tools default to blocked. If a new MCP server exposes a tool the agent hasn't seen before, it's blocked until explicitly classified.

Blast Radius Limits

Even approved write actions have hard limits to contain mistakes:

BLAST_RADIUS_LIMITS = {
    "scale_deployment": {
        "max_replicas": 30,          # Can't scale above 30
        "min_replicas": 1,           # Can't scale to 0
        "max_change": 10,            # Can't change by more than 10 at once
    },
    "restart_deployment": {
        "max_pods_affected": 20,     # Won't restart deployments with >20 pods
        "cooldown_seconds": 300,     # 5 min between restarts of same deployment
    },
    "patch_nodepool": {
        "max_cpu_limit": 500,        # Karpenter CPU limit cap
        "max_node_count": 100,       # Absolute node ceiling
    },
    "modify_asg_capacity": {
        "max_desired": 50,           # ASG desired capacity cap
        "max_increase_pct": 100,     # Can't more than double current capacity
    },
}

def validate_blast_radius(tool: str, args: dict) -> tuple[bool, str]:
    limits = BLAST_RADIUS_LIMITS.get(tool)
    if not limits:
        return True, ""

    if tool == "scale_deployment":
        replicas = args.get("replicas", 0)
        if replicas > limits["max_replicas"]:
            return False, f"Replicas {replicas} exceeds max {limits['max_replicas']}"
        if replicas < limits["min_replicas"]:
            return False, f"Cannot scale below {limits['min_replicas']}"

    return True, ""

Observability for AI-Driven Automation

This is the part most MCP tutorials skip entirely. When an AI agent is making decisions about your infrastructure, you need to observe the agent itself as carefully as you observe the infrastructure it manages.

What to Instrument

We treat the agent as a service with its own SLIs:

Metric What It Measures Alert Threshold
agent_iterations_per_task How many reasoning loops per task > 8 iterations = agent is confused
agent_tool_calls_total Tool calls by server, tool, and classification > 100 write calls/hour = runaway agent
agent_approval_wait_seconds Time waiting for human approval > 300s = approval expired, action dropped
agent_task_duration_seconds End-to-end task completion time > 120s = something is stuck
agent_action_success_rate % of write actions that achieved desired state < 80% = agent is making bad decisions
agent_hallucination_rate Tool calls with invalid arguments (404s, validation errors) > 5% = prompt needs tuning
agent_cost_per_task_usd LLM API cost per task > $0.50/task = model or prompt inefficiency

Integration Patterns: Kubernetes, AWS, and CI/CD

Kubernetes MCP Server: Beyond Read-Only

Our Kubernetes MCP server exposes 14 tools. The write tools use rollout restart and scale — never raw apply or patch on arbitrary resources.

# The restart tool — uses rollout restart, not pod delete
@server.call_tool()
async def restart_deployment(namespace: str, deployment: str) -> str:
    """Trigger a rolling restart of a deployment."""
    # Pre-flight checks
    dep = apps_v1.read_namespaced_deployment(deployment, namespace)
    total_pods = dep.spec.replicas or 0

    if total_pods > BLAST_RADIUS_LIMITS["restart_deployment"]["max_pods_affected"]:
        return f"Blocked: deployment has {total_pods} pods (max {max_pods})"

    # Check cooldown
    last_restart = restart_cooldowns.get(f"{namespace}/{deployment}")
    if last_restart and (time.time() - last_restart) < 300:
        return f"Blocked: deployment was restarted {int(time.time() - last_restart)}s ago (cooldown: 300s)"

    # Execute rolling restart (not delete — pods are replaced gracefully)
    now = datetime.utcnow().isoformat() + "Z"
    apps_v1.patch_namespaced_deployment(deployment, namespace, {
        "spec": {"template": {"metadata": {"annotations": {
            "kubectl.kubernetes.io/restartedAt": now
        }}}}
    })
    restart_cooldowns[f"{namespace}/{deployment}"] = time.time()
    return f"Rolling restart initiated for {namespace}/{deployment} ({total_pods} pods)"

AWS MCP Server: Cost-Aware Actions

The AWS MCP server wraps boto3 calls with cost estimation. Before any capacity change, the agent knows the cost impact:

@server.call_tool()
async def modify_asg_capacity(asg_name: str, desired: int) -> str:
    """Modify ASG desired capacity with cost estimation."""
    asg = autoscaling.describe_auto_scaling_groups(
        AutoScalingGroupNames=[asg_name]
    )["AutoScalingGroups"][0]

    current = asg["DesiredCapacity"]
    instance_type = asg["LaunchTemplate"]["InstanceType"]  # simplified
    hourly_cost = EC2_PRICING.get(instance_type, 0.10)
    delta = desired - current
    monthly_impact = delta * hourly_cost * 730  # hours/month

    autoscaling.set_desired_capacity(
        AutoScalingGroupName=asg_name, DesiredCapacity=desired
    )
    return (f"ASG {asg_name}: {current} → {desired} instances. "
            f"Estimated cost impact: ${monthly_impact:+.2f}/month")

CI/CD Integration: Triggering Rollbacks

@server.call_tool()
async def trigger_rollback(repo: str, environment: str) -> str:
    """Trigger a rollback via GitHub Actions workflow dispatch."""
    # Get the last successful deployment SHA
    runs = github.get_workflow_runs(repo, "deploy.yml", status="success", per_page=2)
    if len(runs) < 2:
        return "Cannot rollback: fewer than 2 successful deployments found"

    previous_sha = runs[1]["head_sha"]  # second-most-recent success

    github.create_workflow_dispatch(
        repo, "deploy.yml",
        ref="main",
        inputs={"target_sha": previous_sha, "environment": environment}
    )
    return f"Rollback triggered for {repo} to {previous_sha[:8]} in {environment}"

Challenges and Lessons Learned

❌ Mistakes We Made

  • Trusting the LLM to pick the right environment. Early on, the agent defaulted to "production" when the environment wasn't specified. We lost 3 pods in staging (thought it was prod) before making environment a required, non-defaultable parameter.
  • Not rate-limiting the reasoning loop. The agent once made 47 Prometheus queries in 90 seconds trying to "find the service with the highest error rate across all namespaces." Prometheus started dropping scrapes. Now we cap at 50 tool calls per task, period.
  • Letting the agent write its own PromQL. LLMs are mediocre at PromQL. They confuse rate() with increase(), forget to wrap histograms in histogram_quantile(), and invent label names. We switched to pre-built query templates that the agent fills in with parameters — accuracy went from 72% to 96%.
  • No verification step after write actions. The agent would restart a deployment and immediately report success — without checking if the new pods actually came up healthy. Now every write action is followed by a mandatory verification tool call with a 30-second wait.
  • Ignoring token costs during development. Our first agent prototype used GPT-4 with full pod specs in the context (including all labels, annotations, and status conditions). Each task cost $0.80. Stripping responses to essential fields brought it to $0.18.

✅ What Worked Well

  • The approval workflow via Slack. Engineers love that they can see exactly what the agent wants to do and approve with one click. Approval rate is 91% — meaning the agent proposes the right action most of the time.
  • Pre-built PromQL templates. Instead of letting the LLM write raw PromQL, we expose tools like get_error_rate(service, window) and get_latency_percentile(service, percentile, window). The agent picks the right tool; the server writes the correct query.
  • Mandatory post-action verification. The system prompt instructs the agent to always verify after a write action. If verification fails, it reports the failure instead of silently moving on.
  • Daily error pattern analysis. The scheduled daily report catches slow-burn issues that don't trigger alerts but degrade over time. It found an Elasticsearch memory leak 3 days before it would have caused an outage.

Best Practices

  1. Classify every tool before the agent can use it. Read, write, or blocked. Unknown = blocked. No exceptions.
  2. Make environment a required parameter on every tool. Never let the agent default to production. Ever.
  3. Use pre-built query templates instead of raw PromQL/SQL. LLMs are bad at query languages. Give them high-level tools and let the server handle the syntax.
  4. Every write action must be followed by verification. Bake this into the system prompt and validate it in the agent controller. If the agent skips verification, flag it.
  5. Set blast radius limits on every write tool. Max replicas, cooldown periods, capacity ceilings. These are your last line of defense against a confused LLM.
  6. Observe the agent like you observe your services. Success rate, hallucination rate, cost per task, iteration count. Build a dashboard. Set alerts.
  7. Run the agent in shadow mode first. For the first month, the agent proposes actions but doesn't execute them. Compare its proposals against what the on-call engineer actually did. Our agent agreed with the human 87% of the time before we turned on execution.
  8. Keep the system prompt under 1,000 tokens. Long system prompts waste money on every API call and don't improve reasoning. Be concise.

Conclusion

We've been running MCP-based infrastructure agents in production for 5 months. The agent handles ~80 tasks per day — mostly diagnostic queries, but increasingly automated remediations. It's not replacing our SRE team. It's handling the repetitive, well-understood tasks so the team can focus on the hard problems.

The key insight: the guardrails are the product. Anyone can connect an LLM to kubectl. The engineering challenge is building the classification system, approval workflow, blast radius limits, verification steps, and observability that make it safe to run in production. That's where 80% of our development time went, and it's the reason we trust it with write access to production Kubernetes.

If you're starting from scratch: build a read-only diagnostic agent first (see my earlier post). Run it for 2 months. Study the logs. Then add one write tool at a time, with approval gates and blast radius limits. The agent will earn your trust — or it won't, and you'll know exactly why from the observability data.

The goal isn't autonomous infrastructure. The goal is infrastructure that's easier to operate — where the AI handles the mechanical work and humans handle the judgment calls. MCP gives us the protocol to build that safely.
