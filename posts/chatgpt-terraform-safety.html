We Tested AI-Generated Terraform in Production for 3 Months

Our platform team generates a lot of Terraform — new services, IAM roles, networking configs, database setups. When AI coding assistants got good enough to write plausible HCL, we decided to test it systematically. For 3 months, we tracked every piece of AI-generated Terraform that made it into a PR, what passed review, what didn't, and what slipped through.

The verdict: useful assistant, dangerous autopilot.

The Good: Where AI Terraform Shines

✅
Boilerplate generation

Module scaffolding, variable definitions, output blocks, provider configs. AI generates these 3-4x faster than writing from scratch.

✅
Module structure

AI consistently produces well-organized modules with proper separation of variables.tf, outputs.tf, and main.tf.

✅
Variable naming and descriptions

Surprisingly good at choosing descriptive variable names and writing helpful description fields.

✅
Documentation

README generation for modules, inline comments explaining resource relationships — better than most humans write.

The Bad: Common AI Terraform Mistakes

1. Outdated Provider Syntax

AI frequently generates Terraform 0.12-era syntax when you need 1.5+:

# ❌ AI-generated (outdated)
provider "aws" {
  region  = var.region
  version = "~> 4.0"
}

# ✅ Correct (Terraform 1.x)
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
  required_version = ">= 1.5.0"
}

provider "aws" {
  region = var.region
}

2. Missing required_providers Block

In 31 out of 142 PRs, the AI omitted the required_providers block entirely. This works locally but breaks in CI where providers aren't cached.

3. Wrong Resource Attribute Names

# ❌ AI-generated (wrong attribute)
resource "aws_instance" "web" {
  ami           = var.ami_id
  instance_type = var.instance_type
  subnet        = var.subnet_id  # Wrong! It's 'subnet_id'
}

# ✅ Correct
resource "aws_instance" "web" {
  ami           = var.ami_id
  instance_type = var.instance_type
  subnet_id     = var.subnet_id
}

The Ugly: 6 Security Issues in 3 Months

These are the ones that matter. AI-generated Terraform is confidently insecure — it produces code that looks correct but has serious security gaps.

Issue 1: Overly Permissive IAM

# ❌ AI-generated — wildcard permissions
resource "aws_iam_role_policy" "lambda_policy" {
  name = "lambda-policy"
  role = aws_iam_role.lambda_role.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = "s3:*"          # Too broad!
      Resource = "*"              # Way too broad!
    }]
  })
}

# ✅ Fixed — least privilege
resource "aws_iam_role_policy" "lambda_policy" {
  name = "lambda-policy"
  role = aws_iam_role.lambda_role.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = ["s3:GetObject", "s3:PutObject"]
      Resource = "${aws_s3_bucket.data.arn}/*"
    }]
  })
}

Issue 2: Public S3 Buckets

# ❌ AI-generated — missing public access block
resource "aws_s3_bucket" "uploads" {
  bucket = "my-app-uploads"
}

# ✅ Fixed — always add public access block
resource "aws_s3_bucket" "uploads" {
  bucket = "my-app-uploads"
}

resource "aws_s3_bucket_public_access_block" "uploads" {
  bucket = aws_s3_bucket.uploads.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_server_side_encryption_configuration" "uploads" {
  bucket = aws_s3_bucket.uploads.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "aws:kms"
    }
  }
}

Issue 3: Missing Encryption

AI generated an RDS instance without encryption, without deletion protection, and with a publicly accessible endpoint:

# ❌ AI-generated
resource "aws_db_instance" "main" {
  engine         = "postgres"
  engine_version = "15.4"
  instance_class = "db.t3.medium"
  db_name        = "myapp"
  username       = "admin"
  password       = "supersecret123"  # Hardcoded password!
}

# ✅ Fixed
resource "aws_db_instance" "main" {
  engine                 = "postgres"
  engine_version         = "15.4"
  instance_class         = "db.t3.medium"
  db_name                = "myapp"
  username               = "admin"
  manage_master_user_password = true  # AWS Secrets Manager

  storage_encrypted      = true
  kms_key_id             = aws_kms_key.rds.arn
  deletion_protection    = true
  publicly_accessible    = false
  skip_final_snapshot    = false
  final_snapshot_identifier = "myapp-final-snapshot"

  vpc_security_group_ids = [aws_security_group.rds.id]
  db_subnet_group_name   = aws_db_subnet_group.main.name
}

Our Workflow: AI Drafts, Humans Verify

After the first month, we established a mandatory pipeline for all AI-generated Terraform:

AI Generates Draft
Human Reviews Structure
tfsec + Checkov Scan
terraform plan Review
Peer Review (2 approvals)
terraform apply (via Atlantis)

Checkov Rules That Catch AI Mistakes

These are the Checkov checks that fire most often on AI-generated code:

# .checkov.yml
framework:
  - terraform
check:
  # S3
  - CKV_AWS_18   # Ensure S3 bucket has logging enabled
  - CKV_AWS_19   # Ensure S3 bucket has server-side encryption
  - CKV_AWS_53   # Ensure S3 bucket has block public access
  - CKV_AWS_145  # Ensure S3 bucket is encrypted with KMS

  # IAM
  - CKV_AWS_1    # Ensure IAM policies don't allow full '*' access
  - CKV_AWS_40   # Ensure IAM policy is not overly permissive
  - CKV_AWS_62   # Ensure no IAM policies with admin privileges

  # RDS
  - CKV_AWS_16   # Ensure RDS encryption is enabled
  - CKV_AWS_17   # Ensure RDS has logging enabled
  - CKV_AWS_118  # Ensure RDS has deletion protection
  - CKV_AWS_157  # Ensure RDS is not publicly accessible

  # Security Groups
  - CKV_AWS_23   # Ensure SG doesn't allow ingress from 0.0.0.0/0
  - CKV_AWS_24   # Ensure no SG allows ingress from 0.0.0.0/0 to port 22
  - CKV_AWS_25   # Ensure no SG allows ingress from 0.0.0.0/0 to port 3389
# Run in CI pipeline
checkov -d . --config-file .checkov.yml --compact --quiet

# tfsec for additional coverage
tfsec . --minimum-severity HIGH --format json
Checkov alone isn't enough

Checkov caught 4 of our 6 security issues. The other 2 (overly permissive IAM with specific service actions, and a Lambda role with too many permissions) required human review. Static analysis catches patterns, not intent.

The Confidently Wrong Problem

The most dangerous aspect of AI-generated Terraform isn't the obvious errors — it's the plausible-looking but subtly wrong configurations. Examples we caught:

  • An ALB listener rule that looked correct but had the wrong priority ordering, causing a catch-all rule to match before specific routes
  • A VPC peering config that referenced the wrong route table, creating an asymmetric routing issue that only manifested under load
  • An ECS task definition with correct syntax but wrong CPU/memory ratios that caused Fargate placement failures
  • A CloudWatch alarm that monitored the right metric but used Average instead of p99, missing latency spikes entirely

These pass terraform validate, pass Checkov, and even pass terraform plan. They only fail in production.

The Verdict

✅ Use AI For

  • Module scaffolding and boilerplate
  • Variable and output definitions
  • README and documentation
  • Converting between resource types
  • Writing Terraform import blocks

❌ Don't Trust AI For

  • IAM policies (always review manually)
  • Security group rules
  • Encryption configuration
  • Network topology decisions
  • Production-critical resource settings

AI-generated Terraform is like a junior engineer's first draft: structurally sound, occasionally brilliant, but needs a senior review before it touches production. The 40% speed boost is real, but only if you invest in the review pipeline to catch the 15% that's wrong.
