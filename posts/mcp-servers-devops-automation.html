What Is Model Context Protocol (MCP)?

Model Context Protocol is an open standard created by Anthropic that defines how AI models interact with external tools and data sources. Think of it as a USB-C for AI tools — a standardized interface so any AI model can use any tool without custom integration code.

Before MCP, connecting an LLM to kubectl meant writing custom LangChain tools, handling authentication, parsing output, and managing errors — all bespoke code per tool. MCP standardizes this into a server-client architecture where tool providers expose capabilities through a consistent protocol.

AI Client (Claude, ChatGPT, etc.)
MCP Protocol (JSON-RPC over stdio/SSE)
MCP Server (kubectl, terraform, aws-cli)
Infrastructure

Why MCP Matters for DevOps

DevOps engineers interact with dozens of tools daily: kubectl, terraform, aws cli, helm, docker, prometheus, grafana, pagerduty. Each has its own CLI syntax, output format, and authentication model. MCP lets you expose all of these through a single, standardized interface that any AI model can use.

Without MCP

  • Custom LangChain tool per CLI
  • Bespoke output parsing
  • Per-model integration code
  • Auth handling in application code
  • No standardized error handling

With MCP

  • One MCP server per tool
  • Standardized JSON responses
  • Works with any MCP-compatible client
  • Auth handled at server level
  • Consistent error protocol

Building a Kubernetes MCP Server

Let's build an MCP server that exposes Kubernetes operations. This server lets any MCP-compatible AI client query pods, read logs, check events, and inspect deployments.

Project Setup

# Install the MCP Python SDK
pip install mcp kubernetes

# Project structure
kubernetes-mcp/
├── server.py
├── tools.py
└── requirements.txt

Server Implementation

import asyncio
from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp.types import Tool, TextContent
import json
from kubernetes import client, config

# Load kubeconfig
config.load_kube_config()
v1 = client.CoreV1Api()
apps_v1 = client.AppsV1Api()

server = Server("kubernetes-mcp")

@server.list_tools()
async def list_tools():
    return [
        Tool(
            name="get_pods",
            description="List pods in a namespace with their status, restarts, and age",
            inputSchema={
                "type": "object",
                "properties": {
                    "namespace": {
                        "type": "string",
                        "description": "Kubernetes namespace (default: 'default')"
                    },
                    "label_selector": {
                        "type": "string",
                        "description": "Label selector to filter pods (e.g., 'app=nginx')"
                    }
                }
            }
        ),
        Tool(
            name="get_pod_logs",
            description="Get recent logs from a specific pod",
            inputSchema={
                "type": "object",
                "properties": {
                    "namespace": {"type": "string"},
                    "pod_name": {"type": "string"},
                    "tail_lines": {
                        "type": "integer",
                        "description": "Number of recent lines (default: 50, max: 200)"
                    }
                },
                "required": ["namespace", "pod_name"]
            }
        ),
        Tool(
            name="get_events",
            description="Get recent Kubernetes events, optionally filtered by namespace",
            inputSchema={
                "type": "object",
                "properties": {
                    "namespace": {"type": "string"},
                    "event_type": {
                        "type": "string",
                        "enum": ["Normal", "Warning"],
                        "description": "Filter by event type"
                    }
                }
            }
        ),
        Tool(
            name="describe_deployment",
            description="Get detailed info about a deployment including replicas, strategy, and conditions",
            inputSchema={
                "type": "object",
                "properties": {
                    "namespace": {"type": "string"},
                    "deployment_name": {"type": "string"}
                },
                "required": ["namespace", "deployment_name"]
            }
        )
    ]

@server.call_tool()
async def call_tool(name: str, arguments: dict):
    if name == "get_pods":
        ns = arguments.get("namespace", "default")
        selector = arguments.get("label_selector", "")
        pods = v1.list_namespaced_pod(ns, label_selector=selector)
        result = []
        for pod in pods.items:
            restarts = sum(
                cs.restart_count for cs in (pod.status.container_statuses or [])
            )
            result.append({
                "name": pod.metadata.name,
                "status": pod.status.phase,
                "restarts": restarts,
                "node": pod.spec.node_name,
                "ip": pod.status.pod_ip
            })
        return [TextContent(type="text", text=json.dumps(result, indent=2))]

    elif name == "get_pod_logs":
        ns = arguments["namespace"]
        pod = arguments["pod_name"]
        lines = min(arguments.get("tail_lines", 50), 200)
        logs = v1.read_namespaced_pod_log(pod, ns, tail_lines=lines)
        return [TextContent(type="text", text=logs)]

    elif name == "get_events":
        ns = arguments.get("namespace")
        event_type = arguments.get("event_type")
        if ns:
            events = v1.list_namespaced_event(ns)
        else:
            events = v1.list_event_for_all_namespaces()
        result = []
        for e in events.items[-20:]:  # Last 20 events
            if event_type and e.type != event_type:
                continue
            result.append({
                "type": e.type,
                "reason": e.reason,
                "message": e.message,
                "object": f"{e.involved_object.kind}/{e.involved_object.name}",
                "count": e.count,
                "last_seen": e.last_timestamp.isoformat() if e.last_timestamp else None
            })
        return [TextContent(type="text", text=json.dumps(result, indent=2))]

    elif name == "describe_deployment":
        ns = arguments["namespace"]
        name_arg = arguments["deployment_name"]
        dep = apps_v1.read_namespaced_deployment(name_arg, ns)
        result = {
            "name": dep.metadata.name,
            "replicas": dep.spec.replicas,
            "available": dep.status.available_replicas,
            "strategy": dep.spec.strategy.type,
            "image": dep.spec.template.spec.containers[0].image,
            "conditions": [
                {"type": c.type, "status": c.status, "message": c.message}
                for c in (dep.status.conditions or [])
            ]
        }
        return [TextContent(type="text", text=json.dumps(result, indent=2))]

async def main():
    async with stdio_server() as (read_stream, write_stream):
        await server.run(read_stream, write_stream)

if __name__ == "__main__":
    asyncio.run(main())

Connecting to Claude Desktop

Once the MCP server is built, connecting it to Claude Desktop (or any MCP client) is a config file change:

// ~/Library/Application Support/Claude/claude_desktop_config.json
{
  "mcpServers": {
    "kubernetes": {
      "command": "python",
      "args": ["/path/to/kubernetes-mcp/server.py"],
      "env": {
        "KUBECONFIG": "/Users/you/.kube/config"
      }
    }
  }
}

Now you can ask Claude: "What pods are crashing in the payments namespace?" and it will call the MCP server, run the kubectl query, and give you a natural language answer with the actual pod data.

MCP vs LangChain Tools

Aspect LangChain Tools MCP Servers
Coupling Tightly coupled to LangChain framework Framework-agnostic protocol
Reusability Python-only, one framework Any language, any MCP client
Discovery Hardcoded in agent code Dynamic tool discovery via protocol
Auth Handled in application code Handled at server level, isolated
Ecosystem Mature, large community Growing rapidly, early but promising
Best for Custom agents, complex chains Standardized tool access, multi-client

Security Model: MCP Servers as Controlled API Surfaces

This is the key insight for DevOps teams: MCP servers act as a security boundary between AI models and your infrastructure. Instead of giving an AI model direct access to kubectl or AWS CLI, you expose a controlled set of operations through the MCP server.

Never give AI models raw CLI access

An MCP server should be a curated, read-only API surface. The server decides what operations are allowed, validates inputs, enforces rate limits, and logs every call. The AI model never sees raw credentials or has direct shell access.

  • Input validation — the server validates all parameters before executing commands
  • Operation whitelist — only expose operations you've explicitly implemented
  • Output sanitization — strip secrets, tokens, and sensitive data from responses
  • Rate limiting — prevent runaway AI loops from hammering your cluster
  • Audit logging — every tool call is logged with timestamp, parameters, and caller
  • Separate credentials — the MCP server uses a dedicated service account with minimal RBAC

Current Limitations

⚠️ What's Not Ready Yet

  • Authentication between client and server — MCP doesn't have a built-in auth layer yet. For now, rely on OS-level process isolation.
  • Multi-tenant support — one server instance per user/context. No built-in RBAC within MCP itself.
  • Streaming for long operations — terraform plan on a large state file can take minutes. MCP's current streaming support is limited.
  • Error recovery — if the server crashes mid-operation, the client has no standard way to recover or retry.
  • Remote servers — most MCP servers run locally via stdio. Remote server support (SSE transport) is available but less mature.

Where This Is Heading

MCP is the foundation for what I'm calling AI-native operations platforms. Instead of engineers writing kubectl commands and reading Grafana dashboards, they'll describe what they want in natural language and the AI will orchestrate the tools.

Now (2024-2025)

MCP servers for individual tools. Read-only diagnostics. Engineers use AI as a faster CLI.

Near Future (2025-2026)

Composable MCP servers. AI chains multiple tools: "diagnose why checkout is slow" → queries Prometheus, reads pod logs, checks recent deploys, correlates with alerts.

Medium Term (2026-2027)

AI-native runbooks. Instead of Markdown runbooks, teams define MCP tool chains that AI executes with human approval gates.

Long Term

Self-healing infrastructure where AI agents continuously monitor, diagnose, and remediate — with humans setting policy, not executing commands.

Getting Started

  1. Pick one tool — start with kubectl or AWS CLI, whichever your team uses most
  2. Build a read-only MCP server — 4-5 tools that answer the most common diagnostic questions
  3. Connect to Claude Desktop or your preferred MCP client — test with real queries from your last 5 incidents
  4. Add tools incrementally — one new tool per week, based on what engineers actually ask for
  5. Never add write tools without approval gates — read-only is safe; write operations need human confirmation

MCP won't replace your DevOps tools. It will make them accessible to every engineer on your team through natural language, with the safety guardrails that production infrastructure demands.
