Why Canary Deployments?

In the last 6 months, canary deployments caught 3 critical bugs before they reached 100% of our users. One was a memory leak that would have taken down our checkout service during peak hours. Another was a database query regression that increased p99 latency by 400%. The third was a broken feature flag evaluation that returned null for 15% of users.

None of these were caught by unit tests, integration tests, or staging environments. They only manifested under real production traffic patterns. That's the entire point of canary — you test with real users at a controlled blast radius.

Argo Rollouts vs Native Kubernetes Rolling Updates

Kubernetes' built-in rolling update strategy is binary — it replaces pods gradually, but there's no traffic control. If the new version is broken, all pods eventually run the bad code before you notice.

FeatureNative Rolling UpdateArgo Rollouts
Traffic splitting❌ Pod ratio only✅ Weighted traffic routing
Pause between steps❌✅ Manual or timed pauses
Automated analysis❌✅ AnalysisTemplate with Prometheus
Auto rollback❌ Manual only✅ On metric failure
Blue-green support❌✅ Built-in
Header-based routing❌✅ With Istio/Nginx

Rollout Resource: Canary with Progressive Delivery

Here's the Rollout spec we use for our payment service — the most critical service in our stack:

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: payment-service
  namespace: production
spec:
  replicas: 10
  revisionHistoryLimit: 3
  selector:
    matchLabels:
      app: payment-service
  strategy:
    canary:
      canaryService: payment-service-canary
      stableService: payment-service-stable
      trafficRouting:
        istio:
          virtualServices:
            - name: payment-service-vsvc
              routes:
                - primary
      steps:
        - setWeight: 10
        - pause: { duration: 5m }
        - analysis:
            templates:
              - templateName: canary-success-rate
            args:
              - name: service-name
                value: payment-service
        - setWeight: 30
        - pause: { duration: 10m }
        - analysis:
            templates:
              - templateName: canary-success-rate
        - setWeight: 60
        - pause: { duration: 10m }
        - setWeight: 100
      rollbackWindow:
        revisions: 2
  template:
    metadata:
      labels:
        app: payment-service
    spec:
      containers:
        - name: payment-service
          image: 123456789.dkr.ecr.us-east-1.amazonaws.com/payment-service:v2.4.1
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: "500m"
              memory: "512Mi"
            limits:
              cpu: "1"
              memory: "1Gi"

The Step-by-Step Flow

10% traffic → canary (5 min pause)
Run AnalysisTemplate — check error rate & latency
30% traffic → canary (10 min pause)
Run AnalysisTemplate again
60% traffic → canary (10 min pause)
100% traffic → promote to stable

AnalysisTemplate: Automated Metric Validation

This is where canary deployments become truly powerful. Instead of a human watching dashboards, Argo Rollouts queries Prometheus and makes pass/fail decisions automatically.

apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: canary-success-rate
spec:
  args:
    - name: service-name
  metrics:
    - name: error-rate
      interval: 60s
      count: 5
      successCondition: result[0] < 0.02  # less than 2% error rate
      failureLimit: 2
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(http_requests_total{
              service="{{args.service-name}}",
              status=~"5..",
              canary="true"
            }[2m])) /
            sum(rate(http_requests_total{
              service="{{args.service-name}}",
              canary="true"
            }[2m]))
    - name: latency-p99
      interval: 60s
      count: 5
      successCondition: result[0] < 500  # p99 under 500ms
      failureLimit: 2
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            histogram_quantile(0.99,
              sum(rate(http_request_duration_seconds_bucket{
                service="{{args.service-name}}",
                canary="true"
              }[2m])) by (le)
            ) * 1000

Real Example: Canary Caught a Memory Leak at 10%

🚨 Incident: Memory Leak Detected at 10% Traffic

A new version of our order service had a memory leak in the connection pool — it wasn't closing Redis connections properly under high concurrency. At 10% traffic, the canary pod's memory grew from 512MB to 1.8GB in 4 minutes. The AnalysisTemplate didn't catch it directly (error rate was fine), but our memory-based analysis caught the anomaly.

We added a memory growth metric to our AnalysisTemplate after this incident:

- name: memory-growth
  interval: 120s
  count: 3
  successCondition: result[0] < 1.5  # memory shouldn't grow more than 50%
  provider:
    prometheus:
      address: http://prometheus.monitoring:9090
      query: |
        container_memory_working_set_bytes{
          pod=~"order-service-.*",
          container="order-service"
        } /
        on() group_left()
        container_memory_working_set_bytes{
          pod=~"order-service-.*",
          container="order-service"
        } offset 5m

Traffic Splitting: Weight-Based vs Header-Based

Weight-Based (Production Traffic)

This is what we use for most services. Real user traffic is split by percentage. The Istio VirtualService handles the routing:

apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: payment-service-vsvc
spec:
  hosts:
    - payment-service
  http:
    - name: primary
      route:
        - destination:
            host: payment-service-stable
          weight: 90
        - destination:
            host: payment-service-canary
          weight: 10

Header-Based (Internal Testing)

For pre-production validation, we route specific requests to the canary using headers. QA teams add x-canary: true to test the new version before any real users see it:

http:
  - match:
      - headers:
          x-canary:
            exact: "true"
    route:
      - destination:
          host: payment-service-canary
        weight: 100
  - route:
      - destination:
          host: payment-service-stable
        weight: 100

If you're already running Istio, use it. If not, Nginx ingress controller with Argo Rollouts works well for basic weight-based canary. Don't adopt Istio just for canary deployments.

Slack Notifications

We integrated Argo Rollouts with Slack via the Argo Notifications controller. Every rollout phase change triggers a message:

apiVersion: argoproj.io/v1alpha1
kind: Application  # notification trigger config
metadata:
  annotations:
    notifications.argoproj.io/subscribe.on-rollout-step-completed.slack: deployments
    notifications.argoproj.io/subscribe.on-rollout-completed.slack: deployments
    notifications.argoproj.io/subscribe.on-analysis-run-error.slack: deployments-alerts

Messages include: service name, current step (e.g., "30% canary"), analysis result (pass/fail), and a link to the Argo Rollouts dashboard.

Metrics That Matter for Analysis

Don't just check error rate. Here are the 5 metrics we validate during every canary:

  • 📊 Error rate — HTTP 5xx / total requests (threshold: <2%)
  • ⏱️ Latency p99 — 99th percentile response time (threshold: <500ms)
  • 🧠 Memory growth — Working set shouldn't grow >50% over 5 minutes
  • 🔄 Restart count — Any OOMKill or CrashLoopBackOff is an instant fail
  • 📈 Saturation — CPU utilization shouldn't exceed 80% at the same traffic level

Rollback Strategy

💡 Automatic vs Manual Rollback

If an AnalysisRun fails, Argo Rollouts automatically rolls back to the stable version. No human intervention needed. The canary pods are terminated, and 100% of traffic returns to stable within seconds. For manual rollback during a pause step: kubectl argo rollouts abort payment-service.

We set rollbackWindow.revisions: 2 so Argo keeps the last 2 stable ReplicaSets ready. This means rollback is instant — no image pull or pod scheduling delay.

✅ Bottom Line

Canary deployments with Argo Rollouts turned our deployment process from "deploy and pray" to "deploy and verify." The initial setup takes a day. The AnalysisTemplates take another day to tune. After that, every deployment is automatically validated against real production metrics. The 3 bugs we caught would have been P1 incidents affecting thousands of users.
