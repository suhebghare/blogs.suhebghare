The Performance Troubleshooting Toolkit

In 8 years of managing production Linux servers — from bare metal to EC2 to Kubernetes nodes — I've narrowed my toolkit to a handful of commands that solve 95% of performance issues. The key isn't knowing every flag; it's knowing which tool to reach for first.

The USE Method: Systematic Diagnosis

Before diving into tools, use Brendan Gregg's USE method. For every resource (CPU, memory, disk, network), check three things:

USE Method

  • Utilization — How busy is the resource? (% time busy)
  • Saturation — Is work queuing? (queue length)
  • Errors — Are there error events? (device errors, drops)

Quick Reference

  • CPU: mpstat, vmstat, top
  • Memory: free -h, vmstat, sar -r
  • Disk: iostat -xz, iotop
  • Network: ss -s, sar -n DEV, nstat

Scenario 1: High CPU — Finding the Culprit

You get paged: "Server CPU at 98%." Here's exactly what I run, in order:

# Step 1: What's the overall picture?
$ uptime
 14:23:01 up 45 days, load average: 12.34, 8.21, 4.56
# Load average > number of CPUs = saturated
# Rising load (4 → 8 → 12) = getting worse

# Step 2: Which processes are eating CPU?
$ top -bn1 -o %CPU | head -20
# -b = batch mode, -n1 = one iteration
# Look at the top consumers

# Step 3: Is it user space or kernel?
$ mpstat -P ALL 1 5
# %usr high = application code
# %sys high = kernel/syscalls (possibly I/O)
# %iowait high = waiting on disk (not CPU-bound)

# Step 4: What's the process actually doing?
$ strace -cp 12345
# Counts syscalls for PID 12345 over a few seconds
# High read/write = I/O bound disguised as CPU
# High futex = lock contention

# Step 5: For Java/Node — get a thread dump
$ kill -3 12345          # Java thread dump to stdout
$ node --prof-process    # Node.js profiling
The iowait Trap

High %iowait in top looks like CPU usage but it's actually disk I/O. The CPU is idle, waiting for disk. Don't scale up CPU — fix the disk bottleneck. I've seen teams add 8 more cores to a server that needed faster storage.

Scenario 2: Memory Pressure and the OOM Killer

# Step 1: Current memory state
$ free -h
              total    used    free    shared  buff/cache   available
Mem:           62Gi     58Gi    512Mi   1.2Gi      3.8Gi       2.1Gi
Swap:         4.0Gi    3.8Gi    200Mi
# available is what matters, not free
# Swap usage > 0 = memory pressure

# Step 2: Who's using memory?
$ ps aux --sort=-%mem | head -10
# Or for a live view:
$ top -bn1 -o %MEM | head -15

# Step 3: Has the OOM killer fired?
$ dmesg | grep -i "oom\|killed"
# Or check journal:
$ journalctl -k | grep -i oom

# Step 4: Per-process memory breakdown
$ cat /proc/12345/status | grep -i vm
VmPeak:  4521892 kB    # Peak virtual memory
VmRSS:   3218456 kB    # Resident (actual physical memory)
VmSwap:   102400 kB    # Swapped out

# Step 5: What's in the page cache?
$ cat /proc/meminfo | grep -E "Cached|Buffers|Slab"
OOM Killer Scoring

The kernel picks victims based on oom_score. Higher score = more likely to be killed. Check with cat /proc/PID/oom_score. Protect critical processes: echo -1000 > /proc/PID/oom_score_adj. But be careful — if nothing can be killed, the entire system hangs.

Scenario 3: Disk I/O Bottleneck

# Step 1: Is I/O the problem?
$ iostat -xz 1 5
Device  r/s    w/s    rkB/s   wkB/s  await  svctm  %util
nvme0n1 2500   800    45000   12000  4.2    0.3    85.0
# %util > 80% = saturated
# await > 10ms on SSD = something's wrong
# r/s + w/s = total IOPS

# Step 2: Which process is doing I/O?
$ iotop -oP
# -o = only show processes doing I/O
# -P = show processes, not threads

# Step 3: Benchmark the disk
$ fio --name=randread --ioengine=libaio --iodepth=32 \
    --rw=randread --bs=4k --direct=1 --size=1G \
    --numjobs=4 --runtime=30 --group_reporting
# Compare results to expected IOPS for your volume type
# gp3 EBS: 3,000 baseline IOPS
# io2: up to 64,000 IOPS

# Step 4: Check for filesystem issues
$ df -h          # Space usage
$ df -i          # Inode usage (can run out before space!)
$ tune2fs -l /dev/nvme0n1p1 | grep -i count
The Inode Exhaustion Incident

We had a server with 50% disk space free but couldn't create files. df -i showed 100% inode usage. A logging library was creating millions of tiny temp files. find /tmp -type f -mtime +1 | wc -l returned 12 million. Always monitor inode usage alongside disk space.

Scenario 4: Network Issues

# Step 1: Connection overview
$ ss -s
Total: 15234
TCP:   12891 (estab 8432, closed 3201, orphaned 12, timewait 1246)
# High TIME_WAIT = lots of short-lived connections
# High CLOSE_WAIT = application not closing connections

# Step 2: TCP retransmits (packet loss indicator)
$ nstat -az | grep -i retrans
TcpRetransSegs    45892    0.0
# High retransmits = network congestion or packet loss

# Step 3: Connection states breakdown
$ ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn
   8432 ESTAB
   1246 TIME-WAIT
    892 CLOSE-WAIT
    234 SYN-SENT
# CLOSE-WAIT piling up = your app has a connection leak

# Step 4: Bandwidth per interface
$ sar -n DEV 1 5
# Or real-time:
$ nload eth0

# Step 5: DNS resolution issues
$ dig +trace example.com
$ time nslookup example.com
# Slow DNS = slow everything

Systemd: Managing Services in Production

# Production-grade systemd unit file
[Unit]
Description=Order Processing Service
After=network-online.target postgresql.service
Wants=network-online.target
Requires=postgresql.service

[Service]
Type=notify
User=appuser
Group=appuser
WorkingDirectory=/opt/order-service
ExecStart=/opt/order-service/bin/server --config /etc/order-service/config.yaml
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=5
StartLimitBurst=3
StartLimitIntervalSec=60

# Security hardening
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/log/order-service /var/lib/order-service
PrivateTmp=true

# Resource limits
LimitNOFILE=65536
LimitNPROC=4096
MemoryMax=2G
CPUQuota=200%

# Logging
StandardOutput=journal
StandardError=journal
SyslogIdentifier=order-service

[Install]
WantedBy=multi-user.target
# Essential journalctl commands
$ journalctl -u order-service -f              # Follow logs
$ journalctl -u order-service --since "1h ago" # Last hour
$ journalctl -u order-service -p err           # Errors only
$ journalctl -u order-service --no-pager -n 100 | grep "ERROR"
$ journalctl --disk-usage                      # Check log storage
$ journalctl --vacuum-size=1G                  # Reclaim space

Cgroups: How Containers Use Them

Every container is just a process with cgroup limits. Understanding cgroups helps you debug container resource issues.

# See cgroup limits for a container (cgroups v2)
$ cat /sys/fs/cgroup/system.slice/docker-CONTAINER_ID.scope/memory.max
536870912    # 512MB memory limit

$ cat /sys/fs/cgroup/system.slice/docker-CONTAINER_ID.scope/cpu.max
50000 100000  # 50% of one CPU (50000/100000)

# Check if a container is being throttled
$ cat /sys/fs/cgroup/.../cpu.stat
usage_usec 1234567890
user_usec 1000000000
system_usec 234567890
nr_throttled 4521        # <-- This many times throttled
throttled_usec 89012345  # Total time spent throttled
Container CPU Throttling

If nr_throttled is high, your container's CPU limit is too low. In Kubernetes, this shows up as high latency with low CPU usage in metrics — confusing until you check throttling. This is why many teams remove CPU limits and only set CPU requests.

Kernel Tuning for Production

# /etc/sysctl.d/99-production.conf

# Network performance
net.core.somaxconn = 65535
net.core.netdev_max_backlog = 65535
net.ipv4.tcp_max_syn_backlog = 65535
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_fin_timeout = 15
net.ipv4.ip_local_port_range = 1024 65535

# TCP keepalive (detect dead connections faster)
net.ipv4.tcp_keepalive_time = 60
net.ipv4.tcp_keepalive_intvl = 10
net.ipv4.tcp_keepalive_probes = 6

# Memory
vm.swappiness = 10              # Prefer killing over swapping
vm.overcommit_memory = 0        # Heuristic overcommit
vm.dirty_ratio = 15
vm.dirty_background_ratio = 5

# File descriptors
fs.file-max = 2097152
fs.inotify.max_user_watches = 524288

# Connection tracking (important for k8s nodes)
net.netfilter.nf_conntrack_max = 1048576
# Apply without reboot
$ sysctl --system

# Verify
$ sysctl net.core.somaxconn
net.core.somaxconn = 65535

Shell Scripting Patterns for Automation

#!/bin/bash
# Production-safe script template
set -euo pipefail
IFS=$'\n\t'

readonly SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
readonly LOG_FILE="/var/log/maintenance/$(date +%Y%m%d_%H%M%S).log"

log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a "$LOG_FILE"; }
die() { log "FATAL: $*"; exit 1; }

# Cleanup trap
cleanup() {
    local exit_code=$?
    log "Script exiting with code $exit_code"
    # Release locks, remove temp files
    rm -f /tmp/maintenance.lock
    exit $exit_code
}
trap cleanup EXIT

# Prevent concurrent execution
exec 200>/tmp/maintenance.lock
flock -n 200 || die "Another instance is already running"

# Disk cleanup: remove files older than 7 days
log "Starting disk cleanup..."
find /var/log/app -name "*.log" -mtime +7 -delete 2>/dev/null || true
find /tmp -type f -mtime +3 -user appuser -delete 2>/dev/null || true

# Check disk space after cleanup
USAGE=$(df -h / | awk 'NR==2 {print $5}' | tr -d '%')
if (( USAGE > 85 )); then
    log "WARNING: Disk usage still at ${USAGE}%"
    # Send alert
fi

log "Cleanup complete"

Quick Reference Cheat Sheet

First 60 Seconds on a Problem Server

  1. uptime — load averages, how long has this been going on?
  2. dmesg -T | tail — kernel errors, OOM kills?
  3. vmstat 1 5 — CPU, memory, I/O overview
  4. iostat -xz 1 3 — disk saturation?
  5. free -h — memory and swap
  6. ss -s — connection states
  7. top -bn1 | head -20 — top consumers
  8. journalctl -p err --since "10m ago" — recent errors
