The Alert Fatigue Problem

Our SRE team was drowning. Every week, we were processing 200+ alerts across three EKS clusters, and the on-call engineer spent most of their shift triaging noise instead of fixing real problems. We ran the numbers over a quarter and the results were brutal:

73%
Alerts were noise (non-actionable)
47 min
Average MTTR per incident
68%
False positive rate
3.2
Pages per on-call shift (avg)

The classic response is "just tune your thresholds." We tried that. We spent two sprints adjusting Prometheus alert rules, adding inhibition rules in AlertManager, and grouping by namespace. It helped — we got from 280 alerts/week down to 200. But the fundamental problem remained: alerts were firing independently with no understanding of whether they were related or actionable.

Architecture: ML-Powered Alert Correlation

We built a lightweight Python service that sits between AlertManager and PagerDuty. Instead of suppressing alerts (dangerous — you'll miss real ones), we correlate them into incident clusters and enrich them with LLM-generated summaries.

Prometheus
AlertManager
Python ML Service (DBSCAN + GPT-4)
PagerDuty

The ML service receives alerts via AlertManager's webhook receiver, clusters them using DBSCAN, and forwards a single enriched incident to PagerDuty instead of 15 individual alerts.

Step 1: Alert Ingestion via Webhook

AlertManager sends grouped alerts to our service. Here's the webhook receiver:

from flask import Flask, request, jsonify
from datetime import datetime
import json

app = Flask(__name__)
alert_buffer = []

@app.route('/webhook', methods=['POST'])
def receive_alerts():
    payload = request.json
    for alert in payload.get('alerts', []):
        alert_buffer.append({
            'fingerprint': alert['fingerprint'],
            'labels': alert['labels'],
            'annotations': alert['annotations'],
            'starts_at': alert['startsAt'],
            'status': alert['status'],
            'received_at': datetime.utcnow().isoformat()
        })
    # Process buffer every 60 seconds via background thread
    return jsonify({'status': 'received'}), 200

We buffer alerts for 60 seconds before clustering. This window catches cascading failures that fire alerts within seconds of each other — a pod OOMKill triggers a deployment unavailable alert, which triggers an SLO burn rate alert. Same root cause, three pages.

Step 2: DBSCAN Clustering

We use DBSCAN (Density-Based Spatial Clustering) because it doesn't require specifying the number of clusters upfront, and it handles noise points well. The feature vector for each alert includes:

  • Namespace — one-hot encoded
  • Service name — one-hot encoded
  • Alert type — categorical (CPU, memory, pod, latency, error rate)
  • Timestamp — normalized to 0-1 within the buffer window
  • Severity — ordinal (info=0, warning=1, critical=2)
from sklearn.cluster import DBSCAN
from sklearn.preprocessing import OneHotEncoder
import numpy as np

def cluster_alerts(alerts):
    features = extract_features(alerts)
    clustering = DBSCAN(eps=0.3, min_samples=2).fit(features)

    clusters = {}
    for idx, label in enumerate(clustering.labels_):
        if label == -1:
            # Noise point — forward as individual alert
            clusters[f'single_{idx}'] = [alerts[idx]]
        else:
            clusters.setdefault(label, []).append(alerts[idx])

    return clusters
Tuning eps

We started with eps=0.5 and found it was too aggressive — it clustered unrelated alerts from the same namespace. After testing against 4 weeks of historical data, eps=0.3 gave us the best precision. Run your own backtests before deploying.

Step 3: Historical Pattern Learning

The real power came from learning which alerts engineers consistently acknowledged without action. We exported 6 months of PagerDuty acknowledgment data and built a suppression confidence score:

import pandas as pd

def calculate_suppression_score(alert, history_df):
    matching = history_df[
        (history_df['alert_name'] == alert['labels']['alertname']) &
        (history_df['namespace'] == alert['labels'].get('namespace', ''))
    ]
    if len(matching) < 10:
        return 0.0  # Not enough data

    ack_without_action = matching[
        (matching['acknowledged'] == True) &
        (matching['resolved_by'] == 'auto')
    ]
    score = len(ack_without_action) / len(matching)
    return round(score, 2)

Alerts with a suppression score above 0.85 get downgraded from PagerDuty page to Slack notification. We never fully suppress — they still go to a #alerts-low-priority channel. This is critical: suppression is how you miss the one time that flapping alert is actually a real outage.

Step 4: LLM-Generated Alert Summaries

When a cluster of alerts fires, the on-call engineer used to get 8 separate PagerDuty notifications. Now they get one, with a GPT-4 generated summary that includes probable root cause and suggested actions:

import openai

def generate_alert_summary(cluster_alerts):
    alert_text = "\n".join([
        f"- {a['labels']['alertname']}: {a['annotations'].get('description', 'N/A')} "
        f"(namespace: {a['labels'].get('namespace', 'unknown')}, "
        f"severity: {a['labels'].get('severity', 'unknown')})"
        for a in cluster_alerts
    ])

    response = openai.chat.completions.create(
        model="gpt-4",
        messages=[{
            "role": "system",
            "content": "You are an SRE assistant. Analyze correlated alerts and provide: "
                       "1) Probable root cause 2) Affected services 3) Suggested first response. "
                       "Be concise. Use bullet points."
        }, {
            "role": "user",
            "content": f"These alerts fired within 60 seconds of each other:\n{alert_text}"
        }],
        max_tokens=300,
        temperature=0.2
    )
    return response.choices[0].message.content
Cost Control

GPT-4 API calls cost ~$0.03-0.06 per summary. At 4-5 clusters per day, that's roughly $5-9/month. We set a hard limit of 50 API calls/day and fall back to a template-based summary if exceeded.

Step 5: PagerDuty Integration

The enriched incident goes to PagerDuty with the cluster summary, individual alert details, and links to relevant Grafana dashboards:

import requests

def create_pagerduty_incident(cluster, summary):
    payload = {
        "routing_key": PAGERDUTY_ROUTING_KEY,
        "event_action": "trigger",
        "payload": {
            "summary": f"[Correlated] {len(cluster)} alerts - {summary[:200]}",
            "severity": max(a['labels'].get('severity', 'warning') for a in cluster),
            "source": "alert-correlator",
            "custom_details": {
                "ai_summary": summary,
                "alert_count": len(cluster),
                "alerts": [a['labels']['alertname'] for a in cluster],
                "namespaces": list(set(a['labels'].get('namespace', '') for a in cluster))
            }
        }
    }
    requests.post("https://events.pagerduty.com/v2/enqueue", json=payload)

The Human Feedback Loop

This is the part most teams skip, and it's the most important. After every incident, the on-call engineer rates the AI summary:

  • Accurate — root cause was correct
  • Partially accurate — right direction, wrong specifics
  • Wrong — completely off base
  • Missed correlation — alerts should have been grouped but weren't

This feedback goes back into tuning the DBSCAN parameters and the LLM prompt. After 3 months, our prompt evolved significantly from the original version — we added specific context about our infrastructure patterns that the LLM couldn't know otherwise.

Lessons Learned

✅ What Worked

  • Correlate, don't suppress. Suppression hides problems. Correlation groups them so you see the full picture.
  • 60-second buffer window catches 90% of cascading alert storms without adding meaningful delay.
  • LLM summaries save 10-15 minutes per incident because the on-call engineer starts with context instead of reading 8 alert descriptions.
  • Human feedback loop improved clustering accuracy from 71% to 94% over 3 months.

❌ What Didn't Work

  • Auto-resolving alerts based on ML confidence. We tried it for 2 weeks. Missed a real database connection pool exhaustion because the pattern looked like a previous false positive.
  • Using GPT-3.5 instead of GPT-4. The summaries were too generic — "check the logs" isn't helpful at 3am.
  • Clustering across namespaces by default. A CPU spike in payments and notifications at the same time is usually two different problems, not one.

Should You Build This?

If your team gets fewer than 50 alerts/week, tune your AlertManager rules first — that's free and gets you 80% of the way. This ML pipeline is worth it when you've already done the basics and still have noise. The total build took us 3 weeks with one engineer, and the ongoing cost is ~$15/month (EC2 t3.small + GPT-4 API).

The goal isn't zero alerts. It's zero useless alerts. Every page should require a human decision.
